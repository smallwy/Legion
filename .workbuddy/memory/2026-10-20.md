## 美术轻量化：占位精灵从「厚涂稿」重制为「真像素」（CR-012）

**起因**：用户要求「不要太写实，美术不能太重」。

### 实测发现的问题（这就是"重"的根因）
原占位精灵虽然美术指引写着"像素风"，实际是 **AI 厚涂稿**：

| 项 | 实测值 |
|---|---|
| 分辨率 | 224×189 / 256×256 |
| 单张颜色数 | **15,915 ~ 24,817**（真像素应 ≤24） |
| 4 张体积 | 290.3 KB |
| 显示尺寸 | 40~56 px → 引擎 `baseScale = displaySize/贴图宽` ≈ **0.19** |

即：把 256px 厚涂稿缩到 1/5 再线性采样 → 必糊、必重。**关键洞察：像素风的本质是
`贴图宽度 = 显示宽度 ÷ 整数`，不是"画得像像素"。**

### 做法：`client/tools/pixelize_sprites.py`
1. 预乘 alpha 后 BOX 降采样（避免黑边）
2. 硬 alpha 阈值 80（去掉抗锯齿软边）
3. **去噪 + 补洞**（关键：阈值会切碎细腿产生游离像素；第一版没做，甲虫出现浮点）
4. 提饱和 1.35 / 对比 1.12（降采样会发灰）
5. 量化到 14 色（透明区先填主体均色，防止黑色占色板位）
6. 1px `#2D2438` 描边（alpha 膨胀取环带）
7. 输出 24/24/24/28px

### 结果
| 维度 | 前 | 后 |
|---|---|---|
| 颜色数 | 15,915~24,817 | 14~16（-99.9%） |
| 4 张体积 | 290.3 KB | **3.4 KB（-98.8%）** |
| 显存 | 933 KB | **9 KB** |
| 缩放 | 0.19（非整数） | **精确 ×2** |

- `BattleConfig` 的 `displaySize` 改为 48/48/48/56（全部 = 工作分辨率 ×2）。
- 原文 256px 归档到 `client/art-source/256px/`（归档≠删除）。
- 对比图：`client/docs/pixel-preview.png`。

### 诚实结论（重要，别自欺）
- 自动化只能做出**合格占位**，做不出好像素画。24px 低于原设计细节下限，
  飞虫/甲虫放大 8× 看面部仍糊；屏幕上 ×2 显示能读成"Q 萌小怪"，够验证玩法。
- 正式美术仍需人工重画（30–60 分钟/只）或外包。

### 引擎侧必做设置（已写进 client/README.md §4.1）
- 图片导入后 **Filter Mode = Point**、关闭 Mipmap，否则线性插值把像素糊掉。
- 代码路径不写 `setFilters`：3.8.0 源码核实 `setFilters` 存在，但 `Filter` 枚举未从 `cc` 重导出，
  各小版本导出路径不一致 → 用编辑器设置最稳。

### 文档同步
- 美术指引新增 **§1.5 轻量化硬指标**（可量化：≤24 色 / ≤3KB / 整数倍 / 禁渐变软阴影）+ §9 校验清单 2 项。
- 计划书 §8.1 登记 **CR-012**；台账 §四登记 CR-012。
- ⚠️ 踩坑：第一次写成 CR-010，**与 10-18 已有的 CR-010 撞号**。教训：追加变更编号前
  必须先 grep 现有最大编号（`grep -o "CR-0[0-9][0-9]" | sort -u | tail`）。
- 同时发现 CR-011 已把「2.2 次/秒 vs 0.65s/轮」按 1.54 次/秒定案，已同步修正
  `BattleConfig.ts` 里"待拍板"的过时注释。

## 返工：24px 版被用户否掉 → 改「网格直接绘制」（CR-013）

**用户反馈**：「之前的是像素风吗 第二也太糊了吧 看不清是啥」。

**我上一轮错在哪（方法论错误，不是参数没调好）**：
CR-012 做的是「256px 厚涂稿 → 降采样到 24px → 量化 16 色」。降采样会把**剪影细节和噪点一起
抹平**，色块是"压"出来的，不是"画"出来的。所以色数达标（14–16）、体积达标（3.4KB）、
缩放也整数倍了，**但放大后认不出是什么**——所有指标都合格而交付物不可用。
**结论：像素风的核心是在目标网格上控制剪影，低分辨率只是它的结果，不是它的手段。**

**新做法**：`client/tools/pixelart_gen.py`
- 32×32 网格，每只怪用几何图元按解剖结构摆放：椭圆（甲壳/头/腹）、线段（腿/触角/中缝）、
  三角（独角）；图元用 SDF 式判定（点到椭圆/线段距离）栅格化
- 自动三阶明暗：按**列内垂直位置**（顶部 30% → hi、底部 28% → lo、中间 → mid），
  天然得到顶光关系，不用逐只手调
- 统一 1px 墨色描边 `#1A161E`，四只怪看起来像一个系列
- 色数 9–11、单张 446–525 字节

**踩到的层序 bug（值得记）**：第一版把所有细节放在一个 `flat` 层、画在 `body` 之前 →
`body` 绘制时把**眼睛整片覆盖**，四只怪脸上只剩白高光点。
正确层序：`outline → back（腿/翅/触角）→ body（自动明暗）→ front（眼/鼻/腮红）→ line（瞳孔/高光）`。
教训：2D 分层渲染器必须有明确的「body 之下 / body 之上」两档，不能用单一 flat 层糊过去。

**踩到的对比度 bug**：虫子眼睛最初用深色（`#1E2214`）贴在深绿/钢蓝甲壳上，等于看不见。
改**亮琥珀眼白 `#EEDE82` + 竖瞳**才可读——深色主体上要放亮细节，这是像素画通用规则。

**结果**
| 维度 | 256px 厚涂原稿 | 24px 自动降采样 | 32px 程序化绘制 |
|---|---|---|---|
| 颜色数 | 15,915~24,817 | 14~16 | **9~11** |
| 4 张体积 | 290.3 KB | 3.4 KB | **1.9 KB** |
| 显存 | 933 KB | 9 KB | **16 KB** |
| 放大 8× 能否认出 | 能（不像像素） | **不能，糊成色块** | **能，剪影清晰** |

- 32px 版显存比 24px 版高（16KB vs 9KB），**这是为可读性付的必要代价**——4 张 16KB 可忽略，
  认不出的贴图才是真浪费。
- `BattleConfig` 的 `displaySize` 全部改 **64**（32×2）。体型差异靠**造型**表达（甲壳更宽、
  翅膀更开），不用非整数 displaySize 硬拉。
- 24px 中间版归档 `client/art-source/24px-autotrace/`；`pixelize_sprites.py` 标记为已废弃。

**新增验证手段**：`client/docs/pixel-preview-ingame.png` —— 按 64px 实际尺寸 + 深色战场底渲染，
这是真验收图。放大 8× 好看 ≠ 实际尺寸看得清，必须单独验。

**仍未闭环**：本机 Cocos Profiler 的 FPS / DrawCall（沙箱跑不了编辑器）。

## 战斗表现方案：定「读图式战斗」路线 + 修两个渲染层 bug

**用户提问**：「根据目前的像素绘画级别，战斗怎么做比较合适」。

### 结论：走「读图式战斗」，不走「演出式战斗」
当前美术是**单帧静态 32px、9–11 色、零动画帧、零特效素材**，所以任何"靠一帧帧画出来的
动作"都不可行。战斗表现必须建立在零素材成本的手段上：变换（位移/缩放/翻转）、
`Graphics` 几何图形、透明度、屏幕反馈（震屏/闪白/顿帧）、时序对比。

关键论点：**静态剪影 + 高对比在混战里的可辨认度，高于有动画的帧序列**——玩家不需要读懂
动物怎么挥爪，只需要知道"哪个圈是红的、什么时候落下"。32px 高度里画"抬手蓄力"只能画出
2–3 个色块的位移，信息量远不如一个圆环。这和美术指引 §4「状态靠特效不画新帧」是同一条路。

**几何符号语言（已定死）**：红圈=会伤到你 / 橙圈=对方在准备 / 金环=你在蓄力 /
绿菱形=可拾取。四种颜色承担全部危险等级信息，不依赖动画。

产出 `docs/战斗表现方案_PAWPACK.md`：三条像素风硬约束（禁非整数缩放 / 禁精灵旋转 /
动效对齐整像素）、P0/P1/P2 分级（每项标注美术帧数与代码落点）、同屏密度推算。

### 同屏密度是美术决定的硬约束（算出来的）
视野 960×540，敌人 64px → 横向最多 15 只；当前 `maxAlive=28` 占屏约 22%（包围盒），
实际视觉重叠更严重。建议 Day3 手感调优时降到 **16–18**，用"少而清晰"换压迫感。

### 修掉两个真 bug（都不是设计问题，是实现缺陷）
1. **背景草地盖住所有实体（致命）**：`buildWorld` 的节点创建顺序是
   `玩家 → 敌人 → 宠物 → 背景 → 特效层`，而 2D 绘制序 = children 遍历序。
   背景是 2400×1350 实心矩形且排在敌人之后 → 把玩家/敌人/宠物全盖住，直接跑只看到空地。
   **`z` 值救不了**（setPosition 的 z 不参与 2D 排序）——之前误以为靠 z 分层安全。
   修法：`BackgroundRenderer` 构造时 `setSiblingIndex(0)` 强制置底。
2. **贴着图后受击白闪消失**：白闪判据用了 `needProcBody()` = `!hasSprite`，
   精灵一加载成功就整段跳过，敌人挨打只剩 30% 缩放脉冲。修法：白闪独立成
   `drawHitFlash()`，判据只看 `hitPunch`；半径取贴图显示宽的 0.72（略小于本体），
   让贴图 1px 墨色描边露在白闪外侧 → 观感是"整只怪闪白但轮廓还在"。

**教训**：**动态 `addChild` 的 2D 项目，绘制顺序是显式契约，不能靠"创建顺序看起来对"**。
背景/特效这类全屏层必须用 `setSiblingIndex` 钉死，否则后面任何一次构造顺序调整都会翻车。

**待办**：缩放手感（`1.28/1.18/1.3` 在 Point 采样下会抖颗粒，建议收敛 ≤1.12 或改整像素位移）；
P0 剩余项（顿帧 / 死亡爆散 / 伤害飘字 / 前摇圈填充 / 玩家受击反馈）。

## ★ 方向核对：用户要的是「百炼英雄式场景战斗」，当前 demo 是「幸存者式」

**用户提问**：「我要的是百炼英雄那样的场景战斗玩法 是这样的吗」

### 核实结论：不是。且当前 demo 是严格照计划书做的——错在计划书那句话
查证《百炼英雄》（厂商咸宁心游，包名 `com.blyx.wd.android`）真实形态，多来源交叉一致：
- 品类被搜狐分析明确归为 **「佣兵团like」**，对标《轰隆隆佣兵团》；文中直接指出
  **「割草感并不显著」**——所以它根本不是幸存者like。
- 真实玩法：**英雄小队 4–5 人（坦克/输出/辅助）列队跟随主角**，摇杆**拖动整队走位**，
  **自动普攻 + 技能 15s/60s 长 CD 手动放**，打**场景里布点的怪群 + 固定 BOSS**，
  BOSS 有 **AOE 读条**靠走位拉扯躲；目标是**推图通关**，**局内无成长**（全靠局外养成）。

**根因**：`docs/立项计划书_PAWPACK_v1.0.md` §2.2 第 151 行写
「玩家 WASD 只控制中心点走位，宠物**环绕**中心点自动施法捕杀——即"百炼英雄式"的移动中捕杀手感」。
**这句类比从一开始就偏了**：百炼英雄是"小队跟随"，不是"宠物环绕"。
反讽的是，同节 CR-008 的「走过去踩一窝」描述**反而更接近真实**（场景布点怪群），
但代码把它实现成了**清空后冷却无限重刷**（`MonsterNest` 的 `respawnDelay → dormant`），
再配上 `BattleDirector` 的 `durationMs` 倒计时撤离 → 合起来就成了刷怪场。

### 偏差清单（7 条，架构级，不是调参能解决）

| 队伍形态 | 宠物**环绕**转圈 | 英雄**列队跟随**（前/中/后排） |
| 玩家 | 无实体，只是个坐标点 | 主角在场，是队伍一员 |
| 屏幕 | **横屏 960×540** | **竖屏**单手握持 |
| 敌人来源 | 怪窝**无限循环刷** | 场景**固定布点**，清完推进 |
| 敌人 AI | 直线追人 | 仇恨 / 站位 / AOE 读条 |
| 一局目标 | **倒计时撤离** | **清点推进 / 击杀 BOSS** |
| 局内成长 | 捡经验珠 | **无**（全靠局外养成） |

## 战斗形态改造落地（CR-014）：环绕 → 列队跟随 + 清窝推进打 BOSS

### 代码改动（battle 层重写 3 块，渲染层全复用）
- **新增** `Formation.ts`：主角位置 + 朝向 → N 个槽位世界坐标。朝向带角速度限速（`turnRate`）
  与静止死区（`turnDeadzone`），防掉头瞬转抽帧、防静止抖动。几何已离线数值验证：
  左右对称、掉头 0.40s、静止不漂移、稳态落后 20.7px。
- **新增** `HeroSquad.ts`（替代 `PetSquad`）：槽位弹性跟随 + 原 CR-009 三段施法状态机原样保留。
- **新增** `EncounterManager.ts`（替代 `MonsterNest`）：4 窝 × 10 只，**清完永久 cleared 不重刷**，
  提供 `clearedCount` / `allCleared` / `lastCleared`。
- **新增** `BossController.ts`：`dormant→chase→aoeWindup→aoeStrike→recover` 状态机，
  AOE 半径 155 / 读条 1.2s，读条时**站定不动**（停顿本身就是可读信号），贴身推挤 88px。
- **改** `BattleDirector`：阶段 `battle→boss→settlement`，结束原因 `victory/hp0/withdraw`，

- **改** `GameBootstrap`：实体改挂固定容器 `Actors`（敌人节点是对象池懒创建，
  直接挂 field 会排到 EntityRenderer 之后 → 特效全被贴图盖住）；`E` 撤离保留。

### 修掉 3 个会直接导致"跑不通"的 bug
1. **BOSS 阶段英雄永不开火**：`BossController` 不在 `EnemyManager` 里，而 `HeroSquad` 索敌只有
   `_enemies.getNearest()` → 620HP 一点不掉，永远通不了关。修法：`HeroSquad.boss` 迟到接线 +
   索敌在「最近杂兵 / BOSS」取更近者；`Enemy` 与 `Boss` 都满足 `CastTarget{x,y,active,dying}`。
2. **BOSS 死亡动画被跳过**：渲染判据用 `alive`（= active && dying<=0），死亡瞬间变 false →
   0.8s 缩小消失整段没播，BOSS 凭空消失。改用 `boss.boss.active`。HUD 血条仍用 `alive`。
3. **近战前摇只有轮廓**：玩家读不出"还剩多久"，走位变成猜。补内填充圆（半径 = attackRange × 进度，
   alpha 42 防止混战糊屏）。

## 战斗深度方向分析（新增 docs/战斗方向分析_PAWPACK.md）

用户问「哪个方向更好点」→ 做了量化分析，不靠感觉。

### 关键实测（都从 BattleConfig 实际值算，非估计）
- 队伍 DPS = 3×10/0.65 = **46.15**
- 单窝 10 只 × 平均 24HP = 240HP → **每窝只打 5.2 秒**
- 全场 1580HP（含 BOSS 620）纯开火 34.2s + 窝间路程 4253px/190 移速 22.4s → **一局约 57 秒**
- 英雄**无 HP 字段**（敌人只打 `_player`）、3 只**共用 pet.png**、经验珠只累加计数、powerMul 恒为 1

### 三条硬约束（这才是关键结论）
1. **几何上站位无效**：队形纵深 52px **< 敌人近战攻击半径 60px** → 前排后排都在同一攻击圈内。
   要成立需纵深 ≥120px（60+15+12 加余量），但摊开后 960 屏里 4 单位会从"小队"变"散珠"，
   与列队观感互斥 —— 这两个决策不能同时要。
2. **时间上无处展开**：一窝 5.2 秒，仇恨需 3-5s 稳定、治疗周期 8-12s → 系统会变后台逻辑。
3. **横向间距 48px < 精灵宽 64px** → 三只英雄现在**互相重叠 16px**（实机观感待验）。

### 结论排序（投入产出比）
① 表现层 P0（顿帧/爆散/飘字/震屏，~200 行 0 美术）
② **行为差异化**（3 英雄索敌规则不同：最近 / 最高血 / 最低血，~60-90 行）← 推荐
③ 单个手动团队技能（空格 12s CD，~80 行）
④ 职业定位（~270 行 + 不可估时平衡）← **推迟到 M1**，等一局拉长 + 队形摊开
✗ 局内成长 ← 不做，会把品类拉回幸存者like（正是 CR-014 刚纠掉的）

核心论点：**"让玩家看到分工"比"让玩家管理分工"便宜 5 倍且更有效** ——
行为差异每颗子弹都在体现，站位在 5.2 秒一窝里根本来不及被学会。

## 画风问题：Q版卡通 vs 像素（成本与产出能力）

### 先纠自己一个错
我一开始说"32px 画不出可爱"是错的。工程里那张 `pet.png`（粉猪，32×32、10 色、正面视角）
证明 32px 完全能做出大耳朵圆脸的可爱感。像素的上限不在"可爱"，在**可表现维度**：
只能靠剪影 + 比例 + 色板，表情/细节几乎为零。

### 做了对照实验 `client/tools/style_compare.py`
同一只猪（从 pet.png 反推比例，共用一套 SHAPES 定义），三种栅格化方式：
- PIXEL：直接读工程真实资产（不是我另外画的，否则对比被我的手活拉低）
- CHUNKY：48 网格、2 格粗描边、眼睛带 1 格高光
- Q-VECTOR：640 超采样矢量 + 软光 + 双高光
输出 `art-source/style-compare.png`（4x 放大 + 1x 实际尺寸两行）。

**结论：1x（64px）下 Q-VECTOR 的可辨识度和可爱度明显高于像素版。**
像素版 1x 时只剩一个能认出是猪的小点，可爱度靠玩家脑补。
但 Q-VECTOR 放大看露馅（描边糊、有紫边）——这是程序化矢量的真实手活水平。

### 硬约束：显示尺寸天花板（这条比风格之争更重要）
960×540 视野下：
- 64px → 32 只占屏 25%，理论上限 126 只 ✅
- 96px → 占屏 57%，上限 56 只 ⚠️
- 128px → 占屏 101%，上限 31 只 ❌ 放不下

所以**精细 Q 版在这个游戏里是白费**：单只超过 ~80px，同屏 32 只就挤爆。
Q 版要可行，必须是"大眼圆身"的简化造型（Cat Quest 路线），不是带毛发/服饰细节的厚涂。

### 成本结构（不是"谁便宜"，是"贵在哪"）
像素：单价低、数量高（每方向每动作都要单画，改剪影要重画）
Q版/骨骼：单价高、数量低（绑定是一次性投入，加动作便宜；但造型复杂度**没有上限**，这是它容易失控的根因）
分水岭在**第 3 个角色之后**：像素每加一个都要重画，骨骼可复用绑定结构。

### 关键判断：画风是唯一可以延迟的决策
换画风**不改代码**——实体是每节点一个 Sprite、靠同图集合批（`EntityRenderer` 只补画
前摇圈/血条/BOSS AOE），换图 + 调 displaySize 即可。
所以现在不该定，等一局循环验证完之后再定，晚定不增加成本。
唯一需要提前留意的是：若走 Q 版且用 Spine，合批比 Sprite 脆弱，多实例容易涨 DrawCall。

### 我在两种风格上的产出能力是不对称的（要如实说）
- 像素：能直接产出可用资产（已有 4 张 + `pixelart_gen.py` 可复现），能保证色数/无抗锯齿/整数倍
- Q版：只能做到"程序化矢量简化级"（就是对照图里那张），真正的厚涂/类手绘必须引入美术

## 浏览器可玩原型（`client/prototype/index.html`）

### 为什么做这个
交付形态一直是"源码 + 组装说明"，代价是**玩法从未被真正试玩过** ——
所有数值/手感判断都卡在"需要实机"。做一个双击即开的单文件 HTML 是唯一解。

单文件 59KB，4 张像素图 base64 内嵌（合计仅 2KB），零依赖。
Canvas 2D 重写全部系统，数值从 BattleConfig.ts 抄，两版共用同一套参数。

### 移植时踩的坑（都会导致"跑不起来"级故障）
1. **`slotTarget` 是独立函数，不是 `formation` 的方法** → 启动白屏。
   Cocos 版里它是 `Formation` 类的方法，改成普通对象后忘改了。
2. **必须用固定 1/60 步长**。弹簧跟随 `v += (target-x)*stiffness*dt`，
   stiffness=220 时 dt 从 0.0167 变到 0.05，增益就从 3.7 跳到 11 → 队形抖飞。
   dt clamp 只防"切标签页回来瞬移"，防不了不稳定。
3. **世界 y 向上、Canvas y 向下**。不用 `scale(1,-1)` 整体翻转（会把文字也翻过来），
   而是手写 `SX(x)=W/2+(x-cam.x)` / `SY(y)=H/2-(y-cam.y)` 逐个换算。

### 测试体系（`tools/proto-smoke.js`，39/39）
记录型 Canvas/DOM 桩 + vm 沙箱跑真实代码。**必须分三类且隔离**，否则互相污染：
- A 系统隔离（无敌）：验喂食/档位/升级逻辑
- B 完整流程（无敌 + 自动选卡）：验 20 波 → BOSS → 结算
- C 难度观察（自动走位、不无敌）：**只输出数据，不设断言**（难度是人的判断）

**上一版的教训**：把 A/B 混着跑，玩家站着不动 30 秒被打死，phase 变 settlement，
`step()` 直接短路，于是"喂食没生效""升级没弹"全是假警报，白查了一轮。
**测试里任何"系统没反应"，先看 phase 是不是已经结束了。**

**测试桩自己的坑**：`Image` 桩在 node 全局作用域定义，闭包作用域不是 vm 沙箱，
里面调 `setTimeout` 会解析到 node 的真实异步版本，沙箱里的桩不生效 → onload 永不触发。
改成同步调 `_onload()`。
**另一个**：只调 `_step()` 不调 `_frame()` 时 render 不执行，drawImage 统计恒为 0（误报"渲染断了"）。

### 实测数据
一局 166 秒 / 20 波 / Lv9 / 303 杀 / victory / 每帧 40.7 次 drawImage。

### 它抓出的真 bug（已修）
1. 饱食度 0.5/秒 **在一局里几乎不衰减**：166 秒只掉 83 点，满饱最多掉到 17，

   ⚠️ 这是"模拟验算没抓到、真跑才抓到"的典型：sim_wave_balance.py 按 331 秒算的，
   实际只有 166 秒（无敌模式 DPS 拉满，3 英雄贴脸输出）。
2. `orbs/enemies/projectiles` 每帧 `filter` 重建数组 → GC 压力 + 外部引用脱钩。
   改 `const` + 原地压缩 `compact(arr, keep)`。

### 待实测确认
- **166 秒偏短**（20 波设计意图 8 分钟）。要拉长加波数（20→30）或加大 spawnRadius，
  **不要加怪物血量**（只是从"打得动"变"磨"）
- **自动走位玩家 12.6 秒就死**：但我的自动走位是原地绕小圈，等于站着挨打。
  真实玩家直线跑应该能活。这条数据不能当"太难"的证据，但暴露了
  6 点血 + 无逃生手段 = 容错极低的真实风险

## 我方攻击技能化（CR-017）：取消"全队发同一种子弹"

### 用户诉求原话
「我方的几个单位不能有技能攻击工作吗 发子弹感觉不太好」

### 诊断：问题不在子弹形态，在**同质化 + 打空**
三个英雄共用 `HERO.damage/telegraph/cast/recovery` → 三个**完全相同**的炮台排成队。
更硬的一条：三英雄同周期（0.65s）齐射，打死一只 20HP 的怪只需 2 发，**第 3 发飞出去时
目标已被队友打死** —— 命中率只有三成。所以"廉价感"有一半来自"打出去的伤害经常没意义"。

### 方案：三个槽位三种空间关系（不看数值就能分清分工）
| 槽位 | 技能 | 判定 | 周期 |
|---|---|---|---|
| 左后 | 贯穿 beam | 线段扫掠、穿透 4 | 0.72s |
| 右后 | 落雷 bolt | 目标点 0.32s 预警 → 半径 54 圆爆 | 1.05s |
| 正后 | 冲击 nova | 脚下半径 96 圆爆 + 击退 | 0.62s |

周期刻意不同 → 施法天然错落，不再"三发同时出膛"。

### 新增/改动
- `battle/AbilitySystem.ts`（判定 + 表现数据，含 union 三型）
- `EnemyManager.damageInRadius / damageInSegment`（线段用"点到线段距离"，不做逐帧扫掠）
- `BossController.tryHitSegment`（不接这条，槽位 0 在 BOSS 战里等于挂机）
- `EntityRenderer.drawAbilities`（同一 Graphics，**+0 DrawCall**）
- `castCycle(stats, kind)` 按技能取；`HERO_ABILITY` → `ABILITY`

### 两个"抬手但什么都没打到"的坑（必须按技能收窄索敌半径）
1. **冲击波**半径 96，沿用 `acquireRange` 340 → 正后那只对着 300px 外的怪放一圈空气。
2. **贯穿**射程 320 < 340 → 目标落在 325 处必空。
解法：`_rangeOf(h)` 按 kind 收窄（nova → r+40；beam → range×rangeMul−10）。

### ⚠️ 我判断错了一次（记下来避免重犯）
技能化后一局 **166 秒 → 88.7 秒**。我归因于"AOE 打多目标清屏"，加 `AOE_FALLOFF=0.6`，
结果只回到 **90.6 秒（+2%，噪声级）**。真因是**命中率从三成拉到十成**（技能瞬发必中）。
递减保留，但它防的是"贴脸清屏"这个极值场景（被围时 6 个目标挤在 96px 内），不是时长。
**教训：改动后的时长变化，先怀疑"命中率/覆盖率"，再怀疑"伤害数值"。**

### 实测（`node tools/proto-smoke.js`，49 条断言，连跑 5 次全绿）
一局 **87~128 秒**（中位约 100）；Lv8~9；303 杀；每帧 drawImage **40.7 → 29.0**（我方无子弹了）。
波动大是因为升级随机三选一 —— **别拿单次当结论，看中位值**。

### 一个刻意的设计，容易被误判成 bug
**正后那只只在贴身时出手**（索敌半径收窄到 136）。拉开距离它站着不动 = 守卫该有的行为。
觉得"它老不动"就把 `ABILITY.nova.radius` 提到 130。

### 测试新增（技能判定组，类型检查完全抓不到）
穿透多目标 / 穿透上限 / 群体递减 / 落雷**预警期间不结算** / 落雷到点真炸 /
冲击只打半径内 / 我方零投射物 / 实例过期回收 / 光束四边形非退化（NaN 与零面积时
浏览器**静默不画**，不报错）。
**vm 跨沙箱的坑**：`assert.deepStrictEqual` 比较两边的 Array 会因原型不同而误报，
改成 `join(',')` 比字符串。

## CR-018 · 攻击方式重制 + 卡通化（原型已落地，Cocos 版未同步）

**判断**：CR-017 把子弹换成贯穿/落雷/冲击波，判定上没投射物了，但用户仍说「常规」——

（英雄放技能 → 宠物用身体干一件事）。

**三招（按「怪怎么死」分，不按「打多远」分）**
| 槽位 | 技能 | 机制 | 怪怎么死 |
|---|---|---|---|
| 左后 | 悠悠球 `yarn` | 毛线球甩出→顿 0.07s→自己滚回来；去程 1.0 伤/4 目标，回程 0.7 伤 + 击退×7 把怪**往猫这边拽** | 被拽回来 |

| 正后 | 踩奶扑击 `pounce` | 跃起→一屁股坐在怪头上→压扁 + 落地圈 74；**有位移**（leapRange 270 / 滞空 0.40s） | 被压扁 |

**卡通化六个杠杆（全部代码层，一张图没换）**
1. **粗描边**：离线把精灵染纯色剪影 → 沿 12 方向偏移铺一圈 → 盖原图 → 合成一张贴图。

2. **Squash & Stretch**：`sq>0` 压扁 / `sq<0` 拉长。蓄力蹲下(+0.18)、出手弹起(-0.20)、
   落地压扁(+0.30)、受击被拍扁(0.32×hitPunch)、跳跃上升-0.24→下落+0.30
3. 圆润形状（粒子方块→圆点；落地印记用**椭圆**，椭圆才读得出"被砸过"）
4. 糖果色板（草地 #3d6440 → #7FD07A）+ 统一深紫描边色 #3B2A46（纯黑显脏）
5. 拟声词（击杀 45% 概率飘 啪/啵/咚/喵；100% 会糊屏）
6. 旋转（甩尾时猫本体真转 2.5 圈 + 球自转）

**踩到的坑**
- **悠悠球逐帧扫掠不记「已命中」→ 球在怪身边连打四五帧**，一球打掉满血 walker(20血/单发10伤)。

## CR-020 · 森林觅食 + ATB 即时回合制（当前主线方向）

**触发**：用户「不行 你没理解我的意思 那就主线玩法是野外觅食吧 一次可以安排多个宠物上阵
去森林觅食 主要是即时回合制的 战斗场景在森林中」。

**方向纠错**：CR-019 做的是「守家」（怪从门里进来，你排指令挡），用户要的是「出门」。
这不只是换场景 —— 守家是**负数游戏**（不输就是赢），觅食是**正数游戏**（赢多赢少）。
后者才有"再走一层"的冲动。CR-019 的 `tactics.html` 保留但不再是主线。

**结构**：编队(1~5 只) → 森林 5 层 → 每层一波 ATB 战斗 → 选「继续深入 / 就地开饭 / 撤退回家」→ 结算。

**ATB 三参数**：`ATB.full=100`、宠物 `spd 20~30`（猫 3.3s/次、狗 5s/次 → **编队=行动节奏**）、
`ATB.slow=0.16`（待选时全场减速）。**慢放而不是暂停**是关键：暂停=纯回合制，不减速=来不及选，
16% 的妙处是敌人还在打你，"慢慢想"有代价。另加 6 秒兜底自动出手防挂机。

**食物一个资源干两件事**（设计支点）：
| 用途 | 代价 |
|---|---|
| 出征前喂食 | 1 份/只，+25% 攻 +15% 速 +4 血 |
| 战斗中被乌鸦偷 | — |
| 层间就地开饭 | 3 份，全队回 50%，**一层一次** |
| 结算计入家底 | — |
想走到底就得路上吃，但吃掉的不算分数 —— 深入vs落袋才成为真实取舍。

**五个宠物**（编队上限 5 = 池子 5，"选谁"实际是"放弃谁"）：
橘子(猫,26血/速30,挠14/弓背) 豆豆(狗,40/20,撞11+打空条/汪汪) 团子(仓鼠,20/25,塞嘴8/钻地)
布丁(兔,24/26,踢9+定身/蹭蹭回12) 麻薯(鸭,28/22,扑翅群伤6/嘎嘎全队+35条)

**三种敌人各有必须应对的理由**（这是让"目标选择"有意义的关键）：
乌鸦 thief 偷食物不打人；**浣熊 bruiser 在场时其他敌人减伤 30%**（后加，原版所有敌人只会掉血，
最优解永远是打最脆的，目标选择等于没有选择）；野猪 brute 只打最靠前的。

**四个静默 bug（都不报错）**
1. **伤害被平方（最严重）**：`dmg = rawDmg × actor.atk`，而敌人调用传的 rawDmg 就是 `e.atk`
   → 乌鸦 atk6 实际打 36，14 秒团灭整队。根因是 `atk` 一个字段承担两种语义（宠物倍率0.9~1.0 / 敌人基础伤害6~13）。
   修：拆成 `dmgMul`（倍率）+ `atk`（基础值）。**教训：一个字段两种语义，迟早在某个调用点乘两次。**
2. **治疗是负收益**：兔子回7血放弃9点伤害，战斗拖长一轮=敌人多打一次。
   实测「会治疗」20% 通关、「无脑只输出」90% 通关——完全反了。回血 7→12 才救回来。
   **判据：1 次治疗 ≈ 1.5 次普攻的等价血量，不能凭感觉给"看起来合理"的数。**
3. **护盾漏 1 血**：`Math.max(1,...)` 保底排在护盾吸收之前，999 护盾也每次漏 1。
   修：顺序排成 会心 → 减伤 → 护盾 → 保底。
4. **资源就绪判定靠计数器**：`if(--assetsLeft===0)` 只在 onload 保证异步时成立；
   同步就绪时第一张图就误判"全部到齐"，`bake(undefined)` 崩。改成按"实际到齐数量"判定。
5. 空目标 `say()` 读 `u.x` → 守卫要放在单一入口 `petAct`，不要每个技能各写一遍。

**自动回血是错的**：第一版给"每场胜 +35% 血"，实测前 3 层满血、第 4 层断崖全灭。
它把资源决策从玩家手里拿走了 → 改成手动开饭。

**实测**（`node tools/forest-balance.js`，40 局/格）
| 配置 | 通关 | 团灭 |
|---|---|---|
| 无脑 5 只 | 10% | 90% |
| 聪明 5 只 | 35% | 65% |
| 聪明 5 只 + 喂食 | 85% | 15% |
| 聪明 4 只 | 20% | 73% |
| 聪明 3 只 | 0% | 98% |
| 单猫单刷 | 0% | 100% |
| 无治疗队 4 只 | 0% | 98% |
人数 / 会不会用技能 / 喂不喂，三项都影响结果，没有万能解。
单场战斗（深度1，3只队）中位 14.9s / 9 次出手。`forest-smoke.js` 113/113。

**文件**：`client/prototype/forest.html`（~2000 行）、`client/tools/forest-smoke.js`（113 断言）、
`forest-balance.js`、`docs/CR-020_森林觅食与即时回合制.md`、`client/README.md` §零改成三原型并存。
`tactics.html`（CR-019 守家版）保留留档，抗命机制待回捞（见文档 §6）。

## CR-021 · 格子阵型 + 全自动战斗（forest.html 大改）

**触发**：用户三条反馈一次给出 ——「界面布局横版都重叠了」「界面也太low」「搞个格子 占位格子里面 战斗时全自动施法的」。

**判断**：第三条不只是界面，是设计层的。一只一只手动点技能，5 只宠物就是 5 倍点击量；
而"摆阵型"已经提供足够决策量。全自动之后玩家从**操作员 → 教练**。

**格子（解决重叠）**
- 旧实现 `x = 250 + col*62 - row*8`，`row = i % 3` → 第 4 只回到第 0 行只错开 62px，必压

- 卡片上显示"当前会放什么技能"—— 全自动后玩家看不到操作，这张卡是唯一的信息窗口

**界面重做**（不是换色，是重排信息层级）

- 底部队列 172×100：头像 + 名字 + 技能名 + 血条(带数值) + 20px 行动条(带百分比)
- **删掉技能面板**，换战斗日志（两侧阵型之间的空档，最近 3 条，越旧越淡）

## CR-022 · 向《雪人兄弟》借关卡机制（17:40，纯设计，未改代码）

用户提出「融合雪人兄弟做玩法微创新 / 想雪人英雄这类关卡元素」。**本轮只出调研与方案，
一行代码没动**，等拍板。产出 `docs/CR-022_雪人兄弟融合_机制调研与关卡元素.md`。

**机制事实（多来源交叉确认）**：Snow Bros（Toaplan 1990）核心是「喷→裹→推→连锁」四拍。
被裹住的敌人**打不死、只能推**，球放着会化开敌人复活 → 形成「每裹一只就欠一笔债」的节奏压力。
球滚撞敌人会变大。单屏固定场景、只能上跳、约 90 秒超时出无敌南瓜怪。

**最重要的一条洞察**：它好玩的根子不是"雪"，是**把「输出」和「决策」拆给两个不同按键**——
喷（无脑高频、不需瞄准）+ 推（一次定生死）。所以门槛低、上限高、失败便宜。
这条比任何具体元素都值得抄。

**诊断出更要紧的问题**：`forest.html` 3051 行写着「全自动战斗里没有按键操作」，
而立项 §1.3 写「玩家只走位」、系统 A 写「老实牛不能移动靠玩家走位带它」、
系统 C 写「玩家被击中→宠物护主」。**CR-021 把玩家踢出了战场**，导致
① 战斗 15 秒玩家 0 次输入；②「半饿最强」失去临场载体（只剩开打前调滑块）。
用户提雪人兄弟，我判断真实诉求是**把操作权拿回来**，不是想要雪。

**方案：打包搬运五拍**（原版四拍 + 第五拍「收」）
宠物自动「打包」成货球（贴立项"多宠自动施法"）→ 玩家走位「推」（贴立项"只走位"，**不加新按键**）
→ 球分两个去向：推出撞敌人（连锁变大）/ 推进营地（落袋成收成）。
**每一推都在"清场"和"落袋"之间选边** —— 这是原版没有的取舍，也是微创新落点。

**半饿系统白送一个载体**：满饱=打包慢但球稳；半饿=打包快、球更大但容易中途松开；
全饿=宠物跑去啃球。喂不喂变成战斗中随时要做的决定，后果体现在手感上而非数字上。

**红线校验**：①不违反（单屏空地是"地点里的区"不是"第N关"）；②不违反（被撞=掉手里的球，
超时=收工钟声，宠物倒地=饿晕喂食即回）；③完全符合（单屏固定正是原版结构）。
**唯一必须砍的是「超时出无敌南瓜怪追杀」**，保留则红线②立刻破。

**关卡元素 PAWPACK 化**（10 项，优先级排序）：
P0 树枝(单向平台)/落叶堆(打滑)/枯木桩(可击碎)/泥坑(卡球)，
P1 荆棘/弹菇/野果(红蓝黄绿)，P2 兔子洞，P3 漂木（贵，先不做），限时惩罚=砍掉。
**建议前两天只做 P0 的四样**，已足够造出"这球往哪推"的全部纠结。

**技术取舍（Cocos 侧）**：平台碰撞与球滚动**都自己写 AABB + 速度积分，不用 RigidBody2D**——
雪人兄弟的手感是手调的，刚体会带来不可控弹性/摩擦，滚球还会原地打转贴墙抖。
地形用 1 个 Graphics 画全部，沿用 CR-018 的 DrawCall 纪律（目标<20）。
代价：比现在的格子+Graphics 重，预计 +1200~1600 行。

**没想通的问题（已在文档里承认）**：宠物在平台关卡里怎么表现？
跟玩家跳会挤成一团；固定当炮台最像原版但也最"死"。倾向"布阵炮台+玩家串联"，但未验证。

**三种接入方式待拍板**：A 替换主战斗（最统一、开发量最大、4 版原型作废）/
B 并存为辐条（最贴立项 Hub-and-Spoke、新旧都维护）/ C 只在现有 ATB 里加球（**不推荐**，
回合推进容不下实时物理，会打架）。建议先做 V1 手感验证再定 A 还是 B，因为两者第一天工作量相同。

### CR-022 修订（17:55）：接棒制

用户否掉了「牧羊人」设定：「这个是主线玩法哦 应该不行吧 哪个宠物作为主战单位？一起进入战斗怎么运行呢」。
**他说得对** —— 主线玩法的主角必须是宠物，不能凭空多一个世界里不存在的角色。原方案只够当辐条。

**改为接棒制**：玩家**就是**当前操控的那只宠物，按 1-6 随时换，其余五只跟随 + 自动打包。
没有「主战单位」，没有「主人」。六只都在打，玩家只是「正站在其中一只身上」。
操控的那只倒下 → 自动切下一个，不 game over（守红线②）。

**本轮最强的设计发现**：立项系统 A 的六个规则变体，原本全是战斗数值，现在可以
**全部映射到「推球」这一个动作上** —— 猫推球会偏转拐弯（对应弹射）、兔推得最远（射程）、
牛推不动球但能撞碎木桩（极硬不能移动）、鼠能把球吞进颊囊搬运（3 个食物槽）、
狐推完闪回原位（无伤接力）、猪每推一次自己变大（永久成长）。
**换谁 = 换一种撞球方式** —— 这是 Snow Bros 单角色推球做不到的。
立项「选谁=选玩法」第一次有了实时载体。

**跟随五只不做寻路**：直接朝操控目标 lerp，忽略平台碰撞 + 轻微浮动。省掉整个平台寻路系统
（这类玩法最容易失控的部分）。代价是短暂穿模，对「会蹦会跳的小动物」题材可接受。

**新开的三个待确认**：①换人要不要硬直代价（倾向 0.4s 起身，否则玩家会一直切到最好用的那只）；
②跟随宠物是否可被打（倾向掉到 1 血不死，防止换人保命/拿它当盾）；
③六种球法是否随养成分批解锁（倾向分批，让养成对战斗可见）。

**必须诚实的一点**：接棒制之后，跟 Snow Bros 的关系变弱了 —— 它只有一个雪人，我们有六个。
我们借的是「推」这个动作 + 关卡元素，不是它的单角色结构。

## 18:40 原型落地：`client/prototype/grove.html`

三条微创新（相对原版全新的）：
1. **没有血量，只有三层包裹**：攻击不扣血只糊苔，糊满即变球。屏幕不需要血条，鼓起来的样子就是进度条。
2. **球能装人**：滚球撞到没满层的敌人把它卷进球里，球变大变慢继续滚。「先铺场再引爆」成立。
3. **落地位置决定球值多少**：火坑 ×2 但断连锁 / 泥坑强化 +2 层 / 营地 ×1+1 稳收。**这是最核心的一条。**

**关卡设计的关键发现**：每层必须是**整条平台 + 中间一个 66px 缺口**。
切成碎段（我第一版切了 3 段）会让「推一次清一片」彻底不成立，退化成「每只敌人造一颗球推一次」。
缺口的作用是给球一个掉层出口，形成「往缺口推还是往人推」的取舍。

**木桩的双重作用**：挡弹丸（迫使玩家靠近）+ 只有球能撞碎（迫使玩家造球）→ 把「推球」从可选项变成必经环节。

**踩到的坑（都是静默错误，没有报错）**：
- `coatFoe` 满 3 层总是 `makeBallFrom`，连锁时 4 只变 12 只球 → 加 `intoBall` 参数走 `absorbIntoBall`，
  `burstBall` 改成按 `b.packed.length` 吐，两边严格对称。
- 木桩球碰撞判反（判球顶而非球底）→ 球永远撞不到木桩，改成 `if (b.y <= top + 2) continue;`
- 火坑只判横坐标 → 站在正上方平台也会被烫，要加 `p.y >= pit.y - 6`
- 推球力太小阻尼太大 → 70% 的球半路崩开（造 20 崩 14）。`drag 230→170`、推速 `540→620`、墙反弹 `0.66→0.72`

每一步都是**加统计**而不是加日志：`S.stat = { made, burned, banked, burst }` 一眼看出是「造不出来」还是「推不到位」。

## 18:55 CR-023：雪人式长主线的可行性判断与四层深度设计

用户要求「用雪人这套关卡做趣味性玩法 / 长主线 / 野外关卡推进 / 模拟经营 + 趣味性关卡推进」，
并明确「如果不行就不用同步策划文档」。

**结论：可行**，但不是照搬。发现三个结构性矛盾，必须先修：

1. **立项红线①「不做线性关卡线」 vs 长主线** —— 冲突真实存在。解法：长主线 = **产地节点地图**，不是关号；
   「走到第几关」换成「这张图能走多深」；没有关卡失败，只有收成变少。红线①措辞要改成「不做卡关式线性推进」。
2. **单角色出战 vs 六宠编队 + 系统C关系网** —— 系统C 六条规则里**四条直接失效**（同类相邻/异类相邻/抢食/护主全都要求多宠同场）。
   这是必须让用户知情的硬事实。解法：六只从「编队成员」改成「**解法池**」；关系网降级为「家园关系」。
3. **模拟经营 vs 融合铁律5**（玩法数量与创新度成反比，《桌宠大乱斗》死法）—— 解法：经营**不做第二玩法**，
   只做「**规则修改器**」：家园产出的每样东西只改关卡规则、不加数值。

**四层深度模型**（全部挂在「推球」一个动词上，不加动词）：
- 层1 规则：糊 → 滚 → 推（永不变）
- 层2 地形：12 种元素，每种绑一条决策（火坑×2断连锁 / 泥坑+2层 / 枯木桩只有球能撞碎 / 落叶堆打滑 / 荆棘掉球 / 弹菇弹起 / 兔子洞传送）
- 层3 角色：六角色 × 地形的**解法矩阵**（兔抛物线越木桩 / 牛堵窄口 / 仓鼠穿走廊），没有最强只有最合适
- 层4 经营：6 件道具全是规则修改器（苔藓罐送1层 / 火种让火坑不断连锁 / 厚泥靴防滑）

**长线结构**：4 产地（苔藓林/枯木坡/泥沼/萤火洞）× 3 层深度（浅3屏/中4屏/深5屏）= 12 张图。
单趟 3-5 屏、3-5 分钟，每屏打完可选「继续深入 / 就地收工 / 撤回」。

**关键判断依据（引用了三份已有底稿）**：
- 深度公式「深度 = 简单规则 × 大量相互作用 × 频繁决策」
- 铁律1「把宠物删掉换成枪，游戏还成立吗」→ 本方案不成立（换枪就没有「抛物线越木桩」这层解法）
- 铁律5「一个玩法做到极紧 > 五个玩法都松」
- 「关卡降级设计」文档早已定调：**不做关卡，做出门**

**没动 `立项计划书_PAWPACK_v1.0.md` 正文**（宪法级改动先出草案给用户审），
重规划提案写在 CR-023 §2，列了 14 处要改的章节。

**坦诚指出的两个没底的地方**：
- 六角色平衡做不住的风险（用「地形克制」代替「数值平衡」缓解）
- Cocos 侧 +1200~1600 行成本，不是「改一下」
