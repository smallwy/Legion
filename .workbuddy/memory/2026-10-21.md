## 09:40 平台/斜坡的体积感改造（用户反馈：斜的和横向的不够丝滑、像画上去的、厚度不吻合）

**病灶定位（先用截图看，不靠坐标猜）**：
1. 平台是"一条竖向渐变糊到底"，顶面高光只是一条白带 → 读成"一块有渐变的板"
2. 斜坡整条剖面一个渐变、没有顶面 → 像"一根弯管子"
3. 没有投影、没有 AO → 和背景之间没有空间分离，就是"画上去"
4. **厚度基准不统一**：浮空台用 h+6（18~26 浮动），斜坡用 26，两块接缝处永远差几像素
5. **斜坡按竖直方向量厚度**：45° 时视觉厚度只有平路的 70% —— 这才是"厚度不吻合"的真因
6. **斜坡端点还有 29° 硬拐**（RAMP_EASE=0.62 → 端点导数 0.38）

**改法（全部在 client/prototype/grove.html）**：
- 新增 `PLAT_TOP=7` / `PLAT_TK=33` 常量，浮空台和斜坡共用同一视觉总厚
- 浮空台改成"整块砖"画法：整体竖向渐变 → clip 进圆角内画顶带(6px,白20%)+高光(2px,白42%)+底带(6px,暗28%)+木纹 → **只描一条外轮廓**
  - 上一版试过"顶面单独描一圈"的伪 3D，结果平台中间横着一条黑线，更脏。**Q版2D平台的正解是"一块砖"，不是伪3D。**
- 斜坡厚度改为**垂直于路面**量：`off(x,t) = t·√(1+m²)`，平台水平(垂直=竖直)，斜坡自动放大 1/cosθ
  - 但顶带/底带保持**固定竖直厚度**，不乘 vk —— 否则陡处亮边变粗，又像管子高光
- `RAMP_EASE 0.62 → 0.82`：端点切角 29°→10°，坡从台面"流"下去。**物理和绘制共用 rampProfile，所以画面和手感同时变顺**
- 加两层影子：远影（偏移 15px, alpha .16）+ 贴地 AO（alpha .13）
- 平台两端加**端面暗带 + 3 圈年轮**（原木切口）—— 少了这笔记，两端就是"糖果棒的头"
- 低对比主题提亮：cliff `#9A7E8E→#B496A6`、tower `#6E62A8→#8E80CA`（同色相抬明度，前景必须比背景亮）

**验证**：`grove-smoke.js` 318 项全通过（改缓动动到物理，必须回归）。
`grove-shot.js` 改成按关卡出图（第 6 段拍 0/2/4/7 四关），因为**坡度不同，垂直等厚的效果必须逐关看**。

**踩到的坑**：
- `_start(hero, stage)` 的第一个参数是**角色**不是关卡，写 `_start(7)` 会越界报 `H.w undefined`

## 11:05 斜坡衔接 + 空间设计（用户第二轮反馈）

用户发截图红框标着坡和平台的接缝：「还是像接上去的啊 玩家的视觉上 应该像滑滑梯 是很自然的衔接 你动动脑子 斜坡也太大了」
外加：「空间上的策略需要好好设计 背景图可以一个章节一张 但是里面的空间设计需要丰富」

### 一、斜坡"像接上去的"——三个叠加病灶，根因是数学不是美术

1. **端点导数不为零（根因）**：`RAMP_EASE=0.82` 让坡顶切线残留 10°。
   平台顶面导数 0，两条轮廓切向差 10° = 一道看得见的折角。**改 `RAMP_EASE = 1.0`（纯 smoothstep）**。
   教训：这类"看着不对"的问题，先算端点导数，不要先调颜色和投影。
2. **接缝黑竖线**：绘制顺序「坡先画、平台后画」+ 平台 `rr()+stroke()` 整圈描边，
   那条右边线正好压在坡起点上。新增 `rampMating(x,y)` + `platPath(g,...,flatL,flatR)`，
   **接坡端做直角、不描竖边、不画年轮**；斜坡轮廓**只描上下缘不闭合**，悬空端才封口。
3. **坡度真的大**：峰值斜率 = 1.5·H/W。140px 扛 94px 落差 = 45°，那是跳台。
   按 **W ≥ 2.4H**（压到 32°）重排全部斜坡。深井/双塔放不下 → 直接删坡。

**只跑起来才看得见的坑**：坡末端离右墙必须 > 球半径，否则球贴墙撞回来又滑上坡，
来回震荡 4 秒出不去，滑梯变碗。

### 二、空间设计：先修一个比"不丰富"更严重的问题

统计八关平台宽度，发现 **后三关（本该是高潮）最长台面只有 274/280/140**。
《雪人兄弟》的爽点是"推一次清一片"，碎平台把它切没了。

**定死一条规则：每关必须有一条 ≥400px 的完整球道。**

- 5 弹跳林：三条左对齐横条 → **金字塔 640/534/294**（八关唯一把"高度"当资源的：上层只够造球，最宽底层才是收获层）
- 6 深井：462 左段 274→**394**，同时变成悬臂
- 7 阶梯塔：9 个碎片 → **4 层整梯**（阶梯感来自层间错位 90~130，不来自切碎）
- 8 双塔：274/140 → **314/260**（140 不是塔，是板子）
- 2 泥沼：坡从"藏在台面底下"移到台面外侧

### 三、这一轮抓到的静默错误（全是不报错、只能靠断言发现的）

1. 坡顶到墙太近 → 球贴墙震荡
2. **敌人 y 是照旧坡面手写的** → 坡加长后悬空 20~30px，球从脚底滚过，"连锁 3"作废
3. 水塘被平台压住 → 球砸不到水面（水塘必须同时落在上下两层的缺口里）
4. 阶梯缺口只错开 40px → 竖井剩 40 宽
5. 木桩插穿台底（桩顶 478 vs 台底 495）
6. 水塘和火坑重叠 → 球滚进去直接被烧

### 四、经验

- **改坡度必须同步重算站在坡上的敌人 y**（用 `rampAt(x).y`，不要手写）
- 水塘/火坑这类"地面坑"，位置要同时满足 **350 缺口 ∩ 462 缺口**，否则球砸不下来
- 木桩可以站在平台顶面（`y: 350`），不一定非在地面 —— 金字塔/双塔这种台面压满地面的关，这是唯一的解法

验证：`grove-smoke.js` **324 项全通过**（含机器人八关巡回）；`grove-shot.js` 扩成八关全拍。

## 14:40 CR-028 市场空间深度调研（用户：「当前这样做下去 有没有市场空间」）

**结论：有市场，但不是现在这条路的市场。**

### 四个市场的数据（都查了一手来源）

1. **Steam 全量基线（GameDiscoverCo 2026-01 cohort，1230 款付费新游，跟踪 8 个月）**
   中位销量 **≈100 份** / 毛利 $1,000；33% 零销量；**74.4% < 1,000 份**；8% > 10,000；1.3% > $100 万；前 1% 拿走 72.8% 收入。
   → **立项 §7.3 的「中值 3-9 万份」实际是 top 2~3%，不是中值。这是必须修的基线错误。**

2. **推球品类的天花板（不是单个游戏）**
   - Snow Bros. Wonderland（官方续作，$29.99）：Steam 估销 **1,060 份** / 53 评测 / 81% 好评
   - Donut Dodo（2022，96% 好评，有 Switch 实体 + N64 众筹）：**6,900 份 / $31.7K**
   - Nightmare in the Dark（2000 Neo Geo 直接克隆）：「never really caught on enough to receive any modern updates」
   → **机制本身的商业价值 ≈ 0。它是加分项，从来不是购买理由。**

3. **宠物 + 家园这层壳已被验证到千万级**
   咩咩启示录 370 万~780 万份 / Steam 毛利 $93M / **成本 $2-3M、20 人、2.5 年**，且**差评 25% 骂战斗 + 25% 骂刷**；
   帕鲁 2,500 万份；星露谷 4,100 万份；Cat Cafe Manager 9.1 万份。
   反面：Miners Moos 仅 5 条评测、Nom Nom 2,090 份 / 好评 93.75% → **好评率与销量完全脱节，结构对了 ≠ 有人买**。

4. **微信小游戏（最大盘子，但错配）**
   月活 **6.52 亿**（+21.2%）、大盘 **300-400 亿**、80 款百万 DAU、300+ 款季度流水超千万、开发者 50 万+ 其中 80% 是 <30 人团队、IAA 4 亿用户 70% 只玩 IAA、1400+ 款广告变现超百万、IAP 首发 5000 万不分成。
   **但** IAA 场景是「等车排队 / 3 秒懂 / 单局 30 秒 / 随时中断」，爆款是消除·俄罗斯方块·拧螺丝；
   推球是「连续 3-5 分钟 / 每 3 秒一次落点决策」。**硬错配，不是调优问题。**

### 三个结构性错配（这是本文最有价值的部分）

1. **卖点层与投入层完全错位**：手感层（斜坡 32°、垂直等厚、轮廓不封口、冰壳、球撞球）市场价值 ≈0，占了 ~95% 精力；
   宠物性格/关系/记忆 + 家园 + 商店页 = 市场真正付钱的东西，**0%**。
2. **内容量与定价错位**：8 关≈25 分钟，撑不起 $14.99（需 60-80 屏）。Donut Dodo 拿 96% 的好评真因是「$9.99 + 1 小时」匹配。
3. **一人 + 双循环**：咩咩 20 人仍被两头骂，我们 1 人做两个循环 = 各 1/20 深度。

### 三条路线（写进文档，等用户选）

- A `$9.99` 复古街机：中位 5,000-15,000 份 / $25K-80K，**现有代码 3-4 周可收尾**
- B 咩咩式小体量：中位 10,000-40,000 份，但要 20 周+
- C **推球解谜**（最被忽略）：5,000-20,000 份、好评易 95%+，但要 80-120 道唯一解关卡

### 关键洞察：IP 认知是分裂的

「雪人兄弟」在**中国/日本街机红白机世代**是资产，在 **Steam 新品页是负债**——受众不在场。
所以三条路的共同点都是：**都不靠"雪人兄弟"四个字**。

### 市场侧三条硬建议

1. **立刻做商店页，跑 A/B**（A：猫喷毛球 / B：六只挤在门口一只被拎走）。成本 2 天，收益是省 3 个月错误投入。
2. **内容量与定价必须对齐**（中间地带最危险：25 分钟 + $14.99 = 差评 = 算法不给流量 = 死亡螺旋）。
3. **宠物需要一个可传播瞬间**：咩咩是「羊拉屎要自己铲」、帕鲁是「给帕鲁发枪」，我们 0 个。
   最小方案：出门前未被选中的五只做不同反应（生气/装可怜/偷偷跟到门口）—— 这就是 GIF 第二帧。

### 方法教训

- 用户问「有没有市场空间」时，不要回答"有希望"。**先找这一品类的"最好成绩"，那就是天花板；再找 IP 正统续作的成绩，那验证受众在不在场。**

> 一句话：**家园是容器，性格是内容。空容器不产生价值，内容自己就能传播。**

### 三、内容量不堆屏数（B 相对 A 唯一的结构性优势）

3 小时需要 60-80 屏（按 38s/屏机器人数据），24 屏只有 1 小时出头。

→ 24 屏 × 2.5 趟 ≈ 60 屏次 ≈ 2 小时，加家园重试 = 3 小时。
> 反过来说：**如果六只在同一屏里只是"打得快慢不同"，这个杠杆就不存在**，B 退化成贵一倍的 A。

## 第三轮：正式 UI 概念图 + 宠物立绘重做

### 十四、核心判断：UI 概念图必须代码画，不能用 AI

- AI 出图的中文必然糊，而 UI 概念图的全部价值就是"字怎么写、按钮多宽、几号字"
- 代码精绘有确定坐标，可直接抄进 Cocos；AI 只能"看着差不多"
- 矢量资产不算 AI 生成 → 规避 Steam 的 AI 披露标签（销量均值约 1/3）

产出 `client/concept/concept-shot.js`（@napi-rs/canvas 离屏渲染，和 grove-shot.js 同一套路）。

### 十五、设计语言「糖果纸」

参考取舍：蛋仔派对抄厚底按钮、卡比抄粉彩+深描边、动森抄奶油纸面板、Ooblets 抄高饱和；
**一律不抄**：满屏红点/活动入口（买断单机、会被判手游味）、3D 体积、无描边。

三条铁律：一切 4px 深描边（贴纸感来源）、投影必须硬投影（模糊阴影=写实信号）、按钮必须有厚度。
**只有天空允许渐变**，其余全平涂。

### 十六、立绘的难点不是画得好，是剪影能分开

旧 drawPet 六只只有"换主色+换耳朵"，涂黑后是同一个雪人。加了 **体型表 BUILD{bw,bh,hd}**：
兔 0.46/0.50 最瘦高、仓鼠 0.72/0.52 最宽矮、牛 hd 0.47 头最大。
写了 `silhouette()` 读像素染色做客观检验 —— 肉眼看永远觉得"挺不一样"，涂黑一排才知道分不开。

第一版翻车点：只换配件不改体型 → 剪影里仓鼠和犬一模一样。

### 十七、战斗 HUD 的问题是"信息平铺"不是"不好看"

原 HUD 头像/名字/血量全塞一个深色块，字号 10-11px，谁都不比谁重要。
重排三级：一级（血量/肚子/目标，奶油纸实体卡）、二级（关卡/道具，半透明或小卡）、三级（提示，无底低对比）。
判定标准：缩到 480px 宽还能一眼读出的就是一级。

### 十八、顺手发现的文档债

**《美术风格指引_PAWPACK.md》§1 写的是"像素 16-32px、整数倍、≤24 色、Point 过滤"，
但实现早在画斜坡时转成矢量 Q 版了。** 已在指引顶部加版本说明，标注作废章节 + 指向新文档。

这类"文档停在旧方案、代码已经走远"的债，比单个 bug 危险 —— 按旧指引验收会推倒重来。

### 十九、截图迭代踩的坑

## v2 重做：四条批评 → 三处系统性纠错（2026-10-21 下午）

用户对 v1 四张概念图的四条批评：
1. 整体风格要 Q 版可爱风
2. 主界面太简易 ——「不是有个宠物家园的感觉吗 应该有一个玩法或者养成才对」
3. 六只宠物同质化 ——「没有那种极致想得到的感觉」
4. 战斗内 UI 太简易 + 「不同关卡差异性的空间设计 也需要的」

### 二十、前三条不是细节问题，是三个系统性错误的叠加

**必须同时改，只改一个会被另外两个抵消。** 这条方法论比任何一张图都值钱。

| # | 错在哪 | v1 | v2 |
|---|---|---|---|
| 1 | 明度 | 黄昏紫 `#3A3560→#B87F9A` | 白天粉蓝 `#7FCDEF→#E9FAFF` + 奶油黄草地 |
| 2 | 比例 | 头径占身高 0.44，眼占脸 1/6 | 头占 0.52–0.60，眼占脸宽 1/3 |
| 3 | 描边 | 统一冷紫近黑 `#3A2B44` | 每只用自身主色的深暖调 |

- 低明度 + 冷紫 = **情绪/抒情**语言（独立游戏海报那一套）。**可爱风第一条是高明度（L>80%），第二条是暖。**
- 头径 0.44 读作"Q 版小人"；眼占 1/6 时六只全是"有五官的团子"而不是角色。
- 冷色近黑描边压在粉彩上会让画面"变硬"——那是绘本感不是可爱感。描边要**融进角色**。

**由此立一条全局纪律**：高明度 + 暖是基调，黄昏/夜色只能做单关氛围，不能做全局。

### 二十一、"同质化"和"极致想得到"是两件事，要两套解法

- **同质化**：不是配件不够多，是三个都没做 —— ①体型拉到 `bw 0.50–0.90`（原挤在 0.46–0.72）②加**材质层**（毛尖/卷尾/颊袋+门牙/折耳/月牙角+斑块/巨尾+星尘）③脸形不共用圆（新增 `headPath(g,cx,cy,rx,ry,chin)`，狐 chin 0.56 倒三角、仓鼠 0.00 方脸）
- **「极致想得到」靠稀缺，不能靠"每只都好看"**——六只平均 = 六只都不想要。做明确梯度 ★普通×2 / ★★少见×2 / ★★★稀有 / ★★★★传说（星屑：最瘦 + 下巴最尖 + 尾巴比身子还大 + 星尘）

**大眼睛三要素**（缺一件就是死鱼眼）：竖椭圆 rw0.88/rh1.16 + 左大右小双高光 + **下缘淡蓝反光**（最易漏，但是"水汪汪"的真正来源；alpha 别超 .55，用过 .62 整只眼发蓝紫）。

### 二十二、"主界面太简易" = 这是插画不是界面

加装饰救不了。要让玩家 3 秒读出循环，同屏必须有四样：
需求气泡（该做什么）/ 一个正在被互动的瞬间（可以点：摸摸+手指+飘心）/ 今日互动 4/6（短目标）/ 亲密度 3/5（长目标）。

**短目标和长目标必须同时在画面上。** 只有短目标 = 手游日常任务味；只有长目标 = 不知道该干什么。
另加一条：六只**每只状态不同**（睡/吃/跳/追/坐屋顶/看蝴蝶）——状态差异本身就是"这是个活着的家"。

### 二十三、"关卡差异性"不能靠换配色

换配色玩家觉得"还是同一关"。必须换**空间结构 + 专属动词**：
草甸=横向·推 / 深井=纵向·落 / 高塔=阶梯·绕。**同一套 HUD 复用三关**才看得出是同一款游戏。

HUD 仍是三级分层，但「**肚子」升为一级**——它决定"再推一关还是收工回家"，是全游戏最重要的一次决策。

### 二十六、交付前复核又抓出四个"读错级"问题（都是自审，用户还没看）

放大逐张看才发现的 —— 缩略图里全都"看着还行"：

1. **传说位反而最不吸引人**。狐「星屑」的常态画的是两道闭眼弧线（想表达"笑里有话"），
   于是它是六只里**唯一没有眼白**、唯一不遵守"大眼睛三要素"的。→ 常态一律 `bigEye()`，
   弧线笑眼只留给满饱态。**规则不能有例外，尤其不能给主角开例外。**
2. **"尾巴比身子还大"这个传说位的唯一理由被裁掉了**。谱上每格 `clip` 半宽 96px，狐的巨尾甩到 `cx±137`。
   → 狐在谱上镜像（尾巴甩右、右边没邻格）+ 该格 clip 放宽到 280；剪影行也必须同步镜像，
   否则主图和剪影方向相反，读成两只不同的宠物。**规格图不能自己骗自己。**
3. **手指光标贴在年糕头右缘外 9px**，读成"狗竖起一根手指"。→ 移到净距 45px 处。
4. **鱼气泡正压在星屑脸上**（星屑右移后与 (932,404) 重合），读成"右眼贴了块白布"。
   → 气泡跟到头顶。**移动角色时，所有附属 UI 都要一起挪。**

一条通用纪律：**UI 元素（气泡/光标/飘字/角标）与角色轮廓至少留 40px 净距**，
资源之间的"贴边"在缩略图里看不出，放大就是"长在角色身上"。

另一个失败的尝试记一下：家园中景空，我把远山从 58/38 加厚到 104/74，结果成了一个
**"绿色大馒头"**——地平线被抬到 y190、天空压窄，且远山与草地同色，读成"草地隆起"。
远处的丘陵就该矮。**"画面空"不等于"要加东西"，先判断空的是体积还是结构。**

## v2.1：三条新批评（家园不够 / 立体感 / 斜面衔接）

### 二十七、"家园还是不够" = 只有一个出口，没有功能骨架

v2 第一版家园只有一个「出门」按钮，灶台/工作台/图鉴全靠"床和食盆暗示"。
用户要的是「**统筹所有功能 + 未来规划有多少东西**」。

**解法：入口做成场景建筑，不做悬浮图标。** 这个游戏卖的是"过日子"，
入口一旦变成图标就退回成菜单页（动森也是建筑即入口）。建筑头顶挂统一小铜牌 = 识别语言。

落地九个入口（含阶段）：选宠 P0 / 出门 P0 / 灶台喂饭 P0 / 工作台做道具 P1 /
产地路牌 P1（3 产地 + 锁）/ 图鉴 P2 / 背包 P1 / 今日目标 P0 / 设置 P0。

**还有一条容易漏的**：主界面必须回答"今天该做什么"。加了左上「今日目标」卡
（一条主线 + 四条可勾选小目标），否则六只再可爱，玩家打开游戏也不知道第一步干嘛。

### 二十八、"有没有立体感" = 只有一阶颜色

v2 第一版立绘是纯平涂 + 一条描边，缩略图上就是贴纸。

**走过的三条弯路（关键教训）**：
1. 用"偏移的大椭圆"当暗部 → 分界弧线切在脸中间，读成"戴了个面具"/"脸上一道脏痕"
2. 加大对比 → 更脏。**方向错了，加多少都是错**
3. 暗带 24% + 亮带 21% → 中间只剩 55% 主色，整只读成"气球"

**正解是环形带**：裁出「外轮廓 − 内缩同形」那一圈（`clip("evenodd")`），
再用一个方向圆裁掉其余三面，只留右下暗 / 左上亮。暗部永远贴轮廓走，进不到脸中心。

参数：暗带 14% 半径、亮带 5.5%、rim ≈ 描边宽×0.9、额头月牙高光、头身 AO 椭圆。
**脸是特例**：只贴边缘暗带，**不加亮带**（会读成"脸上贴了浅色圆片"）。

### 二十九、"斜的没和横向接好" = 三个接缝 bug 叠加

1. 坡脚起点正好在平台右端圆角**外侧** → 读成"平台被斜着砍了一刀"
2. 坡顶撞平台侧边 → 锐角 V
3. **最刺眼的一处**：所谓"木桥"是水平的，却要连接 y=330 和 y=386 两块台 → **右端悬空 56px**

四条规矩：厚度统一 26 / 坡两端压进平台 30px 靠平台盖毛边 / 接缝画木端面封平 /
连接不同高度必须是斜桥。

**试过但不成立**：① 接缝加铁箍 → 4 个读成"一排糖块"；② 坡上画木纹 → 贝塞尔取点
方向算错会"扎"出坡面，且坡只有 190px，抵不上风险。

### 三十、通用纪律（本轮提炼）

- **规则不能有例外，尤其不能给主角开例外**（传说位狐曾经是六只里唯一没有眼白的）
- **规格图不能自己骗自己**：谱上 clip 把"尾巴比身子还大"这个传说位的唯一理由裁没了
- **UI 元素与角色轮廓至少留 40px 净距**，移动角色时所有附属 UI 一起挪
- **"画面空"不等于"要加东西"**：远山从 58 加到 104 变成"绿色大馒头"，已回退

## v3：「像贴上去的」→ 生产方式的天花板

用户：「感觉达不到吸引玩家的级别 我需要商业化的一个游戏UI界面 你需要立绘画图试下吗 最好有动感 现在就像贴上去的」

### 三十一、这条批评不是参数问题，是生产方式

矢量精绘的天花板就是「精致的扁平插画」。继续调参只会得到「更精致的贴纸」。
**解法是分工：AI 给质感氛围，矢量给精度可维护性，引擎给动感。**

| 层 | 谁做 |
|---|---|
| 背景插画 | AI（景深/体积光/环境光污染） |
| 角色立绘 | AI（透明底单只，动态姿势/副运动） |
| UI 控件 | 矢量（必须切图/换字/四态/多分辨率） |
| 动感 | 引擎（静态图只能暗示） |

### 三十二、「像贴上去的」的六个技术成因（可逐条验证）

1. **只有一个深度层** —— 缺前景层。必须有大尺寸虚化草叶/花瓣压住画面下缘
2. **没有环境光污染** —— 草地上的角色腹部要吃绿色反弹光，天空下顶部吃冷蓝。任何物体都不该只有固有色
3. **光照方向不统一** —— 全场单一主光，所有投影朝右下，**包括 UI 控件**
4. **接触阴影没有分层** —— 三层：贴地的深色硬阴影 + 中层软影 + 大范围方向投影
5. **主体与背景没有分离手段** —— rim light。v2 的 rim alpha 只有 .38，几乎看不见
6. **没有动作** —— 动作线 + 重心偏移 + 副运动 + 地面交互

### 三十三、一个失败换来的最重要规则（坐标不可控）

第一版把「气泡 + 三颗飘心 + 手指」按 AI 图上兔子的位置摆好（估的 x20–115, y185–275）。
渲染出来发现 **兔子实际在 y > 330**（我看缩略图时把 display 坐标当成了原图坐标，差 140px），
只露两只耳朵、身体被底部 HUD 吃掉。气泡落在空草地上，手指悬在路牌旁，
读成一个白色胶囊 —— **比原来的贴纸感更糟**。

**→ AI 出整张场景 = 角色坐标随机 = 所有「贴着角色的 UI」必然落空。**
**→ 角色必须单出（透明底），坐标由脚本按栅格定。**

这条推翻了我原本「AI 出一张完整主界面」的想法。正确图层栈：
L0 背景(AI) → L2 角色(AI 透明底) → L3 角色附属 UI → L4 HUD(矢量) → L5 前景(AI)

### 三十四、动感的实话

概念图是静态的，永远只能「暗示」动。真动感给成引擎参数：
呼吸 2000ms / 六只错开 300ms 相位（同步 = 六个机器）/ 按钮回弹 100ms `back.out(3)` /
飘心 900ms 衰减 / **视差：前景 1.15× · HUD 0× · 角色 1.0× · 背景 0.86×**（横向 ±12px 封顶）。

### 三十五、两条合成试错（写进 concept/README 了）

- 底部雾 148px / `.94` 实心 → 把前景花层压成一片米色，景深白做 → 收 116px / `.80`
- 左上 340×112 今日目标方卡 → 压在小屋屋顶上，边缘和红白条纹交错 → 改顶部横贯信息条

### 三十七、`background:"transparent"` 参数不可用（重要！）

第一次要透明底，ImageGen 把"透明"**画成了灰白棋盘格底纹** —— 直接进引擎就是一块布。
**必须走纯品红 #FF00FF 出图 + 程序键控。** 脚本 `client/concept/chromakey.js`。

四个必须处理的细节：
1. 过渡带 alpha 线性映射（真抗锯齿，硬边缩放后会有狗牙）
2. despill：`spill = max(0, min(r,b) - g) * 0.85`，把边缘残留品红往中性拉
3. **清孤立噪点**（3×3 邻域 alpha>8 邻居 < 2 就清）—— 不清的话 **1 个噪点就能把包围盒从 895×1401 撑成 1024×1536**
4. **统计法裁边**（逐行/逐列计数超过阈值才算边界），不能逐像素找极值

## v4：六只立绘全出齐 + 宠物行为系统（用户拍板「画风还可以，出吧」）

### 四十一、姿态模板才是同质化的真正来源

出年糕第一版，技术完全合格，但一眼看过去**和砂糖是同一只**。原因是
「正面站正 + 一只爪抬起 + 领巾 + 头顶呆毛」—— **这是一个姿态模板**。
六只共用姿态模板 = 六次同一角色的换色。

破法：**画风锁统一，姿态语言不统一**。每只的姿态直接说明它的技能：
砂糖站正举爪 / 年糕坐姿前倾+摇尾 / 团子蹲坐含整颗果 / 雪团腾空蹬展 /
豆奶趴卧半眯 / 星屑站正+巨尾甩出。

**副产品一条硬规矩：六只一律正面取景。** 星屑第一版侧身回望，结果成了六只里
唯一头小眼小的（侧三分之四压缩眼部面积），传说位反而最不吸引人。
侧身还会导致图鉴格/HUD 头像/对话立绘都要另出一套正面图 → 成本翻倍。

### 四十二、品红键控阈值不能写死（第二次踩这个工具）

六只里四只的实际背景是 **rgb(215,50,142) 暗品红**，不是纯 #FF00FF。
固定 LO=24/HI=150 把 score=92 判成"半透明过渡带"，映射 alpha≈0.54 →
整张背景留一层淡紫、包围盒撑满 1024×1536。**表面症状像"AI 加了卡片边框"，
实际是背景没键掉。** 诊断时差点去写"剥边框"的代码，白费功夫。

修法：`sampleBg()` 采样四边中位数 → `LO = score0×0.50 / HI = score0×0.78`，
score0 < 60 直接报错。依据：背景 score0=92 → LO=46，而粉彩的粉色内耳 score≈28 安全。

**教训：看到"整张图有内容"先怀疑阈值，别怀疑构图。**

### 四十三、验收图的三层结构（这个做法以后固定用）

`_roster.png` 三行各回答一个问题：
1. **彩色行**：像不像同一套资产？（画风一致性）—— 统一高度归一化，不统一宽度，
   差异体现在胖瘦上。统一宽度会把六只拉成一样宽的方块，体型梯度全没了。
2. **剪影行**：涂黑还能分清谁是谁？（可辨识性，唯一客观判据）
3. **尺寸行**：缩到 180/120/96/60 还看得清吗？（可用性）

### 四十四、"性格"是同一输入的不同反应，不是长相

用户第 3 条「能自己动、有动效、摸的时候有动作反应」。核心判断：
同一根手指摸下去，六只必须给六种回应。都"轻跳一下冒颗心"= 同一个宠物换皮。

六种反应全部用**程序变换**表达（位移/旋转/缩放/透明度），不用序列帧：
砂糖别扭先愣再歪头 / 年糕头顶上来摇尾×3 / 团子颊袋抖倒向手 /
雪团耳朵弹跳起转半圈 / **豆奶几乎不动**（故意的，差异化包含"更少的动作"）/
星屑星尘炸开。

**三层动画栈**：L1 呼吸（常驻永不打断，2800ms，六只相位错开 300ms）/
L2 自主行为（6–14s 泊松随机）/ L3 响应（点击，覆盖 L2 不打断 L1，
预判 90ms → 反应 320ms → 回落 280ms）。

**连续摸必须递进**：第1次基础 → 第3次主动凑过来 → 第5次翻肚子（唯一稀有反应）
→ 每日 30 次后"困了"。每次都一样 = 第三次就不想摸了。

### 四十五、单帧立绘做不到真走路 —— 这个分叉必须现在决定

腿不动却在平移 = **滑步**，比不动还糟。
① 每只再出 2–4 帧行走（+12–24 张，帧间一致性 AI 只有 70%）
② **蹦跳式移动**（跳跃位移 + squash/stretch + 落地挤压，0 张额外图）← 选了 ②

理由：Q 版里蹦跳比走路更贴（仓鼠滚、兔子跳、猫轻盈跳）；squash/stretch 程序就能做；
省下的预算该花在战斗背景上——那是玩家看得最久的东西。
参数：起跳 80ms ease-out / 腾空 320ms 抛物线最高 dy−38 / 落地 90ms ease-in / 回弹 140ms back.out(2.4)。

### 四十八、深度公式复核 + 查出三个落地缺口

**用户问**：6 只是不是做不深？深度怎么做？目前关卡章节规划多少？

**已拍板的关卡规划（2026-10-20 20:07，别再问）**：
首发 **3 产地 × 8 屏 + 1 BOSS = 24 屏**，每屏 1 主目标 + 2 奖励目标 = **72 关等效**，地形美术只做 24 张。
产地：苔藓林（火坑/泥坑）→ 枯木坡（枯木桩/落叶）→ 泥沼（荆棘/大泥坑）；**萤火洞（弹菇/兔子洞）留免费更新**。
4 产地 × 12 屏 = 48 屏装不下 12 周排期（24~48 人日），这是砍到 3 产地的真实原因。

**立项自己的深度公式**：`深度 = 简单规则 × 大量相互作用 × 频繁决策`
- 简单规则：动词只有 3 个（糊/滚/推）
- 大量相互作用：五条腿（① 球的资源性 ② 落点定价 ③ 地形改弹道 ④ 敌人即素材 ⑤ 宠物规则变体）
- 频繁决策：**每 2~3 秒 1 次**（"这一球往哪推"），是唯一高频层
→ 所以预算必须压在关卡，不是宠物。这也是"单宠"的真理由。

**查出的三个缺口（重要）**：
1. **前 2 产地锁单宠 = 16 屏不能换宠**，与 `宠物+趣味性玩法融合设计手册` §285「解锁了但无法使用 = 制造挫败而非期待」直接冲突。第 1 产地通关拿到团子后，整个第 2 产地（8 屏）都只能看它站着。
   建议：锁 **1 个产地**（8 屏 ≈ 1.5 小时，够教学），第 2 产地起解锁层间换宠。
2. **8~10 小时的内容账对不上**：72 目标 ÷ 480 分钟 = 每目标 6.7 分钟，但一屏只要 45~60 秒 → 需每目标重玩 7~9 次，不现实。
   诚实账：首通 72×50s≈1 小时 / 全 S 级 ≈3 小时 / 六只解法 ≈4.5~6 小时。
   **8 小时的真正来源是"六只 × 24 屏"的组合，不是 72 个目标** —— 6 只的价值不在收集，在让 24 屏值得再打一遍。
3. **地形克制只有一句示例**（"枯木桩图废掉 4 只直射宠，只剩兔子和牛"），24 屏里哪张废哪几只**没有表**。首发 6 种地形元素 × 6 只 = **36 格，一格没填**。

**新给的验收标准**：72 个目标里，**每个目标至少 2 只宠物可达成**。只有 1 只能达成的不是深度是卡关。

### 四十九、内容量核算 + 四条乘法式拓展（产品层建议）

**内容量现状（诚实账）**：24 关 × 30–60 秒 → 单趟 3–5 分钟 → **首通 3 产地约 12–15 分钟**；加失败重打 + 刷材料 + 追 S 级 ≈ **3–5 小时**。
结论：**$9.99 及格，$14.99 不行。**

**核心判断：一人 20 周排期下，靠"加关"解决内容量是死路。** +8 关 = 3.5 周只涨 33%。

**四条乘法方案（按性价比）**：
1. **空间变奏（1 周 → +200%）**：24 关 × 3 变奏 = 72 屏，美术 0 增。**必须改空间不能改目标**（CR-024 §8.6.3 实测换目标不改打法）。三条变奏 = 封一条通路 / 挪营地 / 换 2 个特殊件 / 挪敌人出生点。判据：**三条的最优路线必须不同，否则不算变奏**。
2. **元素随机（1.5 周 → +150%）**：手工骨架 + 特殊件池随机 2–3 个。**随机的是"哪个摆件"，不是"平台在哪"**（骨架手工保好看）。风险是无解关 → 用 `grove-bot.js` 跑 100 个种子，无解的丢弃重掷。
3. **宠物专属路径（0.5 周 → +80% 重打理由）**：每只 1 个"只能它走"的隐藏通路 / 互动点，共 6 处。成本极低，是 CR-029 §284"六只各自找到最合适那张图"的可执行版。
4. **吧唧收集层（1 周 → +40%）**：24 关各 1 个隐藏收成点 = 24 枚吧唧。矢量可画（`kit2.js`），图鉴留空位是催收力。名字天然契合。

**明确不做**：每日/周常（买断制 = 手游味，Steam 直接扣分）、加第 4 个动词/装备词条/天赋树（破红线且做不动）、内购抽卡、无尽模式（会暴露"几何只有 24 种"）。

**定价建议**：$9.99。$14.99 会被批"内容少"。

**战略建议**：**不要用现在的猜测赌 3.5 周去加第 4 产地**，先用 P5 已有的 Demo + Next Fest 拿真实数据再决定（BALL x PIT 就是首发单角色、后续加内容）。

### 关键技术发现（决定了能不能可靠生成）
1. **图片 meta 的子资源 id 是固定值**：texture = `<uuid>@6c48a`，spriteFrame = `<uuid>@f9941`。在 survivors-game 里核对 6 张图全部一致 → 可以放心手写 meta 并让 scene 用 `__uuid__` 引用

### 坐标换算（唯一的公式）
网页左上原点 y 向下 → Cocos Canvas 中心原点 y 向上：
```
cocosX = webX - 640
cocosY = 360 - webY
```
背景 `#bg{top:-40,height:853}` → 中心 386.5 → Cocos y = **-26.5**。
宠物锚点统一 **(0.5, 0) = 脚底中心**，宽度 = h × 原图宽高比（从 `_cocos-assets.json` 读，不目测）。

### 九宫格母版三个硬约束
1. **border > 圆角**（panel 24>22，btn 34>30），反了四角被拉成椭圆

3. **尺寸 ≥ border×2 + 可见拉伸区**（96 = 24+48+24）

## 17:00 Cocos 场景跑通：修掉 5 个「文件合法但引擎不认」的缺陷

用户报「启动报错」，截图显示预览每帧抛 `Cannot read properties of null (reading '_getUITransformComp')`。逐层挖下去其实是 5 个独立的结构缺陷，全部在 `client/tools/make-scene.js`：

1. **`Canvas._parent` 是 null**（真凶）。Scene 的 `_children` 里有 Canvas，但没写回父引用。
   `cc.Widget.align()` 走 `this._target || this.node.parent` → null → `getReadonlyNodeSize(null)`
   → 它第一行 `parent._getUITransformComp()` **没有 null 保护** → 每帧崩。
   原验证器的「父子双向」只遍历 `cc.Node`，跳过 `cc.Scene`，恰好漏掉这一条。
2. **子节点在 `_children` 里重复登记**（BG/FogTop/FogBot 各两次）→ `Open scene failed`。
   原因：`addSprite(iCanvas,…)` 建时就挂了一次，末尾「按渲染顺序统一挂载」的循环又挂一次。
   修法：`attach()` 幂等 + 新增 `setOrder()` 显式定序。
3. **`node()` 写死 `z: 0`**，把相机传入的 `z: 1000` 丢了 → 相机与 UI 同平面，`near=0` 切掉界面。
4. **Canvas 位置用 `TL(0,0)`** 得到 `(-640,360)` —— `TL()` 是给子节点用的相对坐标，
   Canvas 自身应是屏幕中心 `(640,360)`。
5. **子节点误用 `addPart()` 的绝对定位**：`addPart` 走 `TL()`（相对 Canvas 中心），
   只能挂到 (0,0) 的满屏容器上。`HudProgress`/`HudTip`/`GoCard`/`Slot` 自己有位移，
   其下的 pip/箭头/星级/新角标全都偏移叠加两次，**飞出屏幕**（HUD 的 8 个关卡格整个消失）。
   判据：**父节点 lpos 不是 (0,0) 时，子节点一律用 `addSprite + inPart()`**。

另外：容器节点（Pets/Badges/HUD/Dock）补 `UITransform`（除 3D 相机外每个节点都要有）。

**验证器 12 → 17 项**，新增「Scene→Canvas 反向」「子节点唯一/单父」「Canvas 位置」「相机 z>0」「每节点 UITransform」。
