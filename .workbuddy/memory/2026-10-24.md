## 补证：饱食轨迹（订正上一节「回家=负收益」的说法）

`grove.html:10653` `S.belly = Math.max(0, S.belly - 16)` —— **每过一屏掉 16**，

## Cocos 键盘双通路修复 + 主界面/战斗内优先级判定

用户两问：① cocos 启动按 F12 没反应 ② 主界面系统是不是更该优化、战斗内是否需要更丰富机制。

### ① F12 没反应 = 两层原因

1. **跳关是 F2，不是 F12**。F12 在浏览器 / Creator 里是开发者工具，键到不了页面。
2. 更硬的：**键盘有两条并存通路，Cocos 侧只接管了动作键**。

   - `GroveBattle` 挂 Cocos `input` + `KEY_MAP`，只映射方向/WASD/空格/J/K

**修法（不复制判断逻辑，这是关键）**：

- 运行时 keydown 匿名函数 → 具名 `onKeyDown(ev)`，DOM 那条继续挂

- `GroveBattle._onKeyDown`：`KEY_MAP` 命中且 `phase==='play'` → 快通道；其余全走 `CODE_NAME` 翻译后 `_key()`
- `EventKeyboard` **没有 `repeat` 字段** → 自己用 `_held: Set<number>` 记（不记的话按住方向键在跳关面板里会飞到底）

冒烟新增 §27c 共 10 条断言（含"紧接着重复 F2 被去重""换键不受影响""repeat 不移动光标"）。

- 台面高度全集 `{156,248,350,462,556}` **只 5 档**
- 台面类型 `ground 27 + ledge 131`，**158 块全是水平矩形，零竖直构件**
- 波次：**15/27 是 `4+4+1`，27 屏全部是「两小波+一 BOSS」，无一例外**
- 敌人 bug **175** / boss 27 / boar 24 / crow 22 → 刺毛虫占 **70.5%**
- 有坡/菇/门的只有 **11 屏**（1,2,3,4,5,6,10,13,15,21,22），**16 屏完全没有会动会变的件**

### 根因（这条要记住）
**同质化的根因不是"机关太少"，是"机关和胜利条件无关"。**
坡只用在 6 屏、弹菇 2 屏、传送门 3 屏；而 7 种目标共 27 次使用**全是计数型/禁止型**，
没有一种回答"球必须往哪儿走"。于是机关全部退化成"更好看的解法"。
**最强证据 = 第 4 屏「缓坡」**：一条 494px 长坡（yL:350 → 地面）专为"顶层推冰壳球"做的，
目标是 `chain:3` —— 在地面糊三只照样能过。设计做对了，目标没跟上。

**所以改动顺序不能反：空间型目标 → 新原语 → 重排关卡。**
先加机关 = 给已经没用的地形再加一层装饰。

### 本作独有的资产：预瞄线
`predictBall()` 逐字复刻 `updateBalls()`，玩家出手前能看完整轨迹。
→ 本作该做**可规划的谜题**（多段因果链），不该做**要躲的反应型机关**。
→ 硬约束：任何新空间件必须 `updateBalls` 与 `predictBall` **两处逐字同源**，
实际工作量 = 估算 **×2**，且第二份写错不报错、只让预瞄线骗人（比不画更糟）。

### 提案：6 原语 + 4 空间型目标 + 三产地空间语法
原语：N1 地脉（材质摩擦）/ N2 反射板（几何反弹）/ N3 承重（可塌结构）/
N4 双层门（portal 升级：跨层 + 人球共用）/ N5 流场（持续横向力）/ N6 单向阀。
**移动平台砍掉** —— `stepBody` 没有平台速度继承，改造成本≈重写落脚模型，用 N5 替代（1/5 成本）。
目标：`route`（指定入口）/ `via`（依次串点）/ `drop`（≥2 层落差）/ `rebound`（必须撞机关）。

三产地空间语法（换语法不是换皮）：
- 产地一「塔」落差与角度 → N1+N2，禁忌：整屏台面全是水平横条
- 产地二「棚」结构会崩 → N3+N4，禁忌：悬空且无可见支撑的大台面（现在 131 块 ledge 全飘着）
- 产地三「流」介质会变 → N5+N6，禁忌：地面从头通到尾（现在地面全是 26..934 整条）

27 屏重排：全新重做 **5 屏**（7/8/14/17 + 部分 13），改目标 **6 屏**，加原语 **16 屏**，其余微调。
→ 骨架能用的约占一半，比"27 屏重画"实际。

## P2 实装：赛道 TOUR（commit 3fbcbcf）

用户对 P1 的反馈是「**没什么感觉**」。这条反馈就是 P2 的立项理由，
也是本轮最重要的一条判断依据：**改摩擦系数 ≠ 改玩法。**

### 核心判断（最值钱的一条）
**这套物理里球几乎从不飞。** 推球初速 `vy = -40`，竖直来源只有"从台面掉落"和撞斜板。
所以"在半空摆环让球穿过"在这个引擎里做不到 —— 方案必须贴着台面设计。

### TOUR 设计
`tour: [{x1,x2,y}...]` + `tourNeed`。球必须**按顺序**走完，游标存**球**上（`b.tour`）。
- 赛道是**附加约束**不是第七种目标：`checkGoal` 里加一条 `TOUR.length && toured < need → false`。
  第一版改成 `goal:"tour"` 时打挂两组断言（全游戏唯一 bank 关消失、forceClear 推不动关卡）。
- 判定 `|球y − 段y| ≤ 12 && x1 ≤ 球x ≤ x2`；x1/x2 一律 min/max。

### 第 5 屏「弹菇」= 之字下降
地面弹菇(200) → 350 层 → 右端 734 掉下 → 462 层 → 右端 800 掉下 → 营地。
实测：350 层 x=250 **基准力走完 2 段；满力只走 1 段**（撞 350 层的桩 650）。
**力度本身成了空间决策** —— 这是这一屏真正的新东西。

### 三个坑（下次别再踩）
1. **`goalProgress()` 的 `text` 字段从来没被 HUD 画过**。HUD 只用 `cells/filled/frac/inner`。
   写进 text 等于没写 → 必须在进度条右侧空白里单独画（豆子右端 BX+207，卡片 272）。
2. **`P.PUSH_BASE` 未导出** → `pow || PUSH_BASE` 里 `NaN` 是 falsy，静默退化成基准 620。
   表现为"满力推只上升 40px"，看着像板坏了。已导出 PUSH_BASE / PUSH_RUN。
3. **球的 y 语义**：`updateBalls` 里是底边，`predictBall` 的 `pts` 是 `y - r`（视觉点）。
   判定用内部 y，画图用 pts，两者差 22px，不能混。

### 视觉迭代三次（都因为截图看不出东西返工）
alpha 0.16 纯色带 → 融进木台面｜加斜纹后两段仍无联系｜出口 1.5px 虚线 → 缩 50% 消失 →
最终：光柱（宽 10、向下渐隐）+ 实心箭头 + 斜纹 + 实边 + 序号「起点」。

### 遗留（必须下一批先修）
**第 7 屏的板把球送回左边送死。** 满力能上 462 层，但反射后 `vx` 必然为负（`/` 形板法线朝左上），
