## 深巢加雾（雾巢）+ 巢室生态 —— 已提交 760ac10

用户原话：「现在这个关卡的怪物都一样啊」「这个关卡 我感觉可以做一个下探的关卡
有迷雾啥的 探索性的 你发挥下想象 创造力」。

**两个病根**：池子是全局的（浅层 1–4 只剩 bug/bug/spider）；一进场整屏全亮，
暗罩只管"离你多远"不管"你去过哪"，那片黑永远不会变形状。

**做了什么**（source of truth 仍是 `prototype/grove.html`，已重抽 GroveRuntime.ts）：

- 光照栅格：`lit`（每帧重算）+ `seen`（只增不减）= 三档明度
  （看得清 / 走过记得 / 没去过）。16px 格 → 40×32 位图 → 放大铺屏，
  一次 drawImage；每格 alpha 乘一个每层固定的噪声（0.86~1.00）。
- 光源：随身灯 240/200/175、球 258/238/222（球就是火把）、炸开的囊 168、
  裂缝 90（只给 0.09，够认出"那边有暖色"）、蛾 88 / BOSS 118。
- 菌光囊：每层 2~3 个，走上去或球撞就炸 → 永久点亮 + 孢子 +2。
- 巢室：蛛巢/石室/卵房/菌圃/地脉，决定怪池 + HUD 名字 + 囊数；
  解锁提前到 1/4/8；同波前 N 只强制不同种（不额外抽随机数）。

**四条坑（下次直接看这里）**：
1. 新内容必须走独立随机流 `nestRand(seed ^ 0x9E3779B1)`，否则 60 层地形整体漂移。
   守门人 `tools/_nest-hash.js`：地形哈希必须一字不差，波次哈希允许变。
2. **`nestMirror` 从没翻过 `chasms`**（10-26 加裂缝时漏的那一行）。
   后果是坐标系分裂。镜像对相对距离是等距变换，补上是安全的。
3. 魔数出现在两个文件里 = 两个真相（生成器 44 / 断言 50 → 482 条全红）。
   统一读 `NEST_FOG.POD_CHASM`。
4. 雾第一版 0.62 太淡（量化：只差 25 级亮度，人眼要 ~40 级）；
   底光原来画在雾之后，整条屏宽把雾照亮 → 挪到雾之前。

**顺带**：`nest-play.js` 原来用 Math.random，同代码两次跑差 1~2 层，
现在按 (层, 角色) 钉死种子，通关率才第一次能横向比。
本轮 14/18，旧代码同种子 89%，差的 2 层都是"剩 1 只送不走"（脉虫窗口 / 蛾要光照）。

**踩过的渲染坑**：`TH` 深巢主题字段是 `wood/wood2/wood3`，没有 `woodDeep` ——
`hexDim(undefined)` 会直接抛错，而且抛在 drawLevel 里 = 整屏地形消失。

**没做**：雾边界撕裂感、裂缝吞球/吞人、走到底部裂缝才下潜、巢室场景道具。

## 目标平台定调：Steam（2026-10-27 用户确认）

用户问「为什么你参照 html 做 不是 cocos 吗」，追问后确认目标平台是 **Steam**。

**当前架构与 Steam 的直接冲突**（先记下来，等真要打包时会撞）：

- 推球逻辑确实在 Cocos 里跑（`GroveRuntime.ts` 是工程资产，引擎编译执行），
  但**画面是叠在 Cocos 画布上的一层 DOM canvas**，不走 Cocos 渲染管线。
  起因：2026-10-21 走 `Texture2D.uploadData` 正路时纯黑，查出
  `Battle.scene` 无 RenderRoot2D、自建相机 visibility 排除 UI_2D。
- 所以 `GroveBattle.ts` 硬依赖 `document`。**打 Windows 原生时 `onLoad` 会被
  第 170 行守卫静默 `return`（只打一行 console.error），战斗场景是一块空屏。**
  这条最危险：不崩、不报错、只黑屏 —— 崩了当场发现，黑屏可能拖到发版前。
- 两条出路：
  ① **Electron/套壳 Web 构建**上 Steam —— DOM 保得住、像素级一致，
     代价是包体 +100MB、手柄要自己接（Gamepad API）、Steam Deck 需 Linux 版 Electron
  ② **Cocos 原生** —— 渲染层重写约 2000 行 ctx 调用，包体小、Cocos 自带输入接手柄
- 用户拍板：**渲染层先不动，等平台方案定死**。合理 —— 现在改了没产出。
  但「先不动」≠「不用管」：画面出口本来就收在 `_mountStage` 一个点上（674 行里
  其余是挂载/存档/键位），将来换实现只改这一处，不会波及玩法。

**下次要做的第一件事**：把静默黑屏改成显式失败（原生平台启动就抛错），
否则将来打包 Steama 版会得到一个"游戏能进、打完第一屏进战斗就全黑"的版本。

## 跳虫第二轮：白跳 + 穿模（已提交 d4458eb / 16b1aa3）

用户两条反馈都是真的：「有的地方不能跳、有的可以，要做合理设计」+
「UI 图里敌方和横木叠加了」。

**病根一（白跳）**：起跳判据只有「高出 40px / 水平 240px / 冷却好了」，
既没上限也不看落点 → 玩家在两层之上（206px）它照样蹲，跳高 123px 顶板底掉回来。
**修法 `pounceLands()`**：逐帧预演抛物线（复刻 stepBody 的单向平台判据 + 木桩实心），
落点比起点高 ≥60px 才许蹲。规则变成玩家能算的一条：它只在真能上去时才蹲。

**病根二（穿模）**：单向平台允许从板底穿上来（**玩家自己就这么跳**），
板厚 20、虫高 28，穿过去必"半截在板上半截在板下"；敌人画在所有地形之后 → 读作 bug。
**修法 `platOverFoe()` 压到板后 + 板顶跟随暗影**。只遮挡不够 —— 出图实测虫被板
整只吃掉（剩 4px 黄边 + 悬空箭头），读作"虫消失"，比嵌在木头里更糟。

**走错的一条路（重要，别再走）**：先试"禁止穿模、让虫绕到板外再跳"，三连崩：
① 判序错——先判穿模再判落地，落地帧 y 还没被纠正（脚 467 在板 462..482 内）→
   27 屏 **38 块台面当场不可达**；
② 板沿震荡——出板后 platAbove 变空、朝向被"朝玩家"覆盖回去，13px 来回摆，
   **7 屏里 6 屏永不上来**（f.detour 锁方向能治，但那是在给错方向打补丁）；
③ 桩：第 13 屏桩立在板中间，两边都被挡。
结论：为躲两帧穿模把机制搞死不值。**穿板不是 bug，是同一条语法** ——
玩家和敌人用同一条规则才叫一致；穿模用遮挡，Mario/Celeste 一直这么干。

**净效果**：逐屏清场 A/B（PROTO=git show HEAD:）**3 clear → 6 clear**
（slope→25s、twin→40s、tundra_boss→122s）。不白跳后机器人反而更好清场：
白跳的虫落回原地要重打，现在要么真上去（同层，打得到）要么在下面不动。

**新工具 `tools/_jump-reach.js`**（三节）：预演 vs 实跑对账（**只查虚假承诺**，
反过来查会得出"必须允许穿模"的荒谬结论）、不白跳（8 屏 ×10s，阈值 0）、
可达性普查（27 屏 125 块台面找起跳点，0 死角）。
**可达性普查这类"每块台面都要有解"的检查只能靠机器**，感觉查不出来。

已知未修：虫在木桩正下方上不来（桩是实心墙，理应如此），会 13px 级徘徊。
判断可接受 —— 桩只 1-3 根、24px 宽，「桩底下是安全区」本身是地形给出的信息。
