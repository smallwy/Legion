## 0 · 一句话

**角色形象在这个仓库里有三套现成出处，动手前先问「哪一套能用」，不要先问「怎么画」。**
这次的错误不是画得不好，是**重造了一个已经存在的东西**。

## 0.5 · 两条原型线：什么时候可以单开文件

仓库里有两个可玩原型，**两条都有自己的抽取管道**，都能进 Cocos：

| 文件 | 起点 | 规模 | 抽取管道 |
|---|---|---|---|
| `prototype/grove.html` | 10-20 | 21599 行 / 27 屏 | `extract_grove_runtime.py` → `GroveRuntime.ts` |
| `prototype/snowlab.html` | 10-28 | 7200 行 / 单屏 | `extract_snowlab_runtime.py` → `SnowlabRuntime.ts` |

**snowlab 是当"量具"建的**，当时的理由也成立：要动的是输入通道（近身糊 → 远程吐）
和资源模型（球额度 → 弹药），两处都在 grove 最底层，而 grove 有 1463 项冒烟断言。

**但这个理由只对"做量具"那一段成立。** 试验台后来开始改玩家**看得见**的东西
（美术风格、镜头、震屏、破碎、主角贴图），主线没跟上 —— 于是同一样东西两边各写一份，
而且新写的那份更差：

| 用户实际说的 | grove（早就做对） | snowlab（重写后） |
|---|---|---|
| 子弹要有特色、有下落 | 六只六把武器，萝卜横射 806px | 统一雪球，直线 149px |
| 宠物别比箱子大 | 玩家 38×44 < 木箱 48 | 贴图视觉宽 68.7 = 1.43 箱 |
| 震屏效果不好 | 20+ 处分级（3~15） | 一处随机平移 |

**判据：这个文件是"量具"还是"作品"，看它有没有开始承载玩家能看见的东西。**
只跑数值（发数、伤害、掉落率）→ 可以单开；
一旦动美术 / 手感 / 镜头 / 演出 → **必须回主线**，否则就是分叉。

### 融合方向：**snowlab 是主体**（2026-10-29 用户拍板："反过来"）

上一版文档这里写的是"grove 是主体"，理由是 grove 内容完整、27 屏、六宠系统。
用户否掉了，原话只有两个字：**"反过来"**。

理由站得住：grove 那 27 屏是**手写坐标**的老关卡，而 snowlab 这一轮刚拿到
程序化生成器（难度递进 / 主通道 / 连通校验 / 门随机）—— 那套东西搬到 grove
等于把 27 屏手写关卡全部重写；反过来把 grove 的**内容**（六宠武器、道具、
黑洞、玩法模块）搬进 snowlab 的生成器，是加法。

所以：

| 方向 | 内容 |
|---|---|
| snowlab → 保留 | Q 版地牢美术、程序化关卡（递进/连通/门随机）、箱堆地形、弹药与裹球 |
| grove → 搬进来 | 六宠六武器的**手感参数**（已搬弹道，伤害层未搬）、道具与小物件、黑洞 |

**注意 snowlab 现在的关卡生成规则已经写死了几条硬约束，搬任何东西进来都不能破：**
- 层高锁 240（净空 214 − 玩家 63 = 151，二段跳 272 才够跨层）
- 单洞最宽 144（更宽切出来的段跳不过去，是死胡同）
- 任何一段 ≥ 96（一列宽的碎段是孤岛）
- 箱子相邻高差 ≤ 2 格（96 < 跳高 123，破了你就有墙）
- 走廊列恒 0 格、相邻列 ≤ 2 格，且不许贴井梯

这几条都有断言守着（`_snowlab-check.js` §一 / §三十 / §四十）。

## 1 · 三套出处（互相是副本关系，不是三个设计）

| 位置 | 是什么 | 谁在用 | 尺寸 |
|---|---|---|---|
| `assets/ui/home/pets/<中文名>.png` | **立绘源**，美术出的正面站姿大图 | `Home.scene` 直连 spriteFrame（家 / 主界面） | 256px 级 |
| `assets/resources/grove/pet/<id>.png` | 立绘源的**收缩副本**，`gen_grove_art.py` 产出 | `GroveBattle.ts` 的 `ART_MANIFEST` → 雪人关卡战斗 | 统一图高 **292** |
| `assets/resources/grove/head/<id>.png` | 同一批图的**圆头像**副本 | HUD / 编队 | 96 |
| `prototype/snowlab.html` 的 `drawPlayer()` | **纯代码图形**，一张贴图都不引用 | 只在贴图取不到时兜底 | 按 `PLAYER_W/H` |

`id` 六个，两处必须一致（`HERO_IDS`）：

| id | 中文旧名 | 立绘文件 | 名字 | 武器 |
|---|---|---|---|---|
| `cat` | 砂糖 | `sugar-stand.png` | 尖耳猫 | 溜溜球 |
| `dog` | 年糕 | `nian-gao-dog.png` | 短尾犬 | 音波喇叭 |
| `ham` | 团子 | `tuan-zi-ham.png` | 胖仓鼠 | 滚坚果 |
| `rab` | 雪团 | `xue-tuan-rab.png` | 长耳兔 | 萝卜炮 |
| `ox` | 豆奶 | `dou-nai-ox.png` | 老实牛 | 飞刀 |
| `fox` | 星屑 | `xing-xie-fox.png` | 影狐 | 影分身 |

**结论**：`grove/pet/` 不是"另一版设计"，是同一只的侧视可用版。
它同时满足三件事 —— 侧视、能施法、和主界面同一只 —— 所以战斗里**默认用它**。

## 2 · 判定流程（按顺序问，别跳）

```
要画一个角色
  ├─ ① `grove/pet/<id>.png` 有吗？
  │     有 → 贴图。键名 `pet-<id>`，绘制走 drawPetSprite()
  │     没有 → ②
  ├─ ② 这个角色是"敌人"且 `grove/foe/<id>.png` 有吗？
  │     有 → 贴图。键名 `foe-<id>`
  │     没有 → ③
  └─ ③ 代码图形（回退路径）
        只在：jsdom 出图没注入 / resources.load 失败 / 新角色还没出图
```

**代码图形那一套不退场**，但它的定位是回退，不是主线。两条判据：

- 它能保证"加载不上也不白屏"，这是它的全部价值；
- **只要它被当成主线，画风必然断层** —— 代码画是矢量硬边，贴图是手绘，
  两张放在一屏里，玩家第一眼看出"这只不一样"。

## 3 · 三个高度，别混

贴图接进来最容易错的就是这一层。同一只猫有**三个不同的高度**：

| 量 | 是什么 | 值（cat） |
|---|---|---|
| 图高 | png 的像素高，**含耳朵和留白** | 292 |
| 体高 | 脚底到头顶（不含耳尖以上的留白） | 图高 × **0.656** ≈ 192 |
| 碰撞高 | 玩法判定的盒子 | `PLAYER_H` = **63** |

两个系数，定义完全不同：

```js
const PET_BODY_K = 0.656;  // 体高 / 图高   —— 素材属性，六只各自量出来的
const PET_VIS_K  = 0.70;   // 体高 / 碰撞高 —— 设计选择，**由箱宽倒推**（见下）
```

绘制宽度反推：

```js
const dh = h * PET_VIS_K / PET_BODY_K;                  // 先还原到体高，再还原到图高
const dw = dh * (img.width / img.height);
```

### `PET_VIS_K` 的取值史：0.78 → 1.0 → 0.70

**不能照抄 grove 的 0.78。** grove 用 0.78 是"让猫的体高只有碰撞盒的 78%"；
snowlab 的 `PLAYER_H = 63` 是照**代码画的那只**量的，那只体高就是 63。
直接搬 0.78 的后果：贴图猫体高 49，比木箱（48）高一格都不到 ——
而断言「玩家比箱子高（63/48 = 1.31）」**依然是绿的**，因为它按 `PLAYER_H` 算、
根本不看贴图。**机器绿、画面错。**

**改成 1.0 只对了一半。** 那一次对齐的是"体高 = 碰撞高"，**宽度没人管**。
`cat.png` 宽高比 0.716，体高一撑到 63，视觉宽就跟着到 **68.7**，
是箱宽（48）的 1.43 倍 —— 用户一句「比箱子大 没办法独立站一个箱子的空格」
才把它问出来。

**现在由箱宽倒推。** 要视觉宽 ≤ 48（= 一箱宽），图高只能到 67
（0.716 × 67 = 48），对应 `PET_VIS_K = 67 × 0.656 / 63 = 0.70`。
结果：视觉 **48.1 宽 / 55.2 高**，箱 48 —— 宽刚好一格，高 1.15 格。

**为什么不靠降碰撞高。** 试过 `PLAYER_H` 63 → 55（视觉 46.3×53.1，
两个条件都成立、碰撞与视觉只差 2px），一跑断言掉三条：比箱高 1.15 /
高度 ≥ 56 承载立绘细节 / 占屏 10.5%。那三条是"角色别缩回去变小"的红线 ——
**缩宽度不能拿高度去换**。

**代价**：碰撞顶比耳朵尖高 7.8px，跳起来会"没碰到就弹下来"。
这 7.8px 只能认：0.716 的宽高比决定了「宽进一格」和「碰撞 = 视觉」不可兼得。

> **教训（第二次撞同一类墙）**：第一次是"高度对齐了、宽度没管"，
> 第二次是"按断言调对了、按箱子量不对"。**角色尺度有三个轴 ——
> 高、宽、碰撞，只对齐一个是必然出事。** 断言现在同时守
> `PLAYER_W / BOX`、`PLAYER_H / BOX` 和形象宽 ≤ 箱宽三条。

## 4 · 绘制约定（四条，全是量出来不是调出来的）

**① 按体高缩，不按图高。**
直接按图高缩，六只集体缩水三分之一，站在怪旁边像幼崽。

**② 原图都朝左。**
翻转判据是 `if (face > 0) scale(-1, 1)`。写反的那版是"向右跑、脸朝左"。

**③ 出手闪白用 `filter: brightness()`，不是盖白矩形。**
盖矩形会在角色周围留一圈白框。系数 `1 + flash * 0.8`（上限 1.8 会提成白猫）。

**④ 走路是切图，不是整只上下蹦。**
同一张站立图按 `WALK_CUT[id]` 的 `hip` / `split` 切成前后腿，绕髋关节对摆，
身体反方向轻前倾。整只上下蹦那是"跳"，和跳跃动作撞在一起就读不出来了。

`WALK_CUT` 的六个值是对着**不透明像素**量的，换素材要重量。

## 5 · 验收怎么做

| 手段 | 抓什么 | 抓不到什么 |
|---|---|---|
| `tools/_snowlab-check.js`（183 项） | 结构、手感、跨模块等式 | **贴图实际画多大**（见 §3） |
| `tools/_pet-shot.js` | 6 倍矢量特写 | 静态帧看不出切腿切歪 |
| `tools/_pet-shot.js` + `POSE=run` | 跑动帧的两条腿有没有错位 | — |
| `tools/_snowlab-shot.js` | 整屏比例、和箱子的关系、耳朵是否穿楼板 | — |

**出图工具必须注入贴图，且加载失败要吭声。** 不注入就静默走代码图形，
而一张"看着也行"的代码猫，最容易把"没加载上"当成"就长这样"。

```
NODE_PATH=... node tools/_pet-shot.js
POSE=run OUT=... node tools/_pet-shot.js
PROTO=<另一版.html> OUT=... node tools/_pet-shot.js   # 对照组
```

## 6 · 当前缺口（2026-10-28 状态）

- **三只怪仍是代码画的**。`grove/foe/` 有 `bug` / `crow` / `boar` / `larva` 四张，
  但和 snowlab 的 `moss` / `fang` / `grub` **不是同一批角色**，
  不能直接贴过来，要单开一轮做"敌人贴图化"。
- **贴图版出手没有动作反馈**。代码版靠张嘴；贴图的闪白在浏览器有效，
  `@napi-rs/canvas` 不支持 `filter`，所以**出图上看不到**（不代表线上没有）。
- **snowlab 只有一只角色**。`artOf('pet-cat')` 是硬写成 `cat` 的，
  接多角色时改成 `'pet-' + heroId`。
