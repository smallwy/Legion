# Legion 主界面系统 UI 重规划

> 版本 v1.1 · 2026-10-24 · 依据 `HomeRuntime.ts` 与 `config/HomeBiz.ts` 源码实读
> 范围：图鉴 / 工作台 / 灶台 / 派遣 / 设置 / 任务 六个入口
> 状态：**已实施**（四条拍板全部落地，见 §7 实施记录）。评审与规格部分保留原文，作为改动依据。

---

## 结论先行

1. **"很 Low" 不是画风问题，是界面形态问题。** 六个功能全塞进同一个 `openSheet()` 壳（640×520 米白卡 + 等高药丸行），所以灶台、工作台、派遣、任务、设置**长得一模一样**，只有标题字不同。玩家看不出这是六个不同的系统 —— 这是结构性病根，重画图标救不了。
2. **任务面板最该先改，且改动最小。** 六个任务平铺六行等高条，奖励埋在一句话里，三态（未完成/可领/已领）里两态同色，可领的不置顶。单文件改动约 120 行，能立刻从"表单"变成"清单"。
3. **任务不该是弹窗。** 它是随时要瞟一眼的东西，不该压暗全屏、强迫关闭。建议改右侧抽屉。这一条要你拍板（涉及交互习惯改变）。

## 一、现状盘点：五个入口，一个壳

| 入口 | 打开方式 | 实际内容 | 本质 |
|---|---|---|---|
| 图鉴 | `openCodex()` | 3×2 六格，Graphics 画圆 + 名字首字 | **已做对**（独立面板、独立形态） |
| 灶台 | `openKitchen()` → `openSheet` | 3 行药丸：食物名 + 花费 + 饱食值 | 列表 |
| 工作台 | `openBench()` → `openSheet` | 2 行药丸：配方 + 花费 + 用途 | 列表 |
| 派遣 | `openDispatch()` → `openSheet` | 4 行药丸：宠物名 + 能不能派 | 列表 |
| 设置 | `openSettings()` → `openSheet` | 2 行药丸：画质 / 音效 | 列表 |
| 任务 | `openTasks()` → `openSheet` | 6 行药丸：名字 + `desc · reward` + 状态 | 列表 |

**同一个 `mkRow()` 造出了六个系统的全部内容。** 每行结构固定：

```
(首字圆 36)  名字 20px          花费/描述 12px         [ 96×34 药丸 ]
```

后果：

- **首字圆是假的图标。** 取 `title.slice(0,1)`，"出门一趟"取"出"、"喂一顿"取"喂"、"做一份干粮"取"做"、"派人去采"取"派"、"带同伴回家"取"带"、"跟它熟一点"取"跟"。六个 18px 圆圈里各一个字，视觉上完全等价于**没有图标**。
- **一行塞三件事**，中间是 ` · ` 拼起来的字符串（任务：`打完回来一次 · 果子 +12 · 材料 +2`）。玩家要奖励，得在一句中文里找加号。
- **卡高写死 520**，6 行只占 276 高，底部 130px 空气。反过来灶台 3 行、设置 2 行更空。

## 二、任务面板评审（六维度 · 满分 5）

| 维度 | 分 | 依据 |
|---|---|---|
| 剪影可读性 | **2** | 六行等高同宽圆角条。缩到 10% 是一片条纹，分不出哪行能领 |
| 明度层级 | **3** | 可行/不可行只差按钮底色，整卡明度差 < 8% |
| 构图与负空间 | **2** | 640×520 装 276 高内容，下 130px 空；可领项不置顶 |
| 风格一致性 | **4** | 米白卡 + 棕描边与场景一致，无突兀 |
| 技术合规 | **5** | 尺寸/文字无溢出，热区 ≥46 高（略低于 88 触屏下限，任务行可接受） |
| 可用性 | **2** | 奖励埋在句中；三态两态同色；`desc` 是产品说明不是进度 |

**结论：重做**（剪影与可用性不过关，不是调明度能救的）。

### 症状清单（问题 → 为什么 → 改法）

| # | 问题 | 为什么是问题 | 怎么改 |
|---|---|---|---|
| 1 | 奖励和描述挤在一个 Label：`打完回来一次 · 果子 +12 · 材料 +2` | 玩家点开任务只有一个诉求 —— **领什么**。奖励是数字，读数字比读中文快一个数量级 | 奖励拆出去：右侧固定三栏 `🍎12  🪵2`（图标 18 + 数字 15px 紧贴）。`desc` 删掉（任务名本身就是动作），进度另给 |
| 2 | 三态只改颜色：`未完成`/`领取`/`已领` 都是同一个 96×34 药丸，前两个还都是灰 | 卡片缩略图测试必挂。玩家扫一遍分不清"哪些能点" | 三态三形：**可领** = 杏黄实心 + 行左 4px 杏黄竖条；**进行中** = 无按钮，右对齐 `0/1`；**已领** = 整行 45% 透明 + 对勾，且**折叠**（默认只显示「已完成 3 ▸」） |

| 4 | 没有进度值 | 存档里是 `s.runs >= 1`，界面只显示"未完成"。玩家不知道打了几次 | `TaskDef` 加 `cur(s)` / `target`，右侧显示 `0/1`，达标时变对勾 |
| 5 | 副标题是产品说明：`做完就领，不每天刷新` | 每开一次念一遍。玩家要的是"有几件可领" | 副标题只放状态：`2 件可领 · 共 6 件`。产品说明首次进入弹一次 toast，不进常驻文案 |
| 6 | 首字圆冒充图标 | 六个圆圈各一个字，视觉等价于无图标 | 用**已有素材**：`assets/ui/icons/` 里 12 个 PNG 正好覆盖（flag/pot/hammer/paw-red/paw/mail） |

## 三、结构性病根：弹窗只该给"必须专注的决策"

六个功能共用一张卡，是因为**它们被当成了同一种东西**。实际上它们分三类：

```
清单型（扫读 + 点一下）        对象型（对某个主体操作）        世界型（空间决策）
├ 任务                       ├ 灶台：对「某只宠物」喂饭      └ 派遣：把「谁」派出去
└ 设置                       └ 工作台：对「某个配方」制作
```

### 重新规划的信息架构

| 系统 | 形态 | 理由 |
|---|---|---|
| **任务** | 右侧抽屉 360 宽，从屏幕右边滑出，**不压暗场景** | 任务是"瞟一眼"，不是"进入一个地方"。压暗全屏 + 点空白关闭 = 每次都打断玩法 |
| **设置** | 保持弹窗（清单型，低频） | 一年开三次的东西不值得单独设计 |
| **灶台** | 对象型面板：左侧当前出战宠物立绘（96 高）+ 环形饱食表，右侧 3 个食物卡（竖排） | 喂饭的对象是**宠物**，现在界面里根本没有宠物，只有"XX 的肚子 42/100"一行字 |
| **工作台** | 对象型面板：左列配方（带产物小图），右侧成品预览 + 材料需求（缺料标红） | 制作的对象是**物品**，现在没有产物图 |
| **派遣** | 不走弹窗。木牌上直接显示倒计时（已有 v3 卡片），点开是"选同伴"小卡 | 已经做对了方向，只是内容还是药丸行 |
| **图鉴** | 保持现状 | 独立形态，已正确 |

**一句话判断标准**：如果这个功能的对象是"某个具体东西"（宠物、物品、配方），界面里就**必须出现那个东西**。现在六个面板里一个对象都没有，全是文字行 —— 这是"Low"的第二个来源。

## 五、需要你拍板的三件事

1. **任务要不要从弹窗改成右侧抽屉？** 改 = 不打断场景、随时瞟；不改 = 保持一致性，但每次都压暗全屏。
2. **灶台/工作台要不要出现"对象"（宠物立绘、产物图）？** 这需要各 1 张立绘 + 2 张产物图。有图就做对象型，没图就是现在的列表 —— **这是"Low"最根本的一条**。
3. **六个入口要不要收敛？** 现在右侧竖栏 5 个徽标（图鉴/工作台/灶台/派遣/设置）+ 屏幕中央任务胶囊。可收敛为 4 个：把「灶台 + 工作台」合成一个「家」入口，内部用左右分栏。减少 20% 的入口密度。

### 7.2 与提案的偏离（三条，都有理由）

1. **「已领」没做折叠**，改成沉底 + 整行 45% 透明。
   六个任务里最多一两个已领，折叠的交互成本（点开/收起）大于它省下的空间。
   规格里"折叠"是为任务量到 10+ 时准备的，现在过早。

2. **家面板的喂饭/制作做成 tab**，不是提案写的"左右分栏同时显示"。
   左右同时显示的话每张卡只有 200 宽，塞不进"产物图 + 代价 + 收益 + 按钮"四件东西。
   tab 让每张卡有 400 宽，代价是喂饭时看不到配方 —— 但这两个动作本来就不会同时做。

3. **奖励图标在离屏渲染环境里验证不了**。
   `tools/_home-rt-shot.js` 的 `resources` 桩**固定回调 err**（这是故意的：要验证"图不在时主界面照常进"），
   所以截图里图标位全是回退的空圆 + 首字。真机有图，但**这一点只能你在 Cocos 预览里确认**。

### 7.3 验证

| 手段 | 结果 |
|---|---|
| `tsc -p tools/tsconfig.homeruntime.build.json`（真类型检查，不只是语法） | 0 error |
| `node tools/_rt-check.js`（端到端 61 项） | 61 通过 / 0 失败 |
| `tools/_home-rt-shot.js` 渲染 + 人工看图 | 主界面四入口 / 任务抽屉 / 家面板 三张已归档 `client/art/04-review/2026-10-24-*` |
| `grove-smoke` + `grove-runtime-check` | 377 / 14 全绿（确认没连带破坏战斗） |

**过程中修掉的三个真 bug**（不是笔误，是会让人查半天的类型）：

1. `HomeRuntime.ICON_KEYS` 静态引用写错类名 —— 类名是 **`HomeController`**，`HomeRuntime` 只是文件名。
   `tsc` 报 TS2304，但 `tools/ts-syntax-check.js`（只 parse 不查类型）**全绿**。
   → **这次改了 HomeRuntime 就必须跑 `tsc -p tools/tsconfig.homeruntime.build.json`**，只跑 syntax-check 等于没查。
2. `new Graphics()` + `panel.addComponent(实例)` —— `addComponent` 只接类，不接实例。
3. `sf.rect.width` 在离屏桩里是 `undefined.width` → 崩在 `openSheet` 里，
   表现是"点了没反应"（面板根本没建起来）。已改成取不到就按 1:1 放。

另外顺手补了 `tools/_mock-cc.js` 的两处缺失：`Sprite.SizeMode` 枚举、`SpriteFrame.rect`。
桩缺一个枚举的后果是**运行时**抛 `undefined.CUSTOM`，比渲染错更难查。

## 八、第二轮修正（2026-10-24，用户驳回后）

用户两条意见，都成立：

> 1. 设计一个东西不考虑遮挡吗？任务不应该放左边吗？而且不能占位那么多吧
> 2. 字体遮挡对齐问题，你不能自己查一下吗

### 8.1 抽屉位置：右侧 → 左侧，全高 → 按内容

**上一版把抽屉放在右侧 340 宽，正好压住全屏最活跃的一块**：派遣告示牌 + 粉垫上六只宠物的右半 + 右下角「出门」。玩家想"一边看任务一边看宠物"—— 恰恰做不到。这是设计时没查场景占位，不是审美分歧。

左侧 340 宽压住的是 Logo、路标牌、木桌边缘 —— 开抽屉时本来就不需要看，而且任务入口（路标牌上的胶囊）就在左边，从入口位置展开逻辑更顺。

高度也从 720 全高改成**按内容算**（六任务 606），上下各留 30+；垂直位置 +26，避开底部资源条（资源条在 y −360..−290，居中的话抽屉底边 −291 正好压它顶部）。

同时去掉全屏拦截层 —— 那层会把整个场景的点击吃掉（宠物摸不到、徽标点不到），等于一个"不压暗的弹窗"，目的白费。改成 canvas 冒泡关闭：`drawerTap` 挂在 canvas 上，抽屉内部 stopPropagation 挡住自己。

⚠ 由此派生的两处必须记住：
- `dispose()` 里要 `canvas.off(TOUCH_END, drawerTap)` —— 节点销毁不会带走外部监听，切场景后旧监听还活着。
- `openCodex()` 要显式 `closeDrawer()` —— 图鉴入口在抽屉右侧没被盖住，点了会两个浮层叠着（openSheet 自带所以我以为不用，图鉴是自己一套）。

### 8.2 文字遮挡：工具量出来的，不是目测

**关键认识：这类问题看截图看不出来。** 1280 宽的图缩到 50% 显示时，两个容器重叠 2px 和完全分开长得几乎一样，所以第一版才会"看起来正常"。必须让工具量。

给 `tools/_home-rt-shot.js` 加了 `--text` 审计，两段：
1. **文字溢出**：用 `measureText` 比实际文本宽 vs 容器宽，按 overflow 模式区分（`NONE` 会压邻居 / `CLAMP` 会截断 / `SHRINK` 安全）。
2. **文字间距**：同父节点下两个 Label，一轴重叠时另一轴净间隙 < 4px 就报，重叠直接标 ✗。

**检测脚本自己先错了一次**：起初按 anchor(0.5,0.5) 硬算矩形，把并排的 `Btn-Go/txt` 和 `/line` 误报成"重叠 61×16"。Home.scene 里的 Label 绝大多数是 anchor **(0,1)** / (0.5,1)。读 `ut._anchorPoint` 之后才是真实数据 —— **先修检测，再改 UI**，否则照着假数据越改越乱。

真实结果（6 处，全部是场景原有版式，不是这次新加的）：

| # | 位置 | 改前 | 改后 |
|---|---|---|---|
| 1 | Logo 英文副标题 | **被中文标题压住 8.5px**，屏幕上根本看不见 | 下移 15，间隙 3.8px |
| 2 | 关卡进度「苔 原」/「3 / 8 关」 | 重叠 1.8px（`txt-prog` 没参与 `alignHud` 的中线对齐） | 按 stage 实际位置下推 20，间隙 3.6px |
| 3 | 出战卡「砂 糖」/ 心形 | 重叠 2.1px | 心形下移到 −34，belly 让到 −53 |

修在**运行时** `fixLabelTightness()`，不改场景 JSON（`JSON.stringify` 重写会让 `__id__` 重排、2000+ 行全量 diff；而且坐标真相会分裂成两处）。方法排在 `alignHud` / `layoutRail` 之后 —— `txt-prog` 要跟着 `txt-stage` 的**实际**位置下推。

新行内排版也顺手改了两处：

### 9.1 「家」→「工坊」，顺带修掉文字没有真居中

**改名**：灶台（喂饭）和木工台（做东西）是两个动作，叫「家」把"在这里能动手做东西"整个盖掉了 —— 名字应该描述**这里能做什么**，而不是"这是个什么地方"。

**"字体对不齐"的根因不是偏 1~2px，是 Label 的对齐方式错了**：

| 项 | 值 | 后果 |
|---|---|---|
| `Cap-工作台/txt` 容器宽 | **36**（场景里按「工作台」三个字写死） | — |
| Label 对齐方式 | `hAlign = NONE`（左对齐） | 文字贴在容器左边 |
| 实际文字「家」 | 12px 一个字 = 12 宽 | 距容器左缘 0，容器距牌子左边 2 → **字整体偏左 12px** |

改文案时字数变了、容器宽没变、对齐还是左对齐 —— 三个条件凑齐就歪。修法不是挪坐标（下次改文案又歪），是让容器吃满牌子 + `CENTER` + `SHRINK`：

```ts
private fitCapText(cap: Node, capW: number) {
    tut.setContentSize(capW - 6, capH - 4);
    tlb.horizontalAlign = Label.HorizontalAlign.CENTER;
    tlb.verticalAlign = Label.VerticalAlign.CENTER;
    tlb.overflow = Label.Overflow.SHRINK;
    txt.setPosition(3, -2, 0);      // anchor(0,1)，去容器左上角
}
```

`alignHud()` 和 `layoutRail()` 都调它（幂等）。以后三块牌子写几个字都居中。

### 9.2 任务抽屉：从「六个药丸」改成「一张清单」

上一版的问题不在配色，在**形态选错**：

| 上一版 | 现在 |
|---|---|
| 行高 **72**，双行（名字在上、奖励在下） | 行高 **44**，单行（名字 + 右侧奖励组 + 按钮） |
| 每行一张 72 高圆角卡 → 六行 = **六个按钮** | 行间只画 1px 细分隔线 → **一张清单** |
| 「全部领取」占一整条 272×46 实心大按钮 | 收进标题行，84×28 小胶囊 |
| 已领平铺 5 个灰行 | 折成一行「▸ 已完成 N 件 / 展开」 |
| 宽度 340、高度 606 | 宽度 **300**、高度 **194~370** |
| 纸淡入 + 整块平移 | 纸**不淡入**（从边上滑出来），内容延迟 70ms 从下方 8px 落位 |

**双行是"占位太多"的直接原因，而且没有多给信息**：第二行只放了两件小奖励，横向排开在名字右侧完全放得下。改成单行后六条 336 高，常态（1 条可领 + 折叠）只有 194 —— 屏幕的 27%。

**「已领」行的处理**：不列奖励，只留一个「已领」右对齐。奖励在领的那一刻就给过了，重复列只会和「已领」两个字打架（上一版真的叠成了 `+2 已领+6`）。

**高度**：`taskLayout()` 一份清单同时驱动高度和绘制。下限从 240 降到 150 —— 240 会把只有两条内容的纸撑出 40px 空气。

**垂直位置**：从 `clamp(DH/2-268, ...)` 公式改成定值 `+20`。公式在小内容时把抽屉推到屏幕下半截；而定值在最大内容（370）时底边也只到 −165，离资源条（−290）还有 125px，本来就不需要让。

**折叠行三角用 Graphics 画**，不用 `▾` —— 靠字体兜底，缺字形就是一格方块（`♥♡` 已经踩过一次）。

### 9.3 工具：`--save` 与 `--touch2`

为了验证"已领折叠"这一态，给 `_home-rt-shot.js` 加了两个参数：

- `--save='{"claimed":["out","feed"],"runs":2}'` 覆盖任意存档字段。原来只有 `--cleared`，而任务的 claimed 态看的是 `claimed[]` 数组 —— **不改存档就永远拍不到已领状态**，等于这一整套设计没验过。
- `--touch2=fold` 在第一次点击后再点一次。折叠行是点开抽屉之后才存在的节点，`--touch` 那一下树里还没有它。
