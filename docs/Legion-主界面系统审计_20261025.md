# Legion 主界面系统审计 · 2026-10-25

> 基线：`1ef8b6d`（改造件四件套已落地）。本文全部数字来自读代码与实测，不含估算。
> 工具：`tools/_t-econ.js`（27 屏经济）、`tools/_home-rt-shot.js`（主界面渲染）、`tools/grove-shot3.js`（战斗截图）。

---

## 0. 一句话结论

**主界面 4 个系统（任务 / 工坊 / 派遣 / 出征）加起来提供的决策点 = 0。**
"存在感低"不是 UI 排布问题，是这 4 个系统**既没有"不做会输"的代价，也没有"做了要取舍"的选择**。加图标、加文字、加动画都救不了。

判定表：

| # | 用户提的问题 | 成立？ | 病根（一句话） | 我的处置建议 |
|---|---|---|---|---|
| 1 | 任务一次性的，后面不用再完成 | **成立** | 6 条任务条件全是"做过就会自动达成"，玩家零决策 | **不做周常**，改成「每趟顺路目标」（抽签制） |
| 2 | 喂饭 / 制作没意思 | **成立，且比你说的更严重** | 这是资源换算表，不是系统；饭钱只占收入 15% | **喂饭挪进出征**，工坊只留改造 |
| 3 | 派遣去干嘛了 | **成立** | 效率是战斗的 1/7，且四样产出战斗全给 | 给它**独占产出**（图纸碎片），否则撤掉 |
| 4 | 出征该汇总成一个宠物 icon | **成立，且是纯 UI 债** | 同一件事说了两遍（底部六格 vs 右边大按钮） | 六格删掉，出征位 = 大头像 + 名字 |
| 5 | 要排行榜撑成就感 | **方向对，但顺序反了** | 现在没有"可比的分数"：评级零奖励、`S.best` 只落盘不用 | 先让评级有奖励，再上本地战绩榜 |
| 6 | 芦苇把画面搞乱 | **成立，是硬 bug** | 前景杆顶到 366~484，比 462 层台面还高 96px，覆盖 68% 屏宽 | 前景立杆区收窄到最外 192px |

## 1. 任务：不该做周常，该做「顺路目标」

### 现状（代码事实）

`HomeBiz.ts:508-570`，6 条任务，`target` **全部 = 1**：

| id | 条件 | 奖励 | 会不会自动完成 |
|---|---|---|---|
| out | `s.runs >= 1` | 12 果 + 2 材 | 是，打一次就达成 |
| feed | `s.feeds >= 1` | 6 果 + 4 材 | 是 |
| craft | `s.crafts >= 1` | 8 果 | 是 |
| send | `s.dispatches >= 1` | 10 果 + 2 币 | 是 |
| pal | `s.cleared >= 1` | 20 果 + 6 材 | 是 |
| pat | 最高心 >= 1 | 15 果 | 是 |

总奖励 **71 果 ≈ 1.5 屏收入**（一屏平均 47.3 果）。`claimed` 是只增不减的数组，领完永久消失。

### 病根

不是"一次性的"，是**任务和玩法完全解耦**。6 条条件全部是"你玩着玩着就满足了"，玩家没有任何一个时刻需要因为任务改变打法。所以它读起来像新手引导的残留，不像系统。

### 我的判断：周常救不了

把 target 从 1 改成 3、加个"每日刷新"，本质只是把"自动完成一次"变成"自动完成 N 次"。玩家还是零决策，只是多了个要点红点的清单。

### 方案：每趟顺路目标（抽签制）

出门时抽 **1~2 条"本趟条件"**，写进这一趟的规则，趟结束失效：

| 类型 | 例子 | 它改变什么 |
|---|---|---|
| 禁止型 | 本趟不许用火坑 / 不许掉饱 3 次以上 | 强迫换解法 |
| 要求型 | 本趟至少一次连锁 ≥3 / 至少一只进营地 | 强迫打特定路线 |
| 携带型 | 本趟带短尾犬通关 | 让"换宠"真正有意义（现在六只只是六把武器） |
| 限制型 | 本趟球额度 −1 | 和已有的 `ballLimit` 字段复用 |

- 完不成**不惩罚**（符合"不做失败惩罚"红线），只是拿不到奖励
- 奖励给**改造碎片**（配合第 3 条派遣改职能），不给果子（果子已经通胀 6.5×）
- 成本：`SaveState` 加 `tripGoals: string[]`，进战斗前生成、结算时判。**不需要服务端**

## 2. 工坊：喂饭和制作没意思 —— 你说对了，而且比你说的更严重

### 数据（`tools/_t-econ.js`，27 屏实测）

| 项 | 数值 | 依据 |
|---|---|---|
| 单屏收入 | 47.3 果 | 达标 14 屏的范围 31~64 |
| 单屏掉饱 | 20 | `BELLY_PER_CLEAR` |
| 一顿野果 | 8 果 → +22 饱 | `MEALS.fruit` |
| **单屏饭钱** | **≈ 7.3 果** | 8 × 20/22 |
| **饭钱占收入** | **15%** | 7.3 / 47.3 |

三道菜的"每饱单价"：

| 菜 | 成本 | 饱食 | 果/饱 | 差异 |
|---|---|---|---|---|
| 野果 | 8 果 | +22 | 0.364 | 基准 |
| 热汤 | 16 果 + 1 材 | +48 | 0.333 | −8% |
| 干粮 | 1 干粮（=10 果 + 2 材） | +35 | 0.286 | −21% |

**三道菜的差别在 8%~21% 之间。** 玩家的最优解永远只有一个（做干粮吃干粮），而且这个"最优解"只省 15% 的钱。

### 病根

**喂饭不是决策，是打卡。** 饱食度这条"压力线"本来是想做"贪不贪"的张力，但：
- 饭钱只占 15% → 饿不饿都无所谓
- `feed()` 里 `if (prev.satiety >= 100) return '已经吃饱了'` → 满饱时按钮直接禁用，玩家连"要不要多吃一口"都没得选
- 制作 2 条配方（`ration` / `basket`）全是喂饭的下游

### 我的判断

**喂饭不该留在工坊里，但也不该删掉。** 它现在的问题是"位置错了"——它属于**出门前的准备**，不属于"回家后的维护"。放在工坊里，玩家每次回家都要点一次，点完就走，这就是"可玩可不玩"的来源。

**制作该砍。** 2 条配方撑不起一栏，而且干粮是喂饭的原料、篮子是一次性的。合并进改造件更划算。

### 方案

| 动作 | 内容 |
|---|---|
| **挪** | 喂饭 → 出征卡（出发前选一顿饭，给**本趟 buff**，不是单纯回饱食） |
| **改** | 三道菜变成三种本趟效果：野果（+饱食）/ 热汤（本趟首屏推球力 +15%）/ 干粮（本趟少掉一屏饱食） |
| **砍** | 制作栏撤掉。`basket` 效果并入改造件（有个改造件叫"加宽球路"，再加一个"派遣提产"） |
| **留** | 工坊只剩**改造**一栏 → 它从"5 个杂项"变成"永久成长商店"，这是唯一有存在感的东西 |

改造后工坊的定位：**进去是为了变强，不是为了打卡。**

## 3. 派遣：不是效率问题，是没有独占产出

### 数据

| 渠道 | 时长 | 产出 | 效率 |
|---|---|---|---|
| 派遣（短尾犬满 10 趟） | 10 分钟 | 40 材 + 10 干粮 | — |
| 派遣（仓鼠满 10 趟，最赚） | 10 分钟 | 60 果 + 10 币 + 20 干粮 | **10 果/分** |
| 战斗（一趟 5 屏） | ≈ 4 分钟 | 290 果 + 5 材 | **72 果/分** |

**派遣效率 = 战斗的 1/7。**

### 病根

`YIELD` 表里四样产出（果 / 材 / 币 / 干粮）**战斗全给，而且给得更多**。所以派遣在玩家眼里永远是"打不动游戏的时候才点"。

补一句历史：`HomeBiz.ts:168-177` 的注释说"把干粮接进来，派遣第一次接进了战力那条链"——这个方向是对的，但它只解决了"派遣的产出有没有用"，没解决"为什么不用战斗拿"。

### 方案（三选一，需要拍板）

| 方案 | 内容 | 代价 | 我的评价 |
|---|---|---|---|
| **① 独占材料（推荐）** | 新增「图纸碎片」，**只能派遣获得**；4 件改造件要碎片才能装 | 改造件价格要重算 | 把派遣和唯一的永久成长线绑死。不破坏战斗节奏 |
| ② 替你打一屏 | 派遣期间随机推进一屏 | 破坏 27 屏进度节奏，玩家会挂机等 | 不推荐 |
| ③ 探索发现 | 带回新场景 / 新菜谱 / 图鉴条目 | 内容量成本高（1 人做不出） | 降级为待定 |

同时把"只能派 1 只"这个限制**保留**（红线：一宠出征）。

## 4. 出征：同意合并成一个 icon，而且 icon 确实画错了

### 现状（`_t-home.png` 实测裁图）

底部 `Dock` 是 6 个 **47×72** 的小格，内容是：

- 头像 28×28，tint `(126,112,98)` + 父节点 `UIOpacity 140` → **一坨灰圆片，没有边框没有底色**
- 一个锁
- 一个药丸标签，写着「差2关 / 差5关 / 差9关 / 差14关 / 差18关」

而右边已经有一个大按钮：**「出门 · 带尖耳猫 · 溜溜球 · 饱食100」**。

**同一件事说了两遍，两遍都不是"出征"。** 底部在说解锁进度（那是图鉴的活），右边在说带谁出门（那才是出征）。

### icon 为什么没显示对（`_t-crop-post.png` 实测）

左侧木牌链是背景图里的水彩立牌，「任务」那块钉着一个米白椭圆 + 13px 深棕字，很贴。

但「工坊」那块：**一张 44×44 的纯白圆角方块把整块木牌盖死了**，方块里是一个深棕色小图标（`icons['pot']`），下面再挂一个小药丸「工坊」。

- 来源：`paintHomeBadge()`（`HomeRuntime.ts:1299`）把 `Badge-工作台/ico` 的 spriteFrame 换成 `pot`
- 病根：`ico` 节点的**尺寸和位置是场景里定的**，没人按木牌重新量过。木牌牌面只有 79 宽，「任务」的椭圆是 54×26，而 `ico` 是 44×44 的白色方底 → 视觉上比牌面还大，直接把木牌吃掉
- 同类问题：`drawFgPebble` 那种"运行时 new 一层贴上去"的做法，只要不重新量场景像素，就一定会错位

### 方案

| 动作 | 具体 |
|---|---|
| **删** | `Dock` 六格整组移除（解锁进度已经在图鉴里，且 `tag` 现在显示的就是"差N关"） |
| **建** | 出征位 = 圆形头像 **96×96**（`grove/head`，原色，不压暗）+ 名字 22px + 「出发」按钮 |
| **点** | 点头像 → 选人面板（6 只一行，带锁 + 差N关 + 招式名），和派遣面板同一套行组件 |
| **修 icon** | 木牌图标改成 **26×26、透明底、木牌牌面正中**；或者干脆删掉图标只留「工坊」两字（牌子本身已经够识别） |
| **顺便** | 派遣那块白卡（v3）同理重量，别再用"看起来对"的坐标 |

## 5. 排行榜：方向对，但顺序反了

### 硬约束（必须先说清）

**这个项目零后端。** 真排行榜需要服务端聚合或平台（微信/Steam）的好友榜 SDK。现在做不了。

### 更关键的问题

排行榜是**成就感的放大器**，它的输入是"可比的分数"。而现在：

| 事实 | 出处 |
|---|---|
| 评级 S/A/B **零奖励**，只落盘 | `grove.html` `S.best` 只用于挑一屏显示 |
| 没有"总分 / 总星"这种可比较的单一数字 | 未实现 |
| 结算卡不显示"本屏最佳" | 未实现 |

**给一个没有分数的游戏加排行榜，等于给空账本做封面。**

### 正确顺序

| 步 | 做什么 | 为什么必须在前 |
|---|---|---|
| ① | 评级给奖励（S 给改造碎片 / A 给材料） | 让"打得好"第一次有回报 |
| ② | 算出「总星数」（27 屏 × 3 档）当主指标 | 排行榜需要一个单调可比的数 |
| ③ | 本地战绩榜：总星 / 全 S 屏数 / 单屏最快时间 / 单屏最高连锁 | 纯本地，零服务端，今天就能做 |
| ④ | 上平台后再接好友榜 | 依赖平台 SDK |

### 明确不做

**假 AI 排行榜**（伪造对手数据、伪造排名）。玩家一旦发现对手不存在，信任归零，而且违反"不做空话"。

## 6. 画面乱：实测定位到三个具体数字

### 截图证据

`_t-s23.png`（芦苇荡）：左侧两根近黑色粗杆从地面竖到半空，右侧同样，**把左侧平台和敌人挡掉一半**。
`_t-s20.png`（浮浮台）：底边一排泥堆 + 碎石 + 芦苇根，和蓝色水塘、球混在一起，**球在哪一眼找不到**。

### 病根（`grove.html:9064-9107`）

```js
const h = 116 + hash(k * 5.3) * 118;   // 116 ~ 234
g.moveTo(px, H + 4);                    // 从 y = 604 起
// tipY = H - h = 600 - h  →  366 ~ 484
```

| 量 | 值 | 对照 |
|---|---|---|
| 杆顶 y | **366 ~ 484** | 球顶 534 / 462 层台面 |
| 比 462 台面高 | **96px** | — |
| 允许立杆的判定 | `edge > FG_EDGE_MIN(0.30)` | `px < 336` 或 `px > 624` |
| **立杆覆盖宽度** | **652 / 960 = 68%** | — |
| 杆粗 `lineWidth` | 4.6 | 球半径 11，**粗 42%** |
| 杆色 | `hexDim(TH.shrub, 0.55~0.60)` 再混 28% | 近黑 |

注释自己写着"中段不立杆"，但 `FG_EDGE_MIN = 0.30` **只保护了屏幕中间 30%**，两侧 68% 全部可以竖到比台面还高。这是"设计意图"和"实现参数"不一致，不是审美分歧。

cliffs 族同样问题：`hi = 466 + hash * 52` → 岩石顶 **466~518**，也在球道之上。

### 修法（具体数值）

| 项 | 现在 | 改成 | 理由 |
|---|---|---|---|
| 立杆判定 | `edge > 0.30`（= 68% 屏宽） | `px < 96 \|\| px > W - 96`（= 20% 屏宽） | 高杆只做"框景"，不做主体 |
| 杆顶上限 | 366 | **504**（`GROUND_Y - 52`） | 在 462 台面之下 42px，不挡平台 |
| 杆粗 | 4.6 | **3.2** | 小于球的 1/3 |
| 杆透明度 | 1.0 | **0.55** | 前景该"压暗"，不是"变黑" |
| 中景芦苇间距 | 11px | **22px** | 一半密度 |
| cliffs 岩石顶 | 466~518 | **504 封顶** | 同上 |

**判据（可测）**：改完后跑 `grove-shot3.js s20 s23 s12`，人工确认三件事：
1. 462 台面完整可见，没有杆穿过
2. 球在任何位置都能一眼找到（球顶 534 以上不能有前景遮挡）
3. 出生点两侧 60px 内没有高于 520 的东西（现在 `fgBlocked` 只挡了 ±46）

## 7. 执行顺序建议

按"见效 / 成本"排序，**每步都可独立上线**：

| 序 | 任务 | 成本 | 见效 |
|---|---|---|---|
| **P0** | 修前景遮挡（第 6 条，纯数值） | 小（改 6 个数字 + 复测 3 张图） | **立刻**，画面可读性直接回来 |
| **P1** | 出征位合并成一个 icon + 修木牌 icon（第 4 条） | 中小（删一组节点 + 建一个面板） | 高，主界面第一眼就变 |
| **P2** | 评级给奖励 + 总星数 + 本地战绩榜（第 5 条 ①②③） | 中（结算卡 + 一个新面板） | 高，补"成就感"的根 |
| **P3** | 任务改「每趟顺路目标」（第 1 条） | 中（存档字段 + 生成 + 判定） | 中，但要 P2 的奖励体系配合 |
| **P4** | 喂饭挪进出征 + 砍制作（第 2 条） | 中大（改面板 + 改数值口径） | 高，但要重跑经济探针 |
| **P5** | 派遣改独占产出（第 3 条） | 中（新资源 + 改造件定价重算） | 中，依赖 P4 |

**P0 和 P1 可以今天就做，都是 UI/数值，不动玩法架构。**
