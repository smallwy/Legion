# Legion 动效路线与性价比

> 版本 v1.0 · 2026-10-24 · 依据 `GroveBattle.ts` / `grove.html` / `HomeRuntime.ts` 源码实读
> 问题：后续要做骨骼动画丰富动效，怎么性价比最高

---

## 结论先行

1. **你想要的是"动效丰富"，骨骼只是其中一种手段 —— 而且在这个项目里是投入产出比最差的那一种。** 真正缺的不是骨骼，是"UI 会动 + 角色腿会动 + 打中有反馈"这三件便宜事。
2. **战斗画面在 DOM canvas 上，不在 Cocos 渲染树里** —— `GroveBattle.ts:313-314` 把 `document.createElement('canvas')` 直接挂到 `document.body`。这决定了 `sp.Skeleton`（Spine 的 Cocos 组件）**接不进战斗**。想在战斗中上 Spine，只能先预渲染成 PNG 序列再 `drawImage`。
3. **最高性价比路线是"分层 + 代码驱动"（穷人的骨骼）**：把敌人贴图切成 `身体 / 前腿 / 后腿` 三块，用**已有的三段相位**驱动腿的位移。不需要生成新图、不需要新接口、约 30 行代码，就能根治"走路像平移"。

---

## 一、硬约束（先搞清哪里能用 Spine）

```
Cocos 场景树                            战斗画面
├ Home.scene（节点树）                   └ DOM canvas（body 直挂）
│  ├ 可以挂 sp.Skeleton  ✓                 ├ 只能 drawImage / canvas API
│  └ 但主界面宠物只有 96px 高              └ sp.Skeleton 完全用不上 ✗
└ Battle.scene —— 记忆里的硬结论：
   「别走 Cocos 2D 渲染」（render-root-2d 要求 RenderRoot 下，
    camera.visibility 默认排除 UI_2D，两次黑屏事故都是这条）
```

| 想在哪用 Spine | 可行？ | 原因 |
|---|---|---|
| 战斗内的宠物 / 敌人 / BOSS | **否** | 画面是 canvas，不是节点树 |
| 主界面宠物待机 | 可以（要装 spine 扩展包 + 资源） | 节点树可用，但 96px 高的小图收益有限 |
| 结算页 / 图鉴大图 / 宣传图 | 可以 | 一次性演出，不占运行时预算 |
| 战斗内但预渲染成序列 | **可以** | Spine Editor 导出 PNG 序列 → `drawImage` |

## 二、五条路线对比

| # | 路线 | 单角色成本 | 运行时开销 | 效果上限 | 推荐度 |
|---|---|---|---|---|---|
| L1 | **分层 + 代码驱动**（身体/腿切开，相位驱动位移） | **0.5 人日**（切图补像素 + 30 行） | 极低 | 腿真的在动，Q 版足够 | ★★★★★ |
| L2 | **序列帧 2~3 帧**（AI 生成 + 对齐 + 相位切帧） | 1 人日/角色（生成一致性是难点） | 低（3 张图） | 比 L1 高，能带形变 | ★★★★ |
| L3 | 程序化形变（**现在用的第五版**） | 已付 | 极低 | 有天花板 —— 单张静态图做不出腿 | ★★★ 补足 |
| L4 | Spine 预渲染成 PNG 序列 | 2~3 人日/角色（分层重绘 + 绑定 + 调曲线 + 导出） | 低 | 很高 | ★★★ 只给 BOSS |
| L5 | Spine 运行时 `sp.Skeleton` | 3~5 人日/角色 + 扩展包集成 | 中 | 很高 | ★★ 只主界面/结算 |

**L1 + L3 组合是当前最优解**：L1 解决"腿"，L3 保留"身体形变"，两者共用同一套相位机，不打架。

## 三、落地顺序（按周，每步都能单独验收）

| 阶段 | 内容 | 工时 | 为什么排这里 |
|---|---|---|---|
| **W1** | **UI 动效**：卡片进/出（缩放 + 淡入 0.18s）、按钮弹性（按下 0.97 → 回弹 overshoot）、数字滚动（果子变化 0.3s 递增）、任务可领徽标脉冲 | 1 天，**零美术** | 全是代码，不用美术资源。玩家感知最强，因为它每秒钟都在看 UI |
| **W2** | **敌人分层腿动**（L1）：4 种小怪切图 + 驱动 | 2 天 | 根治"走路像平移"，这是你提过四次的问题 |
| **W3** | **战斗反馈动效**：受击闪白 2 帧、球滚动拖尾、糊层时粒子、击杀时金币飞向 HUD | 2 天 | 手感。同样零美术（程序化绘制） |
| **W4** | 宠物待机 3 帧（L2）+ BOSS 4 帧 | 2 天 | 待机是"活着"的信号 |

## 四、L1 具体怎么做（零接口改动）

### 4.1 素材：切图不生成图

```
foe-boar.png（现有一张静态朝右图）
  ↓ 手工 / 脚本切成三块
foe-boar_body.png   身体（含头、壳、背）
foe-boar_legL.png   后腿（近侧）
foe-boar_legR.png   前腿（远侧）
```

**要补的像素**：腿在身体下方，抬起时露出的被遮部分。Q 版敌人腿是两条短粗色块，用腿的主色 + 一点暗部补 3~5px 即可，不需要重新画。
**命名约定**：`<原键>_legL` / `_legR`，缺任一块就自动退回单图（保底不崩）。

### 4.2 代码：复用已有的三段相位

`drawFoe` 里现在的关键几行（第五版步态）：

```js
const cyc = (t/stepT + ph0) % 1;
const stretch = cyc < 0.34 ? smoothstep(cyc/0.34)      // 伸
              : cyc < 0.50 ? 1 - smoothstep((cyc-0.34)/0.16)  // 缩
              : 0;                                     // 顿（完全静止）
```

在这套相位上叠腿即可，**不要另起一个周期**：

```js
// 顿（cyc>=0.5）时 stretch=0 → 腿位移自动归零 → 天然有"踏步间隔"
const swing = Math.sin(cyc * Math.PI * 2) * stretch * 3.2;   // ±3.2px
legR_dx =  swing;
legL_dx = -swing;
legR_dy = -Math.max(0, swing) * 0.6;   // 前腿抬起时离地一点
```

关键：**腿位移必须乘 `stretch`**。不乘的话顿的那半秒腿还在动，等于把"一半时间静止"这个好不容易调出来的节拍又破坏掉。

### 4.3 贴图通路：不需要改 `groveSetArt` 签名

现在 `groveSetArt(key, img)` 只存单张。**加序列/分层不需要改它** —— 直接用命名约定多注入几个 key：

```js
// GroveBattle._loadArt 里多加载三个路径
groveSetArt('foe-boar', imgBody);
groveSetArt('foe-boar_legL', imgLegL);
groveSetArt('foe-boar_legR', imgLegR);
```

`drawFoe` 里：

```js
const body = artOf('foe-' + f.kind);            // 现有单图，保底
const legL = artOf('foe-' + f.kind + '_legL');  // 没有就 null
if (!legL) { /* 走现有单图逻辑，一行不改 */ }
```

**这条"有图升级、无图回退"的约定已经验证过**（ART 表空着就走代码图形），照抄即可。

## 五、帧数经济学：2 帧就够读出走路

| 帧数 | 能表达 | 建议 |
|---|---|---|
| 1 帧 + 形变 | 抖动、呼吸、蠕动 | 现在的第五版，已达上限 |
| **2 帧**（伸 / 缩） | **走路、爬行、跑** | 小怪的性价比甜点，配合"顿"相位就是三步态 |
| 3 帧（+ 过渡帧） | 更顺滑，能带抬腿姿态 | 宠物待机、BOSS |
| 6~8 帧 | 完整循环、能带轮廓变化 | 演出用，战斗内不必要 |

**不要做 8 帧**：`grove.html` 是单文件原型，每帧都是 `ART` 表里的一个 Image，4 种敌人 × 8 帧 = 32 张图在内存里。2 帧 × 4 种 = 8 张，加 BOSS 4 帧共 12 张，可接受。

## 六、如果坚持要 AI 生成序列帧，一致性怎么保证

这是实操最大的坑 —— 每次生成腿的位置、身高、配色都会漂。三种做法按可靠性排序：

| 做法 | 一致性 | 成本 | 说明 |
|---|---|---|---|
| **A. 局部重绘（inpaint）** | ★★★★ | 低 | 锁定原图，只框选"腿部区域"重绘成另一个姿态。身体像素完全不动 → 拼接零缝 |
| **B. 图生图 + 固定 seed + 低重绘强度** | ★★★ | 低 | 整图重跑，靠低 denoise（0.25~0.35）锁形。仍会漂 1~2px，需要脚本对齐 |
| **C. 分别生成再手工对齐** | ★ | 高 | 别做。身高会差 3~5%，读作"换了一只怪" |

**必须做的校验**（脚本，30 行）：两帧按主体 bbox 对齐后，**身体区域像素差应 < 3%**。超了就是漂了，重生成。

## 七、什么情况下才真的值得上 Spine

三条同时满足才做：

1. 这个角色**有 3 个以上差异极大的动作**（idle / walk / attack / hit / die）—— 序列帧做 5 个动作要 10 张图，Spine 一套绑定全包；
2. 它**在主界面或结算页**（节点树可用），不在战斗 canvas 里；
3. 它是**招牌角色**（六宠之一或最终 BOSS），玩家会盯着看 3 秒以上。

**当前项目一条都不完全满足**：战斗内用不了、六宠正面立绘做走路只能原地踏步（正面视角的骨骼旋转会变成人字形劈叉，这是已知硬限制）。所以**现阶段不建议上 Spine**。

要做的话，唯一合适的切入点是：**结算页的六宠出场演出**（一次性、可控、无运行时约束、正面视角允许原地踏步 + 重心横移 + 眨眼 + 耳朵摆）。
