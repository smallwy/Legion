## 一、宠物为什么只解锁一只

**结论：不是解锁条件太苛刻，是三条链路同时断了。** 你在 grove.html 里其实 6 只都能选，主界面只是读不到成绩。

### 1.1 解锁条件本身还是 8 关时代的表

```
grove.html:11792   const UNLOCK_AT = { cat: 0, dog: 1, ham: 3, rab: 5, ox: 7, fox: 8 };
config/Roster.ts   PETS[] → at: 0 / 1 / 3 / 5 / 7 / 8
```

两边数字一致（这点没问题），但表是按 **8 关** 设计的：打满第 8 关就全解锁。现在 27 屏，这套节奏等于「前 8 屏送完 6 只，后 19 屏一只都不送」。

### 1.2 两份存档、两个 key、两种数据类型（这是主因）

| 谁 | key | `cleared` 类型 | 含义 |
|---|---|---|---|
| grove.html | `pawpack.save` | **数组**（关卡索引） | 通过了哪几屏 |
| 主界面 HomeRuntime | `pawpack.save.v1` | **数字** | 通了几屏 |

跨过去的唯一通道是 `GroveBattle._syncProgressToHome()`（GroveBattle.ts:438），它只存在于 **Cocos 战斗里**。

**在浏览器直接打开 grove.html 玩，这个同步永远不会发生** —— 主界面读到的 `cleared` 恒为 0，`unlockedPets(0)` 只返回砂糖一只。这就是「一直只有一只」的直接原因。

### 1.3 主界面文案与节点还写死 8

```
HomeRuntime.ts:1094   txt.string = `${s.cleared} / 8 关`
HomeRuntime.ts:3158   `已通 ${cleared} / 8 关`
HomeRuntime.ts:1101   for (let i = 0; i < 8; i++)   // pip-0..pip-7，只有 8 格
```

即使 `cleared` 正确同步成 10，进度仍显示「10 / 8 关」，9、10 两屏的点无处可放。

### 1.4 两头对「出征」的定义不一样

- **grove.html 门口**：`pickHero(i)` 只校验 `i < HEROES.length`，**零解锁校验**，6 只随便点。
- **主界面**：按 `cleared >= at` 判，锁定槽显示「差 N 关」。
- **出征人数**：推球模式锁死 1 只（宪法 v2.0「一宠出征，六宠看家」），但出门按钮副标题写的是 `squadSize()`，那是割草时代 `MAX_SQUAD = 3` 的遗留，会写出「3 只」。

**所以「无法出征」的真相是：主界面没给你那只，grove 门口其实一直能选。**

## 二、多宠物共享关卡还是各自独立

**结论：共享一条线。** 关卡是全局 `LEVELS` + 全局 `S.progress`，换宠物只改 `S.heroIdx`（技能 / 体型 / 速度），进度不受影响。

这是**对的**，不要改成各自独立：宪法 v2.0 明确「一宠出征，六宠看家」，六只的差异应该在**打法**，不在**进度**。

但现在有个真问题：**六只只是六把武器，不是六个角色。** 除了 `w`, `h`, `spd`, `jump`, `atkCd` 和 `fire()`，六只在关卡里没有任何专属互动。玩家换宠物得到的反馈是「技能变了」，不是「这一趟不一样」。

要补的不是进度分叉，是**每只对地形/目标的专属反应**（例：长耳兔跳更高能上别人上不去的台；胖仓鼠滚得慢但能扛泥坑）。这是内容层，可以后置。

## 三、27 关太长 + 目标卡重叠

### 3.1 编号口径抹掉了章节（**这是「太长」的真正来源**）

内部分了 3 个产地：

```
grove.html:9837   const FACTIONS = [苔原, 枯木坡, 泥沼]   // 每产地 9 屏
```

但 HUD 只报一种口径：

```
grove.html:8950   const label = "第 " + (S.stage + 1) + " / " + n + " 关   " + curStage().name;
```

截图里那屏是**第 10 屏**，实际是**枯木坡第 1 屏**，却显示成「第 10 / 27 关 枯木坡口」。

**玩家读到的永远是「一条 27 长的直线」，章节感被这个数字抹掉了。** 27 屏本身不长（3 产地 × 9 屏，和一本书三章没有区别），长的是这个编号方式。

改法（不动任何关卡数据，只改 HUD 文案与点的分组）：

| 位置 | 现在 | 改成 |
|---|---|---|
| HUD 标题 | 第 10 / 27 关 | **枯木坡 · 1 / 9** |
| 顶部进度点 | 27 颗一条 | **当前产地 9 颗**，跨产地才整条替换 |
| 全局 27 | 常驻 HUD | 只在「挑一屏」面板里出现 |

### 3.2 目标卡与进度点是**真的几何重叠**（不是观感）

```
grove.html:8942   const gap = 22;                 // 写死
                  total = (27 - 1) * 22 = 572
                  进度点横跨 x = 194 … 766，y = 35…55
grove.html:9480+  panelBg(g, "ui-cream", W - 288, 14, 272, 130)
                  → 目标卡 x = 672 … 944，y = 14 … 144
```

**重叠区 x 672…766 = 94px，y 35…55 = 20px。** 截图上右边那排点被奶白卡片盖掉，就是这个。

换成「当前产地 9 颗」后：9 颗 × 22 = 176px，居中在 392…568，离卡片左边界 672 还有 **104px 余量** —— 顺带把重叠也解决了。

目标卡本身 272×130 也确实偏大（占右上 272×130，接近屏幕的 6%）。可以缩到 236×112，但**先解决重叠，再谈缩尺寸** —— 尺寸是可以商量的，压字是不能接受的。

## 四、三个具体 bug

### 4.1 蘑菇为什么让球乱跳

```
grove.html:4113-4127
  b.bounceCd = Math.max(0, (b.bounceCd || 0) - dt);
  if (b.bounceCd <= 0) {
    for (const bo of BOUNCERS) {
      if (Math.abs(b.x - bo.x) > 30) continue;
      if (b.y < bo.y - 60 || b.y > bo.y + 10) continue;
      b.vy = -980;                                    // ① 写死，不是加法
      if (Math.abs(b.vx) < 180) b.vx = (b.vx < 0 ? -1 : 1) * 200;   // ② 强改方向
      b.onGround = false;
      b.bounceCd = 0.35;                              // ③ 太短
```

三个原因叠加：

1. **`vy = -980` 是赋值不是累加** → 每次弹起高度固定 229px，永远不会衰减。
2. **`bounceCd = 0.35` 挡不住二次触发**：弹到顶点 0.5s、落回 0.5s，一个来回 1 秒。球落回同一朵菇上立刻再弹，**无限上下循环**。
3. **`b.vx` 被强行改成 ±200**：慢球经过菇时水平速度被覆写；`vx` 正好接近 0 时，符号由浮点残留决定 → 方向随机。玩家看到的就是「球突然往反方向窜」。

另外一个文案错：`wither_shrooms` 的 `sub` 写「**三朵菇** · 连弹上三层」，`bouncers` 数组实际只有 **2 朵**（x=200 地面 / x=520 在 462）。

**修法**（不动数值手感）：弹起改累加 + 衰减上界、冷却加到 0.7s、`vx` 改为「保方向、只补最小值」而不是覆写方向、同朵菇连续触发 2 次后冷却翻倍。

### 4.2 「球不撞火就不会消失」

这是**当前规则的真实后果**，不是错觉。球只有四条出路：

| 出路 | 结果 | 人怎么办 |
|---|---|---|
| 火坑 | 球消失，收成 ×2 | **真消灭** |
| 水塘 | 球消失 | `respawnPacked()` 吐回场上 |
| 营地 | 结算 | 收工 |
| 滚出屏幕（左） | 球消失 | `respawnPacked()` 吐回场上 |

```
grove.html:4467-4485   // 火坑：唯一净消灭
grove.html:4490-4510   // 水塘：vy > 240 才沉，沉了人放回
grove.html:4217        // 出屏：respawnPacked(b, 1, WALL_L + 46)
```

**火坑是唯一能把人从场上抹掉的通道。** 其他终点都把人放回来了。所以「球不撞火就不消失」在逻辑上完全成立。

这原本是设计（火坑收成翻倍 = 冒险的回报），但代价是：**不贪火的玩家做的事全是无效功**，球在场上越滚越多。

### 4.3 左下角撞下去单位会重生 —— **是我写的，故意的，但我判断错了**

```js
// grove.html:4211-4222
if (b.x + b.r < -4) {
  b.dead = true;
  S.stat.lost = (S.stat.lost || 0) + 1;
  const back = respawnPacked(b, 1, WALL_L + 46);   // ← 人放回 x=72
  for (const f of back) S.foes.push(f);
  addText(72, GROUND_Y - 110, "滚出去了…", "#CBD8E8", 18);
```

原注释写的理由是：

> 「滚丢要给人一个交代：装在里面的人放回场上。直接 dead 的话玩家看到的是「莫名其妙少了两只」，那会读成 bug。」

**这个判断被你的实测推翻了。** 当时的顾虑是「球没了人也没了 = 玩家不知道发生了什么」，但玩家实际读到的是「我把它撞下去了，它又活过来了」—— 这比「少了两只」更像 bug，因为它违反了因果。

正确做法不是「放回」也不是「静默消失」，是**给出方向明确的代价**：球滚出左侧屏幕 = 这一球白推，里面的人**掉到场上更低的位置重新裹壳**（而不是原地满血复活），并在 HUD 对应位置挂一次明确损失提示。要么就干脆让左端封口（那是另一套方案）。
