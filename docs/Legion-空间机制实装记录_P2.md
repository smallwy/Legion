## 0. 结论先行

| 项 | 结论 |
|---|---|
| P1 为什么"没感觉" | 材质和板改的是**球怎么滚**，而 27 屏的核心动作仍然是"往右推、落袋、完事"。手感没变，只是同一件事的摩擦系数变了。 |

## 1. 核心判断：先把"球能不能飞"查清楚

这是本批最值钱的一条，也是上一批没查的东西。

实测（`predictBall` 满力 1209，第 7 屏）：

```
起点 (500, 556) →
  500/556  520/556  578/556  595/514  580/471  566/437  551/412
  536/397  521/391 ← 最高点  506/395  491/407  476/429  461/461
  447/462 ← 落到 462 层上  432/462  417/462 ... 357/463 → 掉到左边
```

结论有三条：

1. **满力确实能上 462 层**（上升 165px），板是有效的。
2. **但球在层上会一直往左滚** —— 反射后 `vx` 必然是负的（板是 `/` 形，法线朝左上）。
3. 球往左滚到层左端掉下去 → 落到左边水塘溺死。**"打上去了"和"没打上去"结局一样。**

第 3 条是 P1 的遗留缺陷，记进待办（见 §6）。

**关键推论**：想在空中放环让球穿过，在这个物理里是做不到的。任何"空间目标"都必须**贴着台面**设计。

## 2. TOUR 的数据结构

```js
tour: [
  { x1: 240, x2: 700, y: 350 },   // 段 1：350 层，往右
  { x1: 600, x2: 790, y: 462 },   // 段 2：462 层，往右
]
tourNeed: 2                        // 需要几颗球走完
```

- 一段 = 「在高度 `y` 上、x 落在 `[x1,x2]` 内」。
- 判定：`|球y − 段y| ≤ 12 && x1 ≤ 球x ≤ x2`，**必须按顺序**（游标存在球上 `b.tour`）。
- 顺序不能省：不按顺序的话，球在场地里随便滚两圈就把所有段碰一遍，"路线"就不存在了。
- `x1/x2` 一律取 `min/max`，不假设"小的写前面"—— 写反就让整段静默失效，这种错没人查得出来。

### 赛道是「附加约束」，不是第七种目标

第一版把第 5 屏的 `goal: "bank"` 直接改成 `goal: "tour"`，结果：

- 冒烟里 `findIndex(s => s.goal === "bank")` 返回 −1 —— **全游戏只有这一关是落袋关**；
- `forceClear()` 因为 `checkGoal()` 为 false 而推不动关卡，连锁打挂"肚子/倍率跨关"两条断言。

改成附加约束之后，两边都对：

```js
// checkGoal
if (TOUR.length && S.stat.toured < (st.tourNeed || 1)) return false;

// goalProgress：包一层 _goalBase()，末尾追加
r.text += " · 赛道 " + S.stat.toured + "/" + need;
if (S.stat.toured < need) r.done = false;   // ← 不许"进度条全绿却过不去"
```

**这条设计的可复用性**：任何一关都能挂一条路线要求，不用为它单开一种 goal。

## 3. 第 5 屏「弹菇」的赛道

几何（原有，未动）：地面 556、462 层 160..800、350 层 200..734、248 层 320..614；
弹菇在 (200, 地面) 和 (560, 350)；营地 830。

路线是一条**「之」字下降**：

```
地面弹菇(200) 弹起 229px
  → 落到 350 层  → 往右滚到 734 右端掉下去   【段 1】
  → 落到 462 层  → 往右滚到 800 右端掉下去   【段 2】
  → 落到地面     → 营地 830
```

- 起点**要用弹菇**：球在 350 层以外造出来，上不去 350 层（球不会跳）。所以"怎么开始这条路"本身就是一道题。
- **段 2 从 600 起、不卡 740**：球从 350 层掉下来带着水平速度，落点随推球力度前后飘 ±140px。卡死在 740 的话，推轻一点球落在 700 就"没进赛道"，玩家看不出为什么。

### 实测（`predictBall`，第 5 屏）

| 起点 | 力度 | 走完段数 | 结局 |
|---|---|---|---|
| 350 层 x=250 | 基准 620 | **2** | expire（球寿命到了，没进营地） |
| 350 层 x=250 | 满 1209 | 1 | stump（撞 350 层的木桩 650） |
| 248 层 x=400 | 满 | 1 | camp（落袋） |
| 462 层 x=200 | 满 | **0** | fire |

第二行是这一屏的**关卡设计核心**：满力推反而走不完 —— 球撞上 350 层的木桩就停。**力度本身是空间决策的一部分。**

## 5. 踩到的坑

### 5.1 `pr.text` 从来没被画出来过

`goalProgress()` 返回的 `text` 字段，**HUD 一处都没用**（只用 `cells` / `filled` / `frac` / `inner`）。
所以我第一版加的 `r.text += " · 赛道 0/2"` 完全不会显示 —— 玩家看到的是"一个普通落袋关地上多了几块发光地板"。

修法：在进度条右侧的空白里单独画。位置是量出来的（豆子 5 颗右端在 `BX+207`，卡片可用 272，`赛道 0/2` 约 54 宽 → 左端 `BX+218`，不撞）。

**教训**：`goalProgress()` 的返回值字段有两组消费方（HUD 画、冒烟读）。改文案时以为"写进去就会显示"，是这套代码里最常见的一类假通过。

### 5.2 探针里 `P.PUSH_BASE` 是 undefined

`pow` 传 `PUSH_BASE * 1.95` 时，`PUSH_BASE` 未导出 → `NaN`；而 `predictBall` 里写的是
`let vx = dir * (pow || PUSH_BASE)` —— **`NaN` 是 falsy**，于是静默退化成基准 620。

表现：满力推球只上升 40px，看上去像"板有问题"，实际是测试参数没生效。查了三轮才定位。

修法：导出 `PUSH_BASE` / `PUSH_RUN`，测试一律按 `PUSH_BASE * (1 + PUSH_RUN)` 算，不写字面量。

### 5.3 球的 `y` 语义在预测/实跑之间不一致

`updateBalls` 里球的 `y` 是**底边**（坑用 `y >= pit.y - 8` 判），而 `predictBall` 的 `pts` 存的是 `y - r`（视觉路径点）。
写测试时拿 `pts` 的 y 去对台面高度会差 22px。**判定用内部 `y`，画图用 `pts`，两者不能混。**

## 6. 待办

### P1 遗留（必须先修）

**第 7 屏的板把球送回左边送死。** 反射后 `vx` 必然是负的（`/` 形板法线朝左上），球在 462 层上往左滚到底 → 掉进 240..320 的水塘。「打上去了」和「没打上去」结局一样，正反馈消失。

三个候选（按可行性排序）：
1. **把水塘挪到 380 左边之外**，让球从层上掉下来落在干净地面，靠"左墙反弹 → 往右滚"回营地（需实测 1.6 秒寿命够不够走完）；
2. 462 层加一道**单向阀**（N6），只允许球从右往左进、从左往右不许出；
3. 接受"板是陷阱"，把视觉箭头改成朝下的"危险"语义 —— 最差，因为它把机关降级成障碍物。

### 本批之后

- **N3 承重 / N4 双层门 / N6 单向阀 / N5 流场**（原始提案里的四个原语）；
- 赛道扩到 3~4 屏，形成"每个产地一条路线"的节奏；
- 触屏 / 键盘之外，验证赛道在低端机上的判定稳定性（`|Δy| ≤ 12` 是按 60fps 定的）。
