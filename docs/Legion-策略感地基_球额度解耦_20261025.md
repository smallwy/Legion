> 日期：2026-10-25

> 范围：`client/prototype/grove.html` 规则层 + 第 2 屏；地形几何**未动**

## 0. 结论先行

| # | 结论 | 依据 |
|---|---|---|
| 1 | **没有策略，不是机关太少，是规则结构不允许权衡。** | 7 种目标互斥单选，一屏只考一件事；`ballBudget` 写死 `goal !== "limit" → Infinity`，于是「球不够」也只能当目标，不能和「火坑双份」叠在同一屏。**约束和价值差永远不相遇。** |
| 2 | **球免费时，「一球卷多只」在数学上是亏的。** | 落袋给 `holds+1`：1 只落袋 2 分，3 只卷一起落袋只有 4 分。拆开推永远更赚 → 玩家没有任何理由读地形 → 坡/滑道/缺口全部退化为背景。**这是"空间设计感为零"的数学原因。** |
| 3 | 改一条规则（额度降级为关卡字段）之后，**地形第一次成为必读项**。 | 第 2 屏 8 只敌人 / 5 颗球，实测地形支持单球卷 3；4 颗球只清到 7/8，5 颗刚好。**不卷一定清不完。** |
| 4 | 地形**一句没改**，因为问题不在画。 | 27 屏的地面骨架确实全是一整条平地（见提案 §1.1），但只要球免费，"断裂/落差"只会变成更好看的解法。**先让资源稀缺，空间才有意义。** |

## 1. 证据：为什么「玩不明白」

### 1.1 目标结构：单选题

```
clear / limit / chain / bank / collect / tour / intact / nohit
```

八种目标，`checkGoal()` 是 `if/else` 链 —— **一屏只能过一种**。这带来两个后果：

| 后果 | 表现 |
|---|---|
| 「球有限」不能和别的目标共存 | 只有 4/27 屏有额度，而且那 4 屏除了"省球"什么都不考 |
| 「火坑双份」不能和别的目标共存 | `collect` 5 屏，但球免费 → 可以反复试 → 火坑只是顺路 |

**策略 = 有约束的选择。** 约束和价值差被结构性地分到不同屏，玩家就永远不需要权衡。

### 1.2 球免费 → 拆分最优 → 地形无用

落袋：`food += b.holds + 1 + (boss ? 12 : 0)`
火坑：`food += b.holds * (boss ? 14 : 2)`

| 送法 | holds | 落袋得 | 火坑得 |
|---|---|---|---|
| 1 只单独推 | 1 | **2** | 2 |
| 3 只卷一起 | 3 | 4 | **6** |

球免费时，把所有敌人拆开单独推（各得 2）比卷成一颗（得 4）**多赚 50%**。
所以「一球卷多只」不是技巧，是**亏本操作**。

而「卷多只」是这个游戏唯一需要读地形的行为 —— 它被数值反向激励了。
第 4 屏那条 494 长坡（注释里号称"一球滚到底的成就感"）在旧规则下是**负收益**。

## 2. 改动

### 2.1 额度降级为关卡字段

```js
// 旧
function ballBudget() {
  const st = curStage();
  if (st.goal !== "limit") return Infinity;   // ← 只认 limit 目标
  return Math.max(0, st.ballLimit - S.stat.made);
}

// 新
function ballBudget() {
  const st = curStage();
  if (st.ballLimit == null) return Infinity;  // ← 认字段本身
  return Math.max(0, st.ballLimit - S.stat.made);
}
```

对称改一处：死局判负从 `goal === "limit"` 改成 `ballLimit != null`
—— 否则"新目标 + 额度"的屏会卡在「造不出球，也不能结束」。

老四屏 `limit` 行为**完全不变**（它们本来就带 `ballLimit`）。

### 2.2 第 2 屏（雪原）：让三个数字互锁

```js
goal: "collect", collect: 12, ballLimit: 5, par: { time: 60, made: 5 },
```

| 字段 | 值 | 它管什么 |
|---|---|---|
| `ballLimit` | 5 | 8 只敌人 / 5 颗球 → **平均一球要送 1.6 只** → 必须卷 |
| `collect` | 12 | **不承担约束**，只当引子。实测产出 33，要逼出"必须烧"得设到 26 以上，而掉落有随机，卡边界会变成运气关 |
| `par.made` | 5 | 评级里"用球 ≤ par"这一分要跟着额度走。留在旧值 9 的话，额度 5 的关永远白送这一分，省球没有回报 |

一句话：**8 只、5 颗球、每颗都得卷。想拿双份就得放弃一颗球。**

### 2.3 导出 `coatFoe`

额度到底拦不拦得住，只能从造球入口打进去验。`ballBudget()` 返回的是数字，不是证据。

## 3. 验证

### 3.1 机器人实测（`STAGE=2 ALL9=1`）

```
关            目标  结果  用时  造 崩 烧 袋 沉 装 落袋  收成  清场
2. 雪原       收成  达标   20s   5  0  5  0  0  3   0    33  8/8
```

| 读数 | 含义 |
|---|---|
| 造 5 | 额度用满 = **硬上限真的在拦** |
| 装 3 | 单球最多卷 3 只 → **地形支持这条路** |
| 8/8 达标 | 5 颗球够用 → **有解**，不是无解题 |

额度真伪的对照组：

| 额度 | 结果 |
|---|---|
| 4 颗 | 清 7/8 → **死局判负**（机器人 16 秒用完） |
| 5 颗 | 清 8/8 → 达标 |

一颗之差，从"打不过"到"刚好够"—— 这就是额度该有的手感。

### 3.2 冒烟 §34（21 项）

| 组 | 钉住的东西 |
|---|---|
| ① | `collect` 屏的额度被认（解耦生效） |
| ② | 额度耗尽后**糊满不造球**，敌人卡在"还差一层"；卷进球里不扣额度 |
| ③ | 非 `limit` 目标也会因额度耗尽判负 |
| ④ | `par.made` 跟额度；卡片底部真的画了「用球 x / par.made」 |
| ⑤ | 额度 < 敌人数（约束是真的）且 ≥ ceil(敌/3)（有解） |

## 4. 踩到的坑：测了但看不见

第一版是给 `_goalBase()` 加包装，往 `text` 里追加「球剩 N/M」。

**单元测试全绿，那句话一次都没上过屏幕。**

因为 HUD 只用了 `pr.cells` / `pr.frac` / `pr.inner`，**从来没读过 `pr.text`**。

这和上一批的「机制做了但没画」是同一个病，换了层皮：

| 病 | 表现 | 判据 |
|---|---|---|
| 机制做了没画 | 计时器在跑，屏幕无变化 | 断言要读绘制侧源码 |
| 数据算对了没画 | 函数返回值正确，屏幕无变化 | 断言要钉**真正可见的那条绘制语句** |

已改为钉 `"用球 " + S.stat.made + " / " + par.made` 这条语句本身。

## 5. 诚实边界

**这一批没有动任何地形。** 地面骨架仍然是 27/27 屏一整条平地 26..934。
理由写在 §0 第 4 条：球免费时，改断地面只会多几条更好看的解法。

**空间设计感这一批拿到的是"地形第一次有读的理由"**，不是"地形本身变复杂了"。
