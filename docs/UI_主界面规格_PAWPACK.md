# PAWPACK 主界面规格 v2.9

> 配套资产：`client/shots/home-layout@v2.png`（基准图）· `client/prototype/home-demo.html`（可交互动效 Demo）
> v1 见 `_归档-UI_主界面规格_v1.0-纯矢量版.md`（**纯矢量路线，已废弃**，原因见 §1）

---

## 1. 为什么 v1 被推翻

v1 用纯矢量画了整张家园。问题是生产方式，不是参数：

> **纯矢量的天花板就是"像贴上去的"。** 手工画的草地、云、屋顶，无论加多少层打光，都做不出 AI 插画那种笔触密度和环境光互渗。调参数调不出来。

v1 违反了项目自己在 v3.1 定的分工（AI 负责插画层、矢量负责控件层）。v2 把这条重新执行，并补上第三条：

| 层 | 谁产出 | 负责什么 | **绝对不能混的事** |
|---|---|---|---|
| **L0 背景** | AI 出图 | 建筑、地面、光照、空气透视 | **不能含任何角色** |
| **L1 角色** | AI 出图（透明底） | 六只宠物立绘 | 不能画进背景 |
| **L2 控件** | 矢量 | HUD、Dock、徽标、反馈特效 | 不能画插画 |

**L0 的"不含角色"是硬规矩，不是偏好。** 项目已经踩过一次：AI 出整张含角色的场景 → 角色坐标不可控（按缩略图估兔子在 y185–275，实际 y>330，差 140px）→ 所有"贴着角色的 UI"全部落空，最后互动层只能留空。角色拆成独立层之后，坐标、换装、动画才全部可控。

## 2. 三层各自的规格

### 2.1 L0 背景

| 项 | 规格 |
|---|---|
| 源文件 | `client/shots/bg/home-bg@v1.png`，1536×1024 |
| 裁切 | 取 `y = 48 … 912`（864 高）→ 1536×864 = 16:9 |
| 显示 | 缩放到 1280×720，`top = -40px` |
| 裁 48 的第二个作用 | 排除右下角"AI 生成"水印（水印在源 `y > 915`） |
| 生成参数 | image-to-image，`input_fidelity` 保持画风；prompt 里必须逐个点名"移除猫/兔/仓鼠/狗/牛/狐/蝴蝶/鸟"，并声明"地面保持空" |

### 2.2 L1 角色

六张透明底立绘 `client/shots/ai/<id>@v1.png`，锚点 **脚底中心**（`anchorX 0.500 / anchorY 1.000`）。
实测内容框：四周透明边距各 6px（0.4–0.5%），可以忽略；**底部留白 6px，不是 40px**——曾误判为"立绘底部有大留白导致悬空"，实际是坐标算错了。

### 2.3 L2 控件

四条质感规则（同一套光照，缺一条就回到"贴纸"）：

1. **暖白不纯白**：`rgba(255,251,240,.93)`，让插画的暖色透上来
2. **投影统一朝右下**（主光在左上）。方向不一致是眼睛最先发现的破绽
3. **四层叠加**：垂直渐变（顶亮底暗）+ 双层描边（外深内浅）+ 顶部内高光 2.4px + 底部内阴影 8px
4. **雾不是遮罩**：顶部雾只到 `y=70`、alpha `.46`；底部雾 152px、底部 alpha `.84`。**超过 `.85` 会把前景花压成米色，景深白做**

### 3.1 五个场景入口（徽标，不写字）

图标自己说话，比悬空木板轻，也不会和建筑打架。

| 入口 | 徽标位置 | 图标 | 依据坐标（实测） |
|---|---|---|---|
| 工作台 | (300, 334) | 锤 | 台面盒 `[140,260]-[399,429]` |
| 宠物屋 | (545, 388) | 爪 | 木门列峰 `x=475` / 行峰 `y=449` |
| 灶台 | (702, 342) | 锅 | 大黑锅暗色连通块 `[626,316]-[673,409]` |
| 派遣 | (1100, 480) | 信 | 矢量补建黑板，`baseY=596` |
| 出门 | (284, 202) | 旗 | 路牌盒 `[164,183]-[319,329]` |

### 3.2 六只的位置（位置即性格）

| 宠物 | 星级 | 站位 | cx | footY | h | 占屏高 | 依据 |
|---|---|---|---|---|---|---|---|
| 年糕 狗 | ★ | 路牌旁 | 250 | 600 | 146 | 20.3% | 狗永远在门口等 |
| 雪团 兔 | ★★ | 屋门口 | 450 | 596 | 126 | 17.5% | 兔子不敢走远 |
| 砂糖 猫 | ★ | **屋脊** | 490 | 156 | 82 | 11.4% | 猫必须在最高处 |
| 团子 仓鼠 | ★★ | 大黑锅前 | 716 | 598 | 136 | 18.9% | 贪吃，守锅 |
| 豆奶 牛 | ★★★ | 粉垫子上 | 862 | 592 | 136 | 18.9% | 怕热，找能趴的地方 |
| 星屑 狐 | ★★★★ | **栅栏最右** | 1148 | 596 | 112 | 15.6% | 狐不轻易靠近人 |

三条硬规则：

1. **位置即性格**：站在它在乎的东西旁边
2. **距离即亲密度**：★★★★ 的星屑站最远，用空间关系表达稀有度，不在头上标四颗星
3. **`footY ≤ 600`**（Dock 顶 618 − 18 净距）。上一版写 628，年糕的脚被 Dock 直接切掉

尺寸基准：主界面宠物占屏高 **11.4–20.3%**，战斗内 16.7%（v3.2 §9）。**两个场景分开算，不要混用。**

### 3.3 Dock 的宽度预算（1280 只够 5 组）

**v2.1 改版**：待命队从 5 格改成 **伙伴位 6 格**（出战那只也在格子里，带金色框和 ◆ 角标）。理由见 §10.2 —— 未解锁的格子要一直占着位置，才能起到催促作用；如果只显示已拥有的，第 2 只到手前玩家根本不知道还有别的伙伴。

| 组 | x 范围 | 宽 | 内容 |
|---|---|---|---|
| 资源 | 20 – 278 | 258 | 果子 248 / 材料 36 / 吧唧 12，各 82×62 |
| 出战卡 | 286 – 472 | 186 | 头像 46 + 名字星级 + 五心 + 饱食三段 |
| 伙伴位 | 486 – 739 | 253 | 6 格 × 38，间隔 5；未解锁 = 虚线框 + 🔒 + 「第N关」 |
| 出门 | 747 – 1259 | 512 | 主按钮，占屏宽 40%；右侧安全区 21px |

> 6 格是硬上限。第 7 只进来这一排就放不下了 —— 这也是"六只锁死"的一条物理理由（§10.2）。

**Dock 的元素上限是 5 组。** 上一版塞了 11 个元素（资源 3 + 出战 + 待命 5 + 图鉴 + 背包 + 派遣 + 出门），待命队和图鉴重叠 20px，整体糊成一团。砍掉图鉴/背包/派遣三个键，因为它们本来就有场景入口：图鉴归宠物屋、材料道具归工作台、派遣有黑板。

> **入口不做两遍。** Dock 每多一个键，场景入口就被稀释一分。

## 4. 动画栈（`home-demo.html` 已实现）

三层，只在最后两层打断，呼吸永不打断。

| 层 | 周期 | 参数 | 为什么 |
|---|---|---|---|
| **L1 呼吸** | 2650ms | `scaleY = 1 + 0.016·sin`，`scaleX` 反向 0.009，`translateY -1.3` | 六只相位错开 **300ms**。不错开就会读成"整块画面在动" |
| **L2 自主** | 6.2–14.4s 泊松 | 蹦跳 46% / 摇摆 32% / 表情 22% | 每只一个 `nextAt`，不是全局定时器 |
| **L3 点击** | 690ms | 预判 90ms（收 0.93）→ 反应 320ms（弹到 1.14 + 上跳 13）→ 回落 280ms | 先收再弹，弹跳才读得出"被碰到了" |

**移动一律用蹦，不用走。** 单帧立绘腿不动，平移就是滑步。

**摇摆只到 ±0.035rad**（约 2°）。超过这个角度，绕脚底旋转会让脚明显离地。

点击的三件反馈物（缺一件就不知道"我摸到了"）：

- **涟漪**：脚下扩散环，`scale .25→2.4`，620ms
- **粒子**：6 颗随机字（♥ ♪ ★ ✿），初速 1.1–2.7，寿命 900–1350ms，`vy` 每帧 −0.0016·dt 上浮
- **反应泡**：「!」/「♥」/「★」，32px 圆 + 尖角，`cubic-bezier(.34,1.6,.64,1)` 弹入

**连摸 5 次**：金色爆发 16 颗 + 大涟漪 130px + Toast「亲密度 +1 · 它记住了你」，Dock 里第 4 颗心点亮。这是唯一成本近零的"获得感"。

### 7.2 适配

| 引擎 | 设置 |
|---|---|
| Unity | Canvas Scaler: Scale With Screen Size, **Match = 1**（高度优先，Steam 横屏）；Sprite Atlas 按「界面」分组 |
| Godot 4 | `Content Scale = canvas_items`，`Aspect = expand`；NinePatchRect 的 `patch_margin_left/top/right/bottom` |
| Unreal | DPI Scaling 曲线按 720 基准；`Slate Brush Margin` 左/上/右/下 |
| Cocos 3.x | Canvas `fitHeight = true`；Sprite Type = SLICED，Border 左/右/上/下 |

**Steam 特有**：左右安全区各 20（1080p 30），不贴边；底部 Dock 距屏底 10。

## 10. 游戏接入（`game.html`）

主界面已经不是一个独立效果页了，它是**游戏入口**。打开 `client/prototype/game.html` 就是开局。

### 10.1 三个文件的分工

| 文件 | 角色 | 说明 |
|---|---|---|
| `game.html` | **唯一入口** | 主界面 + 解锁系统 + 存档。玩家只会打开它 |
| `grove.html` | 关卡 | 原八关推关原型。加了三条钩子（见 10.4），**不带参数时行为完全不变** |
| `_归档-home-demo-已被game.html取代.html` | 已归档 | 原「纯展示样张」。它引外部图，今天在预览器里同样会空白；全部动效已并入 `game.html`，保留仅作参考 |

### 10.2 解锁节奏（开局只有砂糖）

**开局 1 只 → 8 关里逐步到 6 只。全部靠通关解锁，不走抽卡**（这条是 `UI_概念设计_v2.0` §1.1 已定的：没有内购，稀有度只做叙事稀缺）。

| 宠物 | 星级 | 解锁条件 | 为什么是这个位置 |
|---|---|---|---|
| 砂糖（猫） | ★ | 开局自带 | 唯一在身边的伙伴 |
| 年糕（狗） | ★ | 通关 **1** 关 | 第一次正反馈必须最早 —— 30 分钟内要拿到第 2 只，否则玩家以为游戏只有一只 |
| 团子（仓鼠） | ★★ | 通关 **3** 关 | |
| 雪团（兔） | ★★ | 通关 **5** 关 | |
| 豆奶（牛） | ★★★ | 通关 **7** 关 | |
| 星屑（狐） | ★★★★ | 通关 **8** 关（全清） | 最稀有压在最难的关上，才有"压轴"的意思 |

**这个表在两个文件里各存一份，必须同步**：`game.html` 的 `PETS[].at` 与 `grove.html` 的 `UNLOCK_AT`。改一处不改另一处，会出现"关卡里说它到家了，回家却没有"。

### 10.3 存档

`localStorage['pawpack.save']`，两个页面共用：

```json
{ "v": 1,
  "cleared": [0, 1, 2],          // 已通关的关卡索引（去重靠 Set）
  "active": "nian-gao-dog",      // 当前出战
  "pats": { "sugar-stand": 12 }, // 每只被摸次数 → 亲密度（5 次 1 心）
  "seen": ["nian-gao-dog"] }     // 已播过「新伙伴加入」的 id
```

`seen` 是必须的。没有它，每次进游戏都会把已解锁的宠物再演一遍"新伙伴加入"——**过场只能用一次，用两次就变成骚扰**。

> 注意：砂糖的 `at = 0`，但它**不算新伙伴**，判定要写成 `at > 0 && !seen.includes(id)`。漏掉 `at > 0` 这条，重置存档后的第一次通关会把砂糖自己也演一遍（这是实测踩到的 bug）。

### 10.4 跳转协议

**主界面 → 关卡**

```
grove.html?from=home&hero=<0-5>&stage=<0-7>
```

`hero` 是 `grove.html` 里 `HEROES` 的索引（cat 0 / dog 1 / ham 2 / rab 3 / ox 4 / fox 5），不是宠物 id —— 两个文件的命名体系不同，转换只在 `PETS[].hero` 一处做。

**关卡 → 主界面**，三个出口都跳回 `game.html`：

| 出口 | 触发 | 行为 |
|---|---|---|
| ESC | 任意游玩中 | 直接回主界面（主界面已取代"门口选人"这一站） |
| E 收工 | 结算面板 | `goHome()` 结算后回跳，解锁过场在主界面播 |
| 全清 | 打完第 8 关 | 同上，`goHome(true)` |

**关卡里也会提示解锁**：`recordClear()` 发现这一关刚好跨过阈值，就在画面顶部浮一条「✦ 新伙伴到家：年糕 / 回主界面见它」，3.6 秒消失。这不是过场，只是让玩家知道"刚才那一下有意义"。

### 10.5 调试条（右下角）

三个键，让不用真打 8 关也能看解锁节奏：

| 键 | 作用 |
|---|---|
| `通关 +1` | 把"第一个没通的关"记为通关，触发对应解锁与过场 |
| `全解锁` | 一次给满 6 只，逐个播过场（每只约 1 秒） |
| `重置存档` | 清 localStorage 并重载，回到"只有砂糖" |

**发布前必须删掉这一条。** 它现在留着，是因为这一轮要的是"你自己看效果"。

### 10.7 构建：交付物必须是自包含单文件

**这条是踩坑之后加的铁律，不是优化项。**

第一版 `game.html` 用 `../shots/bg/home-bg@v1.png` 引外部图。在浏览器预览器里打开时，服务根挂在 `prototype/`，`../` 越界被拦，**全部图片 404**。

症状特别有欺骗性：

| 表现 | 实际 |
|---|---|
| HTML/CSS/JS 全部正常，控件都在 | 图片请求全 404 |
| 画面变成一片淡黄 + 一堆悬空徽标 | 背景层空了，露出 `#stage` 的底色 `#FFE6C6` |
| 宠物一只都不在 | 立绘全 404 |
| 看起来像"设计漏画了" | 设计没问题，是资源没到 |

**所以交付形态是单文件**：图片全部压成 WebP 内联，零外部依赖。这样双击、预览器、发给别人、换机器，全都一模一样。

#### 文件分工

| 文件 | 角色 | 谁改 |
|---|---|---|
| `game.src.html` | **可编辑源**（用 `../shots/` 外部路径，方便改） | 我 |
| `_build-game.js` | 构建脚本 | 只在资源尺寸/质量要调时改 |
| `game.html` | **产物，交付物**（844KB，自包含） | **不手改，改了会被下次构建覆盖** |

**改界面的正确流程**：改 `game.src.html` → 跑 `node _build-game.js` → 交付 `game.html`。


## 11. 概念图 → 游戏：逐参数对齐（v2.3）

v2.2 交付后仍有"两张图看着不一样"的反馈。这一节记录**这次是怎么把它量出来的**，以及每一条的具体数字 —— 下次改界面照这个走。

### 11.1 先解决"看不见"

要逐参数比，前提是能把游戏截成**精确的 1280×720**。走过两条路：

| 方案 | 结果 |
|---|---|
| 开真窗口 + `ImageGrab` 截客户区 | **不可靠**。Chromium 的 `--app` 窗口是自绘标题栏（标题栏画在客户区**里面**），`GetClientRect`/`ClientToScreen` 的起点比真实视口高约 28px，截出来带一条标题栏、右边还被切一截；加上常驻软件会盖住窗口、抢焦点经常失败 |
| **headless + CDP** | **可用**。`--headless=new` 在本机 Edge 155 上能正常起来（旧结论"headless 不落盘"已失效），`Emulation.setDeviceMetricsOverride` 把视口钉成 1280×720@1x，`Page.captureScreenshot` 直接取渲染结果 —— 与窗口大小、是否前台完全无关 |

配套细节（都会让脚本静默失败）：

- 本机有 `http_proxy` 环境变量，`urllib` 访问 `127.0.0.1` 会被转到代理上回 502 → 必须用 `ProxyHandler({})` 显式绕过
- DevTools 的 WebSocket 握手要 `suppress_origin=True`（或加 `--remote-allow-origins=*`）
- 页面侧要有 `#shot` 开关：强制 `#stage` 为 `scale(1)` 且贴 `(0,0)`，否则舞台居中缩放，裁出来的不是设计坐标

脚本：`client/tools/_cdp-shot.py <shot|shotall>` → `client/shots/game-<mode>.png`
对比：`client/tools/_pair.js`（同区域上下放大）、`_compare.js`（叠加差异热力）

### 11.2 六层玻璃（最大的那一处）

概念图 `glass()` 是**六层叠加**，CSS 复刻版只有四层，而且**是不透明的**。

| 层 | 概念图参数 | v2.2 CSS | v2.3 CSS |
|---|---|---|---|
| ① 右下投影 | `rgba(74,44,24,.22)` 偏移 `(+2,+5)` | `0 4px 0 rgba(74,44,24,.17)`（只有 y） | `2px 5px 0 rgba(74,44,24,.22)` |
| ② 垂直渐变 | alpha **.97 / .93 / .95** | **不透明** `#FFFEF8/#FFFBF0/#FAEEDA` | 同 alpha，写成 `rgba(...)` |
| ③ 外深描边 | 2.8px `rgba(122,80,52,.74)` | 2.6px `.72` | 2.8px `.74` |
| ④ 顶部高光 | 2.4px `rgba(255,255,255,.62)` | `inset 0 2px 0 .6` | `::before` 2.4px |
| ⑤ 内浅描边 | 1.3px `rgba(255,255,255,.40)`，内缩 2.2 | **缺** | `inset 0 0 0 1.3px` |
| ⑥ 底部内阴影 | 8px `.14` 渐变 | `inset 0 -3px 6px .10` | `::after` 8px 渐变 |

**最容易做错的是 ②**：写成不透明就立刻从"玻璃"变成"一块贴纸"。背景暖光透不过来，整套控件就"漂"在场景上。

④⑥ 必须真占 2.4 / 8px 高度并被圆角裁掉，所以走伪元素 + `overflow:hidden`。用 `inset box-shadow` 近似会在圆角处露出直角边。

> 附带一条：`.ico-btn`（设置钮）的第二层背景必须**同步改成半透明**，否则圆钮会退回实心片。

### 11.3 文字位置：一律写死 line-height

概念图用 canvas `textBaseline="middle"`，文字中心 = 参数 y。CSS 默认行高随字号浮动，所以**整条 HUD 曾比概念图高 4~6px**，而且字号一改还会再漂。

约定：每个文字元素都写 `line-height:<N>px`，`top = 目标中心 y − N/2`。

| 元素 | 概念图中心（相对底板） | v2.2（偏高） | v2.3 |
|---|---|---|---|
| 苔 原 | (20, 20)，12.5px bold | top 8 → 中心 ≈15.8 | `top:13.5 / lh:13` |
| 3 / 8 关 | (20, 35)，10px | top 25 → 中心 ≈31.6 | `top:30 / lh:10` |
| 连锁 ×1.45 | 右对齐，中心 23，11px bold | **缺这行字** | `right:16 / top:17 / lh:12` |
| 提示条文字 | 左 36，中心 19，11.5px bold | left 14 / top 6 | `left:36 / top:13 / lh:12` |
| 资源数值 | 右 10，中心 26，17px bold | top 8 → 中心 18.2 | `top:17 / lh:18` |
| 资源名 | 右 10，中心 44，9.5px | top 34 | `top:39 / lh:10` |
| 出门主文案 | 中心 (72, 35)，27px | left16 居中 → 76 | `left:12 / width:120 / top:21.5 / lh:27` |
| 出门第二行 | 左 172，中心 27 / 48 | top 13 / 35 | `top:19.5 / lh:15`、`top:42.5 / lh:11` |

Logo 的描边：概念图是 canvas `strokeText`（线宽 5.5 中心描边 → 字外扩 2.75px）。CSS 没有真描边（`-webkit-text-stroke` 会盖住填充），用**八向零模糊 `text-shadow`** 拼；不要用带模糊的写法，那会读成"投影"，白字立刻失去厚度。

### 11.4 图标：两套子风格，线宽按比例算

概念图里 **Dock 资源图标是彩色填充、场景入口徽标是棕色单色线描** —— 这是刻意的，不是随手画的。混用才是问题：资源做线描会又淡又小，徽标做彩色会抢场景的眼睛。

线宽推导（这是 v2.2 定错的地方）：

```
概念图徽标：半径 13，线宽 1.9  →  线宽 / 内容直径 = 1.9 / 28 = 13.6%
我们的画布：内容直径 88        →  88 × 13.6% ≈ 12
```

v2.2 定的是 **8**（理由是"看着精致"），结果缩到 27px 显示时细成发丝。**线宽必须按比例算，不能按大图好看来定。**

尺寸阶梯（都按"图标 PNG 的内容只占画布 68.75%"换算）：

| 用途 | 视觉尺寸 | 图标框 |
|---|---|---|
| 场景徽标（27 圆） | 14.4 | 21px |
| 设置钮（36 圆） | ≈21 | 30px |
| 提示条爪印 | 13.75 | 20px |
| Dock 资源（62 高卡） | 20~25 | 32px |

还有一个踩到的坑：彩色图标用 `translate + scale` 绘制时，**`lineWidth` 不要再乘 scale** —— 它会被当前 transform 一起缩放，乘一次就变成平方，描边直接糊死整个图形（果子会变成一颗褐色圆饼）。

### 11.5 场景道具烘进背景图，不放进运行时

概念图在 AI 背景之上又用 canvas 补了 `noticeBoard(1046,596)`、`signFlag(215,200)`、`ambient()`（草地光斑 / 12 片花瓣 / 5 个爪印）。我们的 `home-bg@v1.png` 里没有，于是**「派遣」徽标悬在半空**（本该钉在告示板上）、路牌光秃秃的。

做法：`client/tools/build-bg.js` 把三样东西烘进 `home-bg@v2.png`。它们是静态的，没有任何运行时理由留在代码里；烘进图里之后 `game.html` 与 Cocos **共用同一张图，两边自动一致，运行时零成本**。

坐标换算（容易错）：CSS 里 `#bg` 是 `top:-40px / height:853px` 画整张 1536×1024，所以设计坐标 `(x,y)` 对应源图像素 `(x*1.2, y*1.2 + 48)`。用一个 `setTransform(1.2,0,0,1.2,0,48)` 一次性处理，道具函数内部仍按设计坐标写。

### 11.6 概念图自己有 bug 的地方，不要照抄

HUD 进度条底板给的是 **300px**，但要装下「标签 + 8 格 + 连锁」：`76 + 176 + 55 > 300 − 36`。实测概念图里**连锁文字压在最后两格上**。

处理：底板加宽到 **330**（左 455，右 785），**中心仍在 x=620**，左右各借 15px，重叠就没了。格子节奏从 22 收到 21（15+6）。

同类判断标准：**照抄的是设计意图（层级、质感、节奏），不是设计事故（重叠、越界、断裂）。**

### 11.7 状态对齐：截图模式

概念图的状态是「6 只都在家 + 3/8 关」，而本作把伙伴绑在关卡上（过关才回家）—— **两条规则直接矛盾**，不改代码就永远比不出所以然。

所以有两个 hash 开关（只在 hash 里出现时生效，正常游玩不受影响）：

| hash | 作用 |
|---|---|
| `#shot` | 舞台强制 1:1 贴左上角 + **清空存档**（`reset`）→ 首屏状态 |
| `#shotall` | 同上 + 存档摆成概念图状态（cleared `[0,1,2]`、active `nian-gao-dog`、pats 12 → 3 颗心）+ `isUnlocked()` 临时全放行 |

`#shotall` 下 HUD 会显示 `3 / 8 关` 与 `连锁 ×1.45` —— 与概念图逐字一致，这才谈得上比对。

## 12. Cocos 场景：四个会让编辑器打不开的坑（v2.4）

只要 `Home.scene` 是脚本生成的（不是编辑器里手摆的），下面四条每条都能让工程"看起来完整、一打开就废"。它们的共同点是：**文件层面完全合法，JSON 解析得动，静态检查也容易漏**。

| # | 症状 | 真因 | 判据 |
|---|---|---|---|
| 1 | 预览白屏，控制台每帧刷 `Cannot read properties of null (reading '_getUITransformComp')` | `Canvas._parent` 是 `null`。Scene 的 `_children` 里有 Canvas，但 Canvas 没写回父引用 | `cc.Widget.align()` 取 `this._target \|\| this.node.parent`，拿到 null 交给 `getReadonlyNodeSize()`，而它第一行 `parent._getUITransformComp()` **没有 null 保护** |
| 2 | `Open scene failed: <uuid>`，场景打不开 | 同一节点在父节点的 `_children` 里出现两次 | `addSprite(iCanvas,…)` 建时就挂了一次，末尾"按渲染顺序统一挂载"的循环又挂一次 |
| 3 | 编辑器里一片黑，或只剩背景一条边 | 相机 z 与 UI 同在 0 平面，`_near=0` 把界面切掉 | `node()` 构造器写死 `z: 0`，把传入的 `z: 1000` 丢了 |
| 4 | 整个界面左移一屏，右侧大量空白 | Canvas 位置写成 `(-640, 360)` | `TL(x,y) = (x-640, 360-y)` 是给**子节点**用的相对坐标，不能拿来定位 Canvas 本身；Canvas 自身位置应是屏幕中心 `(640, 360)` |
| 5 | HUD 的 8 个关卡格、提示条箭头、星级全不见；其余一切正常 | 子节点用了 `addPart()` 的 `TL()`（相对 Canvas 中心的**绝对**定位），但父节点自己有位移 | 父 `HudProgress` 在 `(450,12)`，子 `pip` 又给 `TL(94,14)` → 偏移叠加两次，元素飞到屏幕外。**坐标都是合法数字，静态检查与引擎都不报错** |

### 12.1 坐标系：两种定位不能混用

`make-scene.js` 里有两套定位，长得像、语义完全不同：

| 函数 | 坐标参照 | 只能挂到 |
|---|---|---|
| `addPart(parent, …, wx, wy)` | 画布中心（`TL()` 换算） | 铺满屏幕、位置为 `(0,0)` 的容器：`iCanvas` / `iHUD` / `iDock` / `iBadges` |
| `addSprite` + `inPart(part, dx, dy)` | **父节点左上角**（Cocos 的局部坐标） | 任何节点，包括自己有位移的 `HudProgress` / `HudTip` / `GoCard` / `Slot` |

判据一句话：**父节点 lpos 不是 (0,0) 时，子节点一律用 `inPart`**。混用的后果不是"偏一点"，是"整个元素消失"——因为偏移量往往是几百像素。

`tools/_render-scene.js` 能抓到这类错，前提是它**递归累积** `ox + lpos.x`（它是）。这也是为什么自渲染预览和运行时截图的差异率能压到同一量级：两边算的是同一套父子坐标。

### 12.2 还有一个"不崩但不对"的

容器节点（`Pets` / `Badges` / `HUD` / `Dock`）只做分组、不画东西，很容易被当成可以省掉 `UITransform` 的虚拟节点。Cocos 3.8 里省掉之后**通常不报错**，但 UI 批次与 Widget 的对齐计算都会异常。规矩是：**除 3D 相机外，每个节点都必须有 `UITransform`**，容器给满屏尺寸、锚点左上。

### 12.3 验证器必须查这五项

`tools/verify-scene.js` 从 12 项扩到 **17 项**，新增的全是上面这些"文件合法但引擎不认"的检查：

```
5b 坐标基准
   ✓ Canvas 位置 = 屏幕中心 (640,360)
   ✓ 相机 z > 0
   ✓ 除相机外每个节点都有 UITransform
2  父子关系
   ✓ 父子双向一致（含 Scene → Canvas）   ← 检查范围必须包含 cc.Scene
   ✓ 每个子节点只登记一次、只有一个父节点  ← 查重复项，不只查反向引用
```

**关键教训**：原来的"父子双向一致"只遍历 `cc.Node`，把 `cc.Scene` 跳过了 —— 于是"Scene 里放着 Canvas、Canvas 却没有父引用"这个最致命的情况恰好落在检查范围外，12 项全绿、预览白屏。

### 12.4 非 16:9 视口会留黑边（不是 bug）

预览页顶部工具栏占去 47px 后，画布是 1280×673。项目设的是 `fitHeight`，于是 1280×720 的内容缩到 **1196×673** 居中，左右各留 **41px 黑边**。

按内容区裁切后再和概念图比，差异像素 **3.2%**；直接拿整张 1280×673 去比会得到 18.8%，中间那 15 个点全是这个黑边。**比对之前先确认两边的有效内容区一致**，否则量出来的是适配差、不是设计差。

### 12.5 场景状态与概念图对齐

概念图是「6 只都在家 + 3/8 关」，而按 `game.html` 的规则（过关才回家）摆，待命位只剩 3 格、后两格带锁 —— 和概念图差两个头像。演示场景固定 `ALL_UNLOCKED = true`、`SHOW_NEW_BADGE = false`（概念图是稳定态，没有「新」角标）。真实解锁曲线是运行时的事，不写进静态场景。这与 `game.html` 的 `#shotall` 是同一套做法。

## 13. 家园活体化：站位 / 走动 / 入口可读性（v2.5）

这一节解决的问题来自五条真实反馈：**站得不合理、只有静态、初始不该有六只、功能全是空壳、入口图标太小也没说明**。逐条给出可执行的数字，并标注哪些已经落地、哪些是待接。

### 13.1 站位：先修"物理成立"，再谈好看

**结论：一条水平线上的六个立绘不是"排布"，是"贴纸墙"。**

原来的坐标（设计分辨率 1280×720）：

| 宠物 | 原 cx / footY | 问题 |
|---|---|---|
| 砂糖 | 490 / **156** | 踩在**穹顶上**。屋顶是弧面，没有平台 —— 弧面上站猫，任何角度看都是穿模 |
| 年糕 | 250 / 600 | 与砂糖的 x 只差 240，但深度差 444，透视上不该同屏 |
| 雪团 | 450 / 596 | 夹在年糕和团子之间，三人容器互相压 |
| 团子 | 716 / 598 | — |
| 豆奶 | 862 / 592 | — |
| 星屑 | 1148 / 596 | — |

五只的 `footY` 落在 592~600 之间 —— **六只脚在同一条直线上**，等于没有景深。真实场景里"同一深度排六个人"是最不自然的摆法。

**修法：footY 分五档，h 同步缩放。**

| 宠物 | 新 cx | 新 footY | h | 深度 | 领地 roam |
|---|---|---|---|---|---|
| 砂糖 | 160 | 548 | 84 | 远 | 136 – 192 |
| 星屑 | 1130 | 568 | 112 | 远 | 1106 – 1162 |
| 雪团 | 500 | 574 | 128 | 中远 | 472 – 532 |
| 团子 | 700 | 596 | 138 | 中 | 676 – 746 |
| 年糕 | 320 | 602 | 148 | 近 | 288 – 358 |
| 豆奶 | 890 | 610 | 138 | 近 | 862 – 932 |

三条判据：

1. **footY 越大 = 越近 = h 越大**。砂糖 h 84 / 年糕 h 148，差 1.76 倍，这个比例才是"远小近大"能读出来的量级。差 10% 以内读者看不出来。
2. **相邻两只的中心距 ≥ (容器宽A + 容器宽B) / 2 + 8**。容器宽 = `max(立绘宽 × 1.28, 100)`（点击区下限）。少算这一步就会像第一版那样左侧三只叠在一起。
3. **同一只的深度不在换位时改变**。所以走动只走 x，不动 footY —— 一走 y 就得同步缩 h，不然会出现"走到远处反而更大"的错觉。

砂糖的人格从"最高点归它"改成"站得最远，看得最清"：设定本身（守卫/瞭望）没丢，只是从"垂直最高"换成"水平最远"，物理上就成立了。**改位置必须连带改文案 —— 位置是文案的证据。**

### 13.2 走动：三件套缺一不可

**结论：位移 + 踏步 + 领地，缺任何一件都会露馅。**

单帧立绘没有行走帧，所以"走"只能靠三件事合成：

| 层 | 做什么 | 参数 | 缺了会怎样 |
|---|---|---|---|
| A 位移 | 改 `wrap.style.left` | 速度 ≈ 62 px/s；单次 42~138 px | 只踏步不位移 = 原地跑 |
| B 踏步 | `translateY` 起伏 + 轻微 `scaleY` | 每步 24 px 触发一次，幅度 3.4 px，`scaleY` ±1.2% | 只位移 = 贴纸在滑冰 |
| C 领地 | 目标点夹在 `roam` 区间内 | 见 13.1 表 | 不夹 = 走几次就漂到邻居身上，六只挤成一团 |

**节奏参数（这一项比幅度更影响"活气"）：**

```
初始延迟     0.7 ~ 2.5 s（各只随机，避免同时动）
行为间隔     1.8 ~ 4.2 s
走动权重     62%
  蹦跳       18%
  摇摆       11%
  表情       9%
走完停顿     0.9 ~ 2.6 s（比间隔短，走完更容易接着走）
```

原来的参数是"6.2 ~ 14.4 s 一次、只有原地跳"。实测 7 秒采样里**有一半宠物一次都没轮到** —— 所以"看起来是静态的"不是错觉，是采样率太低。**宠物的存在感取决于「同一时刻有几只在动」，不取决于单只的幅度。**

走动实现的两个坑：

1. **位移与变换必须分两个坐标系**。`left` 是占位盒在父容器里的位置；`transform` 是盒内的绘制变换。混用会看到"一边走一边往画外漂"。
2. **`easeInOutQuad` 而不是线性**。线性起步/落停像传送带；缓动才有"迈步—停住"的重量感。公式：`u<.5 ? 2u² : 1-(-2u+2)²/2`。

**截图冻结开关**：`#shot` / `#shotall` 会把 `nextAt` 推到 `1e15`，否则每次截图宠物位置都不同，差异像素率退化成随机数。动效验证要用 `#walkall`（全解锁 + 不冻结）—— 用 `#shotall` 测会得到"宠物一动不动"，看起来像动效没实现。

### 13.3 场景入口徽标：27 px 是错的

**结论：27 px 的圆钮在实际画面里等于没有入口。**

| 项 | 旧值 | 新值 | 依据 |
|---|---|---|---|
| 圆钮直径 | 27 px | **40 px** | 720p 下 27 px 在草地上是"芝麻"；40 px 才进入"可识别物件"的量级 |
| 图标内容直径 | 14.4 px | **22 px** | 40 × 68.75%（沿用图标家族的留白率）→ 图标框 32 px |
| 点击区 | 27 × 27 | **52 × 52** | 视觉 40 不够摸，用透明伪元素外扩 6 px；不能直接加大盒子，否则阴影和 hover 缩放一起变大 |
| 说明 | 仅 `:hover` | **常驻 11 px 标签** | 触屏与手柄没有 hover，等于完全没说明 |

**圆心不能动。** 尺寸从 27 改到 40 时，`left/top` 各减 6.5 —— 直接沿用旧值会让五个入口整体右移下移，而且看单个不会发现，只有叠加对比才露。

**标签胶囊规格**：高 18 px、半高圆角（胶囊形）、字号 11 / 行高 11、内边距左右 7；宽度只有两种 —— 2 字 34 px、3 字 45 px。**不做九宫格**：只有两种宽度，出两张图比配四个 border 值省事，也不会出现"四值顺序接反"这种只在引擎里才暴露的错。

**每个徽标的 x 必须与它标注的物件中心对齐**，否则玩家读不出"这个图标指的是哪件东西"。物件实测中心（设计坐标）：

| 入口 | 物件 | 物件中心 | 徽标圆心 |
|---|---|---|---|
| 工作台 | 木桌 | 232, 402 | 232, 340 |
| 图鉴 | 门口 | 500, 420 | 500, 352 |
| 灶台 | 右侧石台上的锅 | 628, 405 | 628, 330 |
| 派遣 | 告示板 | 1048, 570 | 1048, 498 |
| 去苔原 | 路牌 | 250, 240 | 284, 202 |

第一版把"灶台"放在 702, 342 —— 距锅 120 px，浮在屋顶右侧的半空。**图标与物件的距离超过物件自身高度的一半，读者就不会建立关联。**

### 13.4 初始状态：静态场景只在"这一刻家里有谁"上说真话

**结论：初始只应有 1 只（砂糖，at=0），其余五只在关卡里，不在家里。**

原来的 Cocos 场景犯了两个错：

1. `ALL_UNLOCKED = true` —— 为了让场景与概念图对比，写死全解锁。结果玩家一进编辑器就看到六只齐活。
2. **宠物节点无条件创建六个** —— 即使 `ALL_UNLOCKED = false`，六只也全都画在场景里。伙伴位那一排又按进度显示锁，两处规则互相打脸。

修法：宠物节点按 `CLEARED >= p.at` 判定。`CLEARED` 取 0，`ACTIVE` 改为 `sugar-stand`。

> **v2.8 修订**：上面这条后来从「未达成的根本不建节点」改成「六只全部预置、未达成的 `_active = false`」。
> 原因是战斗侧的出战人数改成了「已解锁数」（见 `config/Roster.ts`）：打赢一局 → 关卡 +1 → 年糕解锁 →
> 战斗里真的多出一只。如果家里连节点都没有，就会出现"战斗里多了一只、家里看不见"的新断层 ——
> 正是这一轮要消掉的那类毛病。家园贴图不在 `resources` 下（走 UUID 直连），运行时拿不到，
> 所以"预置 + 开关 active"是这条链路上唯一不需要改资源管线的做法。
> 真正的开关在 `HomeRuntime.bindPets()`，按存档再刷一遍。

解锁曲线（`at` 字段）保持不变，`ALL_UNLOCKED` 与 `SHOW_NEW_BADGE` 留作概念图对照开关，**不要改 `isUnlocked` 的判断本身**。

### 13.6 工具链教训：渲染器的锚点方向

**结论：自渲染预览器把 Label 的垂直居中算反了，导致所有 Label 的位置判断都不可信。**

`cc.UITransform` 的 `anchorPoint.y = 1` 表示**顶边**，盒体从节点位置向**下**延伸：

```
anchor.y = 1   → 盒顶 = py          → 文字中心 = py + h/2
anchor.y = 0   → 盒顶 = py − h      → 文字中心 = py − h/2
anchor.y = 0.5 → 盒顶 = py − h/2    → 文字中心 = py
```

通用式：`ty = py + (anchor.y − 0.5) × h`

原来写死 `py − lineHeight/2`，等于同时假设"anchor.y = 0"和"盒高 = 行高"，两个都错。徽标标签（盒 18 / 行高 11）因此整体上浮，看起来像"文字压在圆钮上"。

**这条的教训不是那个公式，而是：自渲染器本身也要被验证。** 当"场景文件里的数字都对，但预览图不对"时，先怀疑预览器，别去改场景 —— 改场景只会把对的改错。

## 14. 运行时交互：把静态贴图变成可操作的界面（v2.6）

### 14.1 根因不是"忘了绑定"，是这个场景从来没有交互层

对 `Home.scene` 做类型统计，结果很难看：

| 组件类型 | 数量 |
|---|---|
| `cc.Node` | 91 |
| `cc.UITransform` | 90 |
| `cc.Sprite` | 56 |
| `cc.Label` | 29 |
| **`cc.Button`** | **0** |
| **自定义脚本组件** | **0** |

也就是说：这个界面上**没有任何一个节点是可点的**，**没有任何一帧是被驱动的**。
它是一张做得很像 UI 的图。上一版 §13.5 写了"入口接线现状"，但那说的是网页原型；
Cocos 侧连一根线都没有。这两件事必须分开记，否则会拿网页版的验收结论去验收 Cocos。

### 14.2 可点性规范（缺一条就会返工）

| 项 | 规格 | 依据 |
|---|---|---|
| 最小热区 | **88 × 88** 逻辑像素 | 触屏手指落点直径经验下限；低于此值误触率陡增 |
| 热区与视觉分离 | 视觉可以小，热区必须够 | 徽标视觉 47×48、齿轮 43×46，都不达标 → 另开隐形热区，视觉一个像素不动 |
| 按下反馈 | 缩放到 **0.90**（小元素）/ **0.965**（大按钮） | 0.90 在 47px 上只有 4.7px 位移，再小就看不出来；大按钮缩太多会显得塌 |
| 状态数 | 常态 / 按下 / 禁用 **三态必做** | 「选中」态在主界面不适用（没有多选），不为对称而硬加 |
| 抬起判定 | 必须同时监听 `TOUCH_END` **和 `TOUCH_CANCEL`** | 手指滑出节点范围时只会收到 CANCEL；只听 END 就必然出现"按下去弹不回来"的卡死态 |
| 点击穿透 | 命中后置 `propagationStopped = true` | 否则弹层背后的元素会被同一次点击触发 |

**实测到的三个不合格项**（本轮已修）：

| 元素 | 视觉尺寸 | 处理 |
|---|---|---|
| `Badge-*` × 5 | 47 × 48 | 热区扩到 88×88（隐形节点，置顶） |
| `IconBtn`（齿轮） | 43 × 46 | 同上 |
| `Btn-Go`（出门） | 509 × 84 | 高 84 距下限差 4px，按 88 标准属可接受区间，不拉伸画面（拉伸会让九宫格边框变粗） |

### 14.3 动效清单：为什么只有这几条

动效不是越多越好。同屏同时在动的元素一旦超过约三分之一，界面就会读成"吵"。
所以这里按**注意力优先级**分配，而不是"每个元素都给它一点动"：

| 元素 | 动效 | 周期 | 幅度 | 目的 |
|---|---|---|---|---|
| 宠物 · 呼吸 | 垂直浮动 | 2.8~3.7s（各只错相） | ±1.6 px | 生命感，最底层 |
| 宠物 · 溜达 | 水平位移 | 走 1.2~2.4s，停 1.8~4.2s | 55~150 px | 生命感，主要读点 |
| 宠物 · 踏步 | 走动时 y 高频抖动 | 7.5 Hz | 3.2 px | **缺这条就只剩平移，一眼假** |
| 宠物 · 点击 | 抛物线跳 + 冒 ♥ | 0.42s | 12 px | 点击回应 |
| `Btn-Go` 箭头 | 左右摆 | 1.9s | ±3 px | 主行动的持续邀请 |
| `HudTip` 提示条 | 上下浮 | 2.6s | ±2 px | 引导条，弱于主行动 |
| `GoCard` 宠物卡 | 心跳缩放 | 1.6s | 1.2% | 生命感 |
| `FogTop` / `FogBot` | 单向缓移 + 透明度呼吸 | 14s / 18s | 6 / 9 px，α 228~255 | 空气感 |
| 全部可点元素 | 按下缩放 | 即时（指数平滑，26/s） | 见 14.2 | 可点性 |

**明确不做的**：

- **徽标不做待机脉动。** 五个徽标同时脉动会全部抢注意力，反而没有一个显得重要。
  徽标只在按下时有反馈。注意力预算留给「出门」。
- **关卡进度 pip 不做呼吸。** `CLEARED = 0` 时 8 格全灭，让 `pip-0` 呼吸会被读成
  "第 1 关已完成"，是错的语义。
- **不做入场逐元素飞入。** 主界面是高频回访场景，每次进来都播一遍动画是负担。

**雾层只往一个方向位移**：雾图宽度正好铺满 1280，左右或向上移都会露边。
所以位移区间取 `[baseY − amp, baseY]`，只往下压，压下去的部分被背景吃掉。

### 14.4 移动形态：蹦跳也否了，走路必须有帧（v2.9 修订）

**两次判断都错，这里一并承认。**

| 版本 | 做法 | 实际读成什么 |
|---|---|---|
| v2.6 | 横移 + 7.5Hz 踏步 | "贴纸在滑 / 在倒退" |
| v2.7 | 蹦跳（抛物线 + 挤压拉伸） | "跳来跳去"，不是溜达 |
| v2.9 | 贴地碎步 + 前后走 + 近大远小 | 动作成立但**仍不迈腿**——素材只有一帧 |

结论一句话：**一只只有一张正面站立图的角色，做不出走路。** 这不是参数问题，
是素材问题。所有"用代码补出走路"的尝试都只能改变它的**位移方式**，不能改变
它的**肢体姿态**。

#### 当前实现（v2.9，已生效）

| 参数 | 值 | 依据 |
|---|---|---|
| 走动构成 | 60% 前后（深度）+ 40% 短距离横移 | 正视图角色**朝镜头走**才成立；横走距离一长立刻变"滑" |
| 横移距离 | 40 ~ 90 px/段 | 短到不足以让人注意到"没有迈腿" |
| 深度范围 | baseY −20 ~ +8 px | 出了这条带就离草地了；必须夹紧（见下方 bug） |
| 速度 | 28 ~ 40 px/s（平均），smoothstep 起停 | 84px 高角色的合理步速；线性起停像"被推了一下" |
| 步频 | `spd × 2.4` 步/秒，随速度变 | 匀速步频 + 变速位移 = 脚在原地打滑 |
| 碎步起伏 | 1.2 px | 大一点就变回"跳" |
| 摇摆 | 1.5°（每步一次） | 正视图不做镜像，方向只能靠倾 |
| 近大远小 | ±3%（`1 + yOff × 0.0016`） | 再大就暴露"这只是贴纸在缩放" |
| 停顿 | 0.9 ~ 2.6 s | 一直走像机器 |
| 点击 | 弹 10 px + 冒心 | 保留 |

**踩到的两个真 bug：**

1. **深度会越走越高。** 直接把 `pos.y` 当输入再写回 `pos.y`，每帧的呼吸（1.5px）
   会被当成新起点累加 —— 30 秒后宠物漂到离草地 250px 的地方。修法：`fy/ty` 全部
   改成**相对 `baseY` 的偏移**，写回时用 `baseY + yOff`。这条已写成断言
   （`走动不离开草地这条带`）。
2. **横走支路的 `ty` 没夹紧。** 每段 ±5px 累加，同样会飘走。

#### 要走真步，只能补帧——规格如下

| 项 | 值 |
|---|---|
| 帧数 | 6 帧/循环（接触 / 下沉 / 过渡 / 接触 / 下沉 / 过渡） |
| 帧率 | 12 fps（84px 的小角色不需要 24fps） |
| 单帧尺寸 | 128 × 128 透明底，脚底基线统一压在第 120 行 |

### 14.7 为什么只加脚本、不动场景文件

`Home.scene` 已经过了 17 项结构验证，且上一次手改场景刚触发过
`Cannot read properties of null (reading '_getUITransformComp')`。再动一次场景，
风险收益不成比例。

查了 Cocos 的预览构建记录，确认了可以绕开：

```
temp/programming/packer-driver/targets/preview/main-record.json
  └─ cce:/internal/x/prerequisite-imports
       ├─ .../assets/scripts/HomeRuntime.ts
       ├─ .../assets/scripts/PetWander.ts
       └─ ...（assets/scripts 下全部 .ts，含未被场景引用的）
```

`prerequisite-imports` 会 **import 所有项目脚本**，所以文件顶层代码**一定执行**。
于是 `HomeRuntime.ts` 在顶层注册场景启动回调自行接管，**场景文件一行没改**。

认主界面也**不靠场景名**，靠结构：`Canvas` 下同时有 `Badges` / `Dock` / `Pets`。
名字会改，结构不会。

### 14.8 存档回流：战利品怎么真正进池（v2.8）

`SettlementPanel` 原来自己写着 `'（资源入池在家园场景接线，M2）'` —— 打完一场，
家园顶部三个数字一个都不变。玩家第一次注意到之后，「出门」这个动作就失去意义了。

**架构定死一条：家园只读存档，写只发生在战斗结算。**

```
Battle ──settleInto()──▶ SaveData(localStorage) ──loadSave()──▶ Home
```

| 环节 | 在哪 | 做什么 |
|---|---|---|
| 读 | `GameBootstrap._save = loadSave()` | 进战斗时读一次快照，一局内不再重读（外部改档不影响这一局） |
| 写 | `director.onSettle` → `settleInto()` | 资源入池 + 关卡 +1 + 饱食度回写，**一次做完** |
| 显示 | `SettlementPanel.show(stats, loot, …)` | 只显示上面那份 loot，**不自己再算一遍** |
| 读 | `HomeRuntime.bindSave()` | 资源 / 关卡进度 / 出战人数 / 饱食度 / 出发卡文案 |

两处各算一遍是"面板说 +16、家园只 +14"这类对不上的经典来源，所以 `lootOf()` 只有一个实现。

**换算表**（`SaveData.LOOT`）。直接拿经验珠数当果子不行：一局满编约 390 珠，
而家园基线是 248 —— 一场翻倍，养成曲线一步走完。

| 资源 | 公式 | 满编通关一局 | 相对基线 |
|---|---|---|---|
| 果子 | 经验珠 ÷ 24 | +16 | +6%（248） |
| 材料 | 击杀 ÷ 16 | +18 | +53%（36） |
| 吧唧 | 击杀 ÷ 60 + BOSS 3 | +8 | +42%（12） |

材料与吧唧动得更明显是刻意的 —— 它们才是"要攒"的东西。果子是消耗品，涨太快反而破坏喂食的重量。

存档容错：键名带版本号（`pawpack.save.v1`），JSON 坏了回默认、值越界夹回区间、
存储不可用（隐私模式）就退化成内存态。**丢档不等于崩游戏，也不等于丢进度用崩来提示。**

### 14.9 饱食度：从两套口径收敛成一个数（v2.8）

| 侧 | 改造前 | 改造后 |
|---|---|---|
| 家园 GoCard | 抽象「饱食 12 / 20」+ 3 格同色小方块（**而且这 3 格从上线起就没渲染出来过**，见下） | `SaveState.satiety` 一个 0~100 的数，3 格按档位着色 |
| 战斗 `SATIETY` | 100 制、起始 100 | 起始值来自存档，其余不变 |
| 出发卡 | 「饱食 12/20」写死 | 读存档 |

一个属性两个量纲，玩家读不出是不是同一件事。现在只剩一个字段：家园读它、
战斗从它起手、结算写回它。

**3 格 bar 不是"三等分"，也不是"按比例填充"**，是按战斗里的档位线着色：

| 档位 | 区间 | 颜色 | 亮几格 | 火力 |
|---|---|---|---|---|
| 满饱 | ≥ 70 | 绿 `#6BCB77` | 3 | ×1.0 |
| **半饿** | 30 ~ 70 | **金 `#FFD700`** | 2 | **×1.5（最强）** |
| 全饿 | < 30 | 红 `#FF5252` | 1 | ×0.6 |

金色是"最强区间"的招牌色 —— 战斗里 `C_SATIETY_SWEET` 用的也是金。这样家园那条 bar
的形状本身就把「半饿最强」教给了玩家，不用等进战斗才知道。

参考 `shots/home-satiety-tiers.png`（上=满饱 100/100 绿，下=半饿 52/100 金）。

> **挖出来两个真 bug**
>
> **① 那 3 格 bar 从来没显示过。** `addPart()` 走的是相对 Canvas 中心的绝对定位，
> 只能挂到位置为 (0,0) 的容器上。GoCard 自己有位移（left 290 / top 633），
> 再 `addPart` 一次就叠了父偏移，三格跑到屏幕外 x ≈ −932。场景文件里完全看不出异常
> （坐标是合法数字，只是参照错了）。父节点有位移时必须走 `addSprite + inPart()`。
>
> **② 底色导致染色失效。** Cocos 的 Sprite `_color` 是**乘算** tint，只能变暗不能提亮。
> `belly-bar` 原来是橙 `#FFB56A`（蓝通道只有 106），乘上绿之后是橄榄色 ——
> 绿 / 金 / 红三档会糊成一片"脏橘"。改成近白底 `#FBF1E4`，乘算才是干净的档位色。
>
> 顺带给 `tools/_render-scene.js` 补上 tint 支持。它原来只处理 `a < 255`，
> 不处理 RGB 染色 —— 于是**所有靠颜色表达的语义在图里都看不见**。
> 用这种渲染器做 UI 评审，"颜色对不对"这一半等于没看。
