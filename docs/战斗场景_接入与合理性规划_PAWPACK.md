## 一、接入了什么

### 1.1 链路

```
Home.scene ──[出门 → 出发卡 → 出发]──▶ Battle.scene ──[结算 → 回家园]──▶ Home.scene
                                            │
                                            └─[再来一局]─▶ 原地重开
```

三条边都通了，不是单向。

| 环节 | 实现 | 触发 |
|---|---|---|
| 进战斗 | `director.loadScene('Battle')` | 出发卡「出发」按钮 |
| 重开 | `BattleDirector.restart()` + 各系统 `reset()` | 结算「再来一局」/ 空格 |
| 回家园 | `director.loadScene('Home')` | 结算「回家园」/ R 键 |

### 1.2 Battle.scene 为什么只有一个空节点

`GameBootstrap` 自己的注释写着契约：

> 「世界全部由代码搭建（相机/主角/英雄小队/敌人/BOSS/渲染器/HUD），不依赖任何编辑器内手动摆放」

所以场景只需要一个挂载点。于是：

```
Battle (Scene)
└── BattleRoot (cc.Node + cc.UITransform，零尺寸容器)
```

**场景里非 `cc.*` 类型数量 = 0。**

这一条很重要：把 `GameBootstrap` 挂进场景要写**压缩 uuid**，手写格式错了就是 `Open scene failed`。改成运行时 `addComponent(GameBootstrap)` 后，场景文件里根本不出现自定义类型 —— 反序列化失败这条路被彻底绕开。

### 1.3 三条硬约束（都是验证器在守的）

| 约束 | 为什么 |
|---|---|
| **不加 `cc.Canvas`** | 战斗侧所有 HUD 坐标都基于 `visibleHalfSize()`（相机视野 540 世界单位）。Canvas 会把自己的 UITransform 对齐到 1280×720 设计分辨率，两套基准混用 → HUD 整体偏移 |
| **不预置 `cc.Camera`** | `PlayerController` 在构造时自建唯一的正交相机并把 HUD 挂在它下面。预置第二个相机会出现双相机争渲染 |
| **BattleRoot 零尺寸** | 它只是容器，世界原点即屏幕中心。给它尺寸会让子节点坐标偏移 |

### 1.4 验证

| 验证器 | 项数 | 结果 |
|---|---|---|
| `tools/verify-battle-scene.js` | 16 | 全过 |
| `tools/_rt-check.js`（主界面运行时） | 49 | 全过 |
| `tools/verify-scene.js`（主界面结构） | 17 | 全过 |
| `tools/verify-roster.js`（队伍 / 存档 / 战利品） | 61 | 全过 |

Battle.scene 的 16 项查的是「基础设施是否完整」而不是主界面那套（Canvas 位置、相机 z 之类在这里不适用）：SceneGlobals 8 个配置齐全、无悬空 `__id__`、父子互指、无 Canvas、无预置相机、`UITransform.node` 反向引用。

### 问题 1 · 队伍人数对不上（P0）✅ 已修

| 侧 | 改造前 |
|---|---|
| 主界面 | `ACTIVE = "sugar-stand"`、`CLEARED = 0` → 家里只有**1 只**砂糖 |
| 战斗配置 | `HERO.count = 3`，`HERO_SLOTS` 是 3 个槽位（左后/右后/正后） |

**后果**：玩家带 1 只宠物出门，进战斗却出现 3 个跟班。这不是数值问题，是"我养的宠物和场上打的不是同一批"——最伤代入的那一类断层。

**修法：删掉 `3` 这个数字本身，而不是把 3 改成 1。**

新建 `config/Roster.ts` 作为唯一真值：

```
已通关数（存档）
   └─▶ squadSize()   → 出战人数 = min(已解锁数, 3)
         └─▶ rolesFor() → N 个「槽位 + 技能」
               └─▶ HeroSquad 实例化 N 个
               └─▶ powerScale() → 敌人数量 / BOSS 血量
```

于是随解锁从 1 长到 3（解锁骨 1 / 3 关），养成有正反馈，两边**永远**一致。

顺带修掉三处派生问题：

| 问题 | 修法 |
|---|---|
| `Formation.slotTarget(i)` 按索引取槽位，隐含"槽位数 = 人数" | 改成 `slotTarget(slot, out)`，槽位跟着角色走。人数一变就不会再出现"1 只时被夹到左后槽位、读成站偏了" |
| 单人时用左后槽位没有对称对象 | `rolesFor(1)` 给正后方 `[-40, 0]` |
| 只有 1 只宠物时要打为 3 人标定的 20 波 | 敌人数量与 BOSS 血量乘 `powerScale = 人数 / 3` |

**配平为什么数量与血量都要乘**（只乘一个都不行）：

- 只减数量 → 甲虫（60HP）相对更耐打，1 只宠物要打 5 发，节奏比满编慢一倍；
- 只减血量 → 同屏怪数不变，1 只宠物会被 6 个方向同时逼近，走位失效。

目标不是"让 1 只宠物也打得过 3 只的量"，而是**让每一局的时长量级保持一致**。
满编单体 DPS ≈ 44.8（12/0.72 + 16/1.05 + 8/0.62），1 只贯穿 ≈ 16.7 —— 37%。
1/3 与 37% 同阶，所以按线性缩放是合理的起点。

> ⚠️ 这是**离线推算**的首次配平，不是实测值。首局真跑后按 `BattleStats.timeMs` 复核，见问题 5。

### 问题 2 · 饱食度两套口径（P0）✅ 已修

| 侧 | 改造前 |
|---|---|
| 主界面 GoCard | 「饱食 12 / 20」+ 3 格 belly bar |
| 战斗 `SATIETY` | `max 100`、`start 100`、档位线 70 / 30 |

**后果**：同一个属性在两个界面用两个量纲。玩家在家园看到"12"，进战斗看到一条接近满的条——他不知道是不是同一件事。

**修法：字段化。** `SaveState.satiety`（0~100）成为唯一真值：家园读它、战斗从它起手、结算写回它。

3 格 bar 顺手改成按档位着色（**不是三等分、也不是按比例填充**）：

| 档位 | 区间 | 颜色 | 亮几格 | 火力 |
|---|---|---|---|---|
| 满饱 | ≥ 70 | 绿 `#6BCB77` | 3 | ×1.0 |
| **半饿** | 30 ~ 70 | **金 `#FFD700`** | 2 | **×1.5（最强）** |
| 全饿 | < 30 | 红 `#FF5252` | 1 | ×0.6 |

**这只是纯 UI 改动，却顺手把「半饿最强」教给了玩家** —— 金色就是最强区间的招牌色，
战斗里 `C_SATIETY_SWEET` 用的也是金。玩家不用等进战斗挨打才知道该饿着打。

两个实现坑（都是真 bug，不是风格问题）：

1. **那 3 格 bar 从上线起就没渲染出来过。** `addPart()` 走相对 Canvas 中心的绝对定位，
   只能挂位置为 (0,0) 的容器；GoCard 自己有位移，叠一次父偏移三格就飞到屏幕外 x ≈ −932。
   场景文件里看不出任何异常（坐标合法，只是参照错了）。
2. **底色导致染色失效。** Cocos 的 Sprite `_color` 是乘算 tint，只能变暗不能提亮。
   `belly-bar` 原来是橙 `#FFB56A`（蓝通道仅 106），乘绿之后是橄榄色 —— 三档糊成一片"脏橘"。
   改近白底 `#FBF1E4`，乘算才是干净的档位色。

### 问题 3 · 战利品不回流（P0）✅ 已修

`SettlementPanel` 原来自己写着：

> `'（资源入池在家园场景接线，M2）'`

**后果**：打完一场，家园顶部的苹果/木材/金币一个都不变。玩家第一次注意到之后，"出门"这个动作就没有意义了。

**架构定死一条：家园只读存档，写只发生在战斗结算。**

```
Battle ──settleInto()──▶ SaveData(localStorage) ──loadSave()──▶ Home
```

| 环节 | 位置 | 做什么 |
|---|---|---|
| 读 | `GameBootstrap._save = loadSave()` | 进战斗读一次快照，一局内不再重读 |
| 写 | `director.onSettle → settleInto()` | 资源入池 + 关卡 +1 + 饱食度回写，一次做完 |
| 显示 | `SettlementPanel.show(stats, loot, squad, cleared)` | 只显示上面那份 loot，不自己再算 |
| 读 | `HomeRuntime.bindSave()` | 资源 / 进度 / 出战人数 / 饱食度 / 出发卡文案 |

**换算表**（`SaveData.LOOT`）。直接拿经验珠数当果子不行：一局满编约 390 珠，
家园基线 248 —— 一场翻倍，养成曲线一步走完。

| 资源 | 公式 | 满编通关一局 | 相对基线 |
|---|---|---|---|
| 果子 | 经验珠 ÷ 24 | +16 | +6%（248） |
| 材料 | 击杀 ÷ 16 | +18 | +53%（36） |
| 吧唧 | 击杀 ÷ 60 + BOSS 3 | +8 | +42%（12） |

材料与吧唧动得更明显是刻意的 —— 它们才是"要攒"的东西。

**顺手接上了关卡推进**：通关 `cleared + 1`（封顶 8），驱动宠物解锁与出战人数。
打赢一场 → 年糕回家 → 下一局队伍变 2 只。这条链路是"出门"唯一的意义来源。

为了让"家里真的多出一只"，`make-scene.js` 改成**六只全部预置 + `active` 开关**
（原来未解锁的根本不建节点）。理由：家园贴图不在 `resources` 下（走 UUID 直连），
运行时拿不到，预置 + 开关是唯一不需要改资源管线的做法。

### 问题 4 · 无失败惩罚 → 躲伤害没有收益（P1）⏸ 待拍板

| 现状 | 后果 |
|---|---|
| HP 6，归零 = "体力不支撤退"，**照样带走全部战利品**（红线②） | 玩家最优策略是站桩输出。而核心操作是 WASD 走位 —— 走位变成纯装饰 |

**这条不是"设计错了"，是"红线②和核心操作打架"。**

**建议方案：不给"死亡惩罚"，给"效率差异"。**

| 结局 | 战利品系数 |
|---|---|
| 通关（击杀 BOSS） | ×1.0 + BOSS 掉落 3 吧唧 |
| 主动撤离 | ×1.0 |
| HP 归零 | **×0.6** |

"体力不支时东西掉了"符合直觉，也不清零 —— 红线②说的是"没有游戏结束"，不是"没有任何代价"。

**代码已经留好口子，只差一个数字**：`SaveData.LOOT.mulHp0`，现在写的是 `1.0`
（= 与主动撤离等价）。你点头后改成 `0.6` 即可，`verify-roster.js` 里那条断言会自动跟着切。
`docs` 与代码注释都标了"待拍板"，不会有人误以为是漏改。

### 问题 5 · 单局时长与波次数量对不齐（P1）⏸ 待实测

`SATIETY` 的注释里有两处自相矛盾的记录：

- 「改技能后一局缩到 **约 90 秒**」
- 但 `WAVE.total = 20`、`WAVE.interval = 3.0`

20 波哪怕每波只打 4.5 秒，加上 19 次 3 秒间隔，也是 `20×4.5 + 19×3 = 147 秒`。

**后果**：饱食度按 90 秒标定的（掉 81 点、喂 2 次），实际打 147 秒会掉 132 点 →
玩家必须喂 4 次，肉块消耗翻倍，"喂食是有代价的决策"变成"一直在喂"。

**方案：先量一次真实单局时长再定标。** `BattleStats.timeMs` 本来就在统计里，跑 3 局
把实际值记下来，然后二选一：

- 波次压到 12~14 波、间隔 3s → 约 90 秒，现有饱食度标定不动；
- 保留 20 波 → `decayPerSec` 降到 0.55 左右。

**先测再调，不要凭注释改数值。** 沙箱里启动不了 Cocos 预览（进程 3 秒即退），
这一条必须你在编辑器里跑一次才能定。

| 验证器 | 项数 | 查什么 | 结果 |
|---|---|---|---|
| `tools/verify-scene.js` | 17 | 主界面结构（基础设施 / 坐标基准 / 引用完整性） | 全过 |

| `tools/verify-roster.js` | **61** | **三条跨模块等式 + 存档容错 + 战利品换算** | 全过 |
| `tsc -p tools/tsconfig.all.json` | — | 全量 strict 类型 | 0 error |

`verify-roster.js` 是这一轮新增的，也是最该有的一个 —— 它查的三条等式
**只靠界面截图看不出来**，但一旦漂移玩家会立刻感觉到"假"：

```
① 出战人数 = min(已解锁数, 上限)              家园几只 ↔ 场上几只
② 饱食度 = 存档里的那一个数                   家园 bar ↔ 战斗 HUD
③ 结算战利品 = 面板显示 = 真正入池              面板说 +16、家园只 +14 这类
```

它同时把存档当成"外部输入"来打：损坏的 JSON、越界的值、空的 active、浮点场次。
存档是全程序唯一一个不能假设"是本程序写的"的数据。
